# Changelog

## Unreleased

- Every application closes on Ctrl-C, headless ones included. `application::BaseApplication` now owns the application message bus, its `application` scope, and the `Events` channel, and Ctrl-C posts `Events::Close` there. A runtime that owns its loop reads `next_event` every tick and stops on `Close`; worker threads and tools subscribe to or post on `events`. `GraphicsApplication::messages` and `message_bus` return the base application's, and when another library already installed the process's interrupt handler, the engine warns instead of panicking.
- Builds without the `headed` feature keep `gameplay::DefaultWorld` and authoring audio graphs, so a server can run the same gameplay code as the windowed game, with the sprites and sounds it posts going unheard. The world leaves out only cameras and poses there, and the `audio` module only `DefaultAudioSystem`, which plays graphs through the audio hardware. A headless build also compiles again: it used to fail on the nightly features only the UI uses.
- BETP payloads are as long as the data they carry, up to 1024 bytes (`betp::packets::MAX_PAYLOAD_SIZE`), instead of always 1024. A `Data` packet is 19 bytes plus its payload and a `Message` 21 plus its payload, so an isometric arena move order, a 10-byte payload, goes out in 31 bytes instead of 1045, and an isometric arena snapshot of three characters in 58 instead of 1043.
  - Sessions, the `network::datagram` pipelines, and `network::Client`, `Server`, `ChannelClient`, and `ChannelServer` send and deliver `betp::packets::Payload`, re-exported as `network::Payload`: a fixed-capacity buffer that holds up to 1024 bytes without allocating. Build one with `Payload::new`, which returns `PayloadTooLarge` for more, and read it as a byte slice.
  - `PacketReadError::InvalidPacketLength` reports the range of lengths a packet type allows, as `min` and `max`, which are equal for every type but `Data` and `Message`. `betp::MAX_PACKET_SIZE` names the longest packet, 1045 bytes.
- The `inspector.port` parameter moves the HTTP inspector off its default port, 6680, so two applications can run on one machine. Before, the second one to start panicked. `inspector::http::HttpInspectorServer::new` takes the port, and `inspector::http::DEFAULT_PORT` names the default.
- `network::ServerEvents` names the connection events `network::Server::drain_events` reports, so applications can match on them without depending on `betp`.
- BETP delivers reliable payloads once and in the order they were sent, and never gives up on them while the connection lasts. Reliable payloads travel as `Message` packets, which alone take sequence numbers, so a receiver knows that a gap is a message still to come. It holds up to 32 messages (`betp::WINDOW`) that arrive early and delivers each run once the gap fills. The sender keeps up to 32 messages unacknowledged and queues the rest, and resends each one every 100 ms (`betp::RETRY_INTERVAL`) until it is acknowledged. Unreliable payloads travel as `Data` packets, are sent once, and are delivered as they arrive.
  - Before this, reliable and unreliable packets shared one sequence and were delivered in arrival order, and a reliable packet was resent on every update until its eight attempts ran out, or dropped when 16 packets were already queued. A short burst of loss could lose a reliable payload for good, and two could arrive in the wrong order.
  - Every packet on an established connection, keepalives included, carries the acknowledgement of the messages received. A session that receives a message acknowledges it in its next update, with a keepalive when it has nothing else to send.
  - Sessions deliver payloads themselves: read them with `drain_received` on `betp::client::Session`, `betp::server::Session`, and the `network::datagram` pipelines, which no longer report an `Accepted` outcome. `network::ChannelServer::drain_received` returns each payload with its sender's connection id, as `network::Server` does, and the in-process channel transport no longer delivers data that arrives before a connection is established. `network::Client::send` keeps payloads queued before the connection is established and sends them once it is, where it used to discard them.
  - On the wire, `Data` packets lose their sequence and are 1043 bytes, `Message` packets are 1045, and keepalives are 19. `ConnectionStatus` is replaced by `packets::Acknowledgement`, and `Packets::wire_size` returns any packet's length. `betp::Local` and `betp::Remote` are gone.
  - `betp::server::Session` no longer has `connect` or the client-side handshake states, which only clients use.
- Networked games can host and join BETP sessions over UDP. `network::Server::bind` opens one socket that serves up to 64 clients, each with its own handshake and session, told apart by the address it sends from. `network::Client::connect` joins a server, and keeps asking until the server answers, so a client may start before the server does. Call `update` on both once per tick. A server reports `ClientConnected` and `ClientDisconnected` through `drain_events`, and each payload through `drain_received` with the connection id of the client that sent it. Dropping a client or a server tells the other end that the session ended, so it does not wait for a timeout.
  - Before this, neither adapter decoded what it received, and the client sent a 1024-byte buffer that a 1045-byte data packet does not fit, so no session could be established over UDP. Both now pass every datagram through the same `network::datagram` pipelines that the protocol tests use.
  - Each session gets random handshake salts, so two clients no longer get the same connection id.
- BETP sessions stay open while neither side has anything to send. A connected session that has sent nothing for 250 ms (`betp::KEEPALIVE_INTERVAL`) sends a keepalive, a 13-byte packet that carries only the connection id and never reaches the application. Each side ends the session once it has heard nothing from the other, neither data nor a keepalive, for 5 seconds (`betp::TIMEOUT`).
  - Before this, the server disconnected a client that sent nothing for 5 seconds, so a player who did not act for that long was dropped, and a client never noticed a server that disappeared without saying so. A `network::Client` now reports `is_connected` as `false` once its server has been quiet for 5 seconds.
  - The client session now takes the time in `betp::client::Session::update`, as the server session does, and so does `network::ChannelClient::update`.
- A BETP client counts as connected only once the server confirms it, so a lost challenge response no longer leaves a client that believes it is connected to a server that never accepted it. The client resends its challenge response on every update until the server sends anything on the connection, and gives up after 5 seconds (`betp::TIMEOUT`). A server that accepts a client sends a keepalive at once, unless a payload goes out first, so the handshake takes half a round trip longer than before.
  - `betp::client::Session::has_ended` reports a connection, or an attempt to make one, that has ended. `network::datagram::ClientDatagramPipeline::advance` reports `Disconnected` for both and no longer reports `Connected`: check `is_connected` instead.
- Physics bodies that have come to rest sleep, and a step leaves them out: it does not move them, test them against each other or against bodies without mass, or publish their transforms. A world whose bodies all sleep takes no time to step. On an Apple M4, a pile of a thousand one-meter boxes dropped ten layers deep, as the cubes demo drops them, steps in about 570 µs while it settles and in no measurable time once it sleeps, 10 seconds after the first boxes were spawned. With half of them spheres, as the demo has them by default, a step takes about 400 µs, about 90 µs after 10 seconds, and about 50 µs from 30 seconds on, for the spheres that rolled away and keep rolling.
  - Each body sleeps on its own, once it has stayed within 2.5 cm and 0.05 radians of where it was for half a second, whatever the bodies that touch it do, and it loses what speed it had left. So a body that moves slower than 5 cm a second stops. Bodies that a `physics::Constraint` holds together, through any number of others, sleep together once all of them have stayed.
  - To the bodies that are awake, a sleeping body is as fixed as a body without mass: they lie on it and lean on it without moving it. A sleeping body wakes in the step in which a body comes within 5 cm of it that moves faster than half a meter a second, or that has moved more than 2.5 cm since the current half second began. The step finds the contacts of the bodies that wake, with what they lie on and lean on, in a second round of its search for contacts, so a box that lands on a sleeping box pushes it no further into the ground than it pushes one that is awake. A body that falls away from under a sleeping body wakes it within three steps. A body that pushes into a sleeping body slower than half a meter a second is stopped by it, as by a wall.
  - Bodies in a pile that is at rest move faster than a tenth of a meter a second now and then, for a step, as their contacts close the small gaps between them, which is why it takes half a meter a second to wake a body. At a tenth, the thousand boxes woke each other all the time and two thirds of them never slept, and at a quarter they slept after 22 seconds. Letting bodies that touch sleep only together, as one island, made the boxes sleep after 26 seconds, and let spheres that rolled about the pile wake all of it every few seconds.
  - A sleeping body also wakes when it is pushed with `DynabitWorld::apply_impulse`, given a transform that moves it, or taken hold of or let go by a constraint, and when a body near it appears, is given a transform that moves it, or is removed. A transform that puts a body where it already is wakes nothing.
  - `DynabitWorld::set_sleeping(false)` keeps every body awake. The physics benchmark keeps its piles awake, and with them awake, a step is no measurably slower than before.
- Physics contacts are recycled, as Box2D recycles them (https://box2d.org/posts/2026/10/contact-recycling/). A pair of bodies whose contacts take a search over their shapes, which is a pair with a hull or with a shape that turns with its body, such as a box that rotates, gets the contacts it had in the last step instead of searching again, for as long as its bodies have moved less than 2 cm and turned less than 0.05 radians relative to each other since the contacts were found, and neither has turned more than 0.05 radians. A recycled contact keeps its normal and its points' offsets from their bodies as they were in the world, and how deep it reaches follows from how far each body moved, with its offsets turned the way the body turned.
  - On an Apple M4, steps of the benchmark pile of 128 bodies take 28.5% less time, and of the pile of 65,536 bodies, which is still falling when it is timed, 3.6% less. With every body awake, a step of the cubes demo's pile of a thousand rotating boxes takes about 470 µs once it has settled, from about 570 µs, and with half of them spheres about 325 µs, from about 400 µs.
  - A pair whose bodies a constraint holds is searched again in every step, since the constraint can press them into each other however little they move, and so is a pair whose bodies move apart faster than 2 cm in a step, which could not recycle its contacts in the next step either. Skipping those pairs is what keeps a pile that is still falling from stepping 2% slower.
  - Each lane keeps the contacts of the pairs it found, and a pair's contacts are found in whichever lane's part has them, so that the contacts a pair gets do not depend on the number of lanes or on how long they took.
  - A box that tips a little on another one keeps the four corners of the patch they touched over, where a search finds it on one edge.
- Contact friction starts every step from the impulses that held the bodies in the step before, as the push that holds them apart already did. A pile leans on friction, and when it started from nothing, the passes of one step did not work it out through a deep pile. A thousand boxes dropped ten layers deep kept creeping: twenty seconds after they were dropped, a few hundred of them still moved more than a centimeter in half a second, where fewer than ten do now. Two boxes stacked on a slope that friction holds them on slid 11 and 14 cm in ten seconds, and now stay where they are.
  - Every contact keeps three impulses for the next step instead of one. Steps of the benchmark piles take 3.9% longer at 65,536 bodies and 2.6% longer at 128 on an Apple M4.

- A physics joint can give way gradually instead of turning freely until a limit stops it dead, as the joints of a body do. `physics::Constraint::with_resistance` takes a function that returns the torque, in newton meters, that holds the second body back when it is turned by an angle from the pose the bodies are in during the first step that the world has both. Return more for larger angles, and the joint turns until the torque matches what turns it and has taken up the speed it came with.
  - The torque only brakes. It slows a body that turns further away, as far as stopping it, but does not turn it back and leaves alone a body that turns back. So a limb stays where it is brought to rest, and swings back freely when something pulls it back.
  - The angle counts every way of turning together, leaning and twisting alike. The resistance works on every kind of constraint, and the limits of a joint still stop it where they are set, so a ball joint without limits and with a resistance has no hard stop at all.
  - It is one more row, about the line that the second body has turned about since that first pose, that may apply no more impulse in a step than the torque gives. A bar of a kilogram that sticks out from a ball joint and falls under gravity of 16 comes to rest leaning 1.21 radians with a resistance of 10 newton meters a radian, and 0.39 with 40, which is where the resistance has taken up what the bar gained by falling.
- Two physics bodies can be joined by a ball joint, which with the hinge and the constant velocity joint is enough to build a ragdoll. Create a `physics::Constraint::ball` with the handles of the two bodies, an axis, and two optional limits. The physics world keeps the anchors of the two bodies at the same place and lets the second body turn any way about them.
  - The limits count from the axis, a direction of the first body that should point along the limb the second body is, and from the pose the bodies are in during the first step that the world has both. `lean` is a `math::Radians`: how far the second body may lean away, the same to every side. `twist` is a range of them: how far back and how far on it may turn about its own length. Without either, the joint turns freely that way. Set `lean` when you set `twist`, because a joint that is folded all the way back on itself has no twist to tell.
  - The joint is three rows that pin the anchors together, and one more for each limit. Both stop the joint at the limit instead of a step's turn beyond it. A bar that spins at 6 radians a second about its length stops within 0.03 radians of either end of its twist limit, while gravity leans it to within 0.03 radians of its lean limit.
  - A ragdoll of ten boxes and nine joints of the three kinds, pushed over from standing, comes to rest lying on the ground with every joint within 3 cm. While it falls, its joints give up to 9 cm: the knees, when legs of 2 kg each take the weight of the rest of the figure, which is eleven times that. They take up 5% of that in a step.
  - `physics::constraint::Kind` has a `Ball` variant.
- Two physics bodies can be joined by a constant velocity joint, which is what the shoulders and hips of a ragdoll are made of. Create a `physics::Constraint::constant_velocity` with the handles of the two bodies, the direction of the joint's axis as the first body has it, and an optional limit. The physics world keeps the anchors of the two bodies at the same place, and lets the second body lean away from the first any way, but not twist relative to it about the axis, as the two halves of a drive shaft do: when one turns about its length, the other turns as fast about its own.
  - The limit is a `math::Radians`: how far the second body may lean away from the pose the bodies are in during the first step that the world has both, the same to every side. `None` lets the joint bend freely. Like a hinge, the joint stops at its limit instead of a step's turn beyond it.
  - The joint is up to five rows: three that pin the anchors together, one that takes up the twist, and one for the limit. The twist is limited about the line halfway between the axis as each of the two bodies has it, which is what keeps the two turning equally fast however the joint is bent. That line is lost when the joint is folded all the way back on itself, so set a limit, or keep the bodies from leaning that far.
  - A bar that hangs from such a joint and is knocked into a swing while it spins at 6 radians a second about its length stays within 0.03 radians of no twist. A bar that is carried around a limit of 0.5 radians at 4 radians a second stays within 0.05 radians of it, and one that gravity leans against the limit rests within 0.03.
  - `physics::constraint::Kind` has a `ConstantVelocity` variant.
- Two physics bodies can be joined by a hinge, which is what the joints of a ragdoll are made of. Create a `physics::Constraint::hinge` with the handles of the two bodies, the direction of the hinge's pin as the first body has it, and an optional limit. The physics world keeps the anchors of the two bodies at the same place, and lets the second body turn relative to the first about the pin only, as a door does on its frame or a forearm at the elbow.
  - The limit is a range of `math::Radians`: how far back and how far on the second body may turn about the pin, counted from the pose the bodies are in during the first step that the world has both. `None` lets the hinge turn freely. A hinge stops at the end of its limit instead of a step's turn beyond it, because it only lets the bodies turn as fast as brings them to that end during the step.
  - A hinge is up to six rows that a step solves in turn, where a distance constraint is one: three that pin the anchors together along the axes of the world, two that keep the pins of the two bodies along each other, and one for the limit. Each takes up 5% of what its bodies are off in a step, and leaves alone the last 5 mm or 0.005 radians. A bar hinged at one end that swings at 7 radians a second stays within 4 cm of its hinge. Three bars hinged in a row to a fixed point, each limited to 0.3 radians, hang within 0.04 radians of their limits.
  - Bodies that a constraint holds still collide with each other, so shape and place the parts of a ragdoll so that they do not touch in the poses their hinges allow.
  - `Constraint::kind` returns what a constraint holds its bodies to, as a `physics::constraint::Kind`. It replaces `Constraint::length`.
- Two physics bodies can be held a set distance apart. Create a `physics::Constraint::distance` with the handles of the two bodies and a length, the way a `Body` is created, and the physics world keeps a point of each body that far from the other, as a stiff rod between them would. The bodies stay free to turn about those points, which `Constraint::with_anchors` places on them. Delete the handle the constraint was created with to let the bodies go. In the physics benchmark on an Apple M4, which has no constraints, steps take the same to within 1%.
  - `physics::dynabit::World::new` takes a listener for created constraints, between the one for created bodies and the one for deletions. `gameplay::DefaultWorld` gives it one, so `world.create(Constraint::distance(..))` is all an application needs.
  - A constraint names its bodies by handle and acts in every step that both are in the world. So constraints and bodies can be created in any order, and a body that is created again with its handle is held like the one before it. A constraint whose body was deleted stays in the world without acting until it is deleted too.
  - A step takes its constraints through three parts, between finding the contacts and moving the bodies. One lane gets them ready once the contacts are found, and starts their bodies off with the impulse of the last step. Before each pass over the contacts, one lane solves the constraints in turn, four times over: it gives the two bodies of each the impulse along the line between their anchors that stops the anchors from closing or parting. The contacts follow, so they have the last word on where bodies may be. After the last pass, each constraint keeps its impulse for the next step, unless it is not a number, and no more than 100,000 N s of it. A world without constraints has no stage for them.
  - Constraints that share a body, as the links of a chain do, only carry each other's load once they have reacted to each other, so a step solves them sixteen times: four before each of its four passes over the contacts. That is enough because every step starts from the impulses of the one before. Twelve links that hold a body of ten times their mass come to be 7 cm off their lengths together. They were 42 cm off with one solve before each pass, and 96 cm off with four that start from nothing. On an Apple M4, a step takes about 0.3 µs longer for every constraint.
  - Bodies move straight on for a step where a rod would swing them, which leaves the anchors a little off their length. Each step, the constraint has the anchors close or part at the speed that takes up 5% of that, and leaves the last 5 mm alone. A pendulum of 2 m that swings at up to 8 m/s stays within 7 cm of its length. A larger share holds a single rod closer, but made a chain that carries a heavy body come apart.
  - A constraint only acts along the line between its anchors. With a length of zero it has no line until the anchors have come apart, so it follows them about as far behind as they move in a step and does not pin them to each other.
  - `PhysicsBody::to_world` returns where a point of a body is in world space.

- A fast body of any shape no longer passes through another body between two physics steps. Until now only a fast sphere was tested along its path, and only against other spheres, so a fast box, capsule, or hull, or a fast sphere at a thin wall, could end a step on the far side of what it should have hit. In the physics benchmark on an Apple M4, a step of the pile of 65,536 bodies takes 1% less than before, and a step of the pile of 128 the same to within the 1% that runs differ by.
  - Two bodies that are apart are also tested along their paths when a step carries a point of one further than half of what its shape reaches where it is thinnest, by its linear velocity and its spin together. `PhysicsBody::outruns_its_shape` tells that for every shape, where it was only ever true for a sphere, and `PhysicsBody::swept_bounds` covers the path of every such body.
  - The paths are followed by conservative advancement: GJK tells how far apart the shapes are and along which direction, the bodies' velocities and spins bound how fast that gap can close, and the bodies are moved on for the time that takes at least, up to ten times. Two spheres keep their closed form. Bodies that meet get the contacts they would have where they meet, at up to four corners of a flat side, with the time they meet at, and the solver holds them to the speed that brings them together as the step ends, as it did for spheres.
  - `physics::rounded_shapes_contact` takes how far apart two shapes may be and still get a contact, before its working storage. Such a contact has a negative depth, which is the gap. Pass zero for what it returned before.

- The alley splits data between lanes, so code that runs on every lane writes its own part without locks and without `unsafe`. Physics has neither left: it took a lock for every lane in every stage of a step, and kept lanes apart in `unsafe` code of its own. In the physics benchmark on an Apple M4, a step of the pile of 65,536 bodies takes the same, and a step of the pile of 128 takes about 2% more, a microsecond.
  - `core::alley::LaneOwned` gives every lane a value of its own, and `LaneRanges` gives every lane a range of one array, in balanced ranges or at split points you choose. Call `lend` with `Alley::id` before a dispatch. A lane takes its part with `own`. A stage that runs on one lane switches between that and every lane reading everything, with `join` and `split`. Taking a part on a lane of another alley, twice, or while it is joined, panics.
  - `core::alley::PairBatches` sorts items that each write two entries of an array into batches that write no entry twice, as the contact solver did for itself. Lanes work through one batch in a stage of `ConcreteLane::each_ref_keyed`, whose key is the batch and which fails unless every lane passes the same one. Each group of items gets a `Claim` on its entries, which `LaneRanges::batch` checks before it lets the lane reach them. Mark an entry that items only read, such as a body that contacts never move, with `PairBatches::FIXED`.
  - `physics::SweepBounds::repair`, `merge`, and `fill` take the lane that calls them, and `merge` is no longer `unsafe`. Call `SweepBounds::lend` before the dispatch, `share_order` between `repair` and `merge`, and `share_cells` after `fill`. `SweepBounds::rebuild` takes an alley and rebuilds on every lane of it.
  - A lane function can no longer share its `ConcreteLane` with another thread: the lane is proof, to storage that is split by lane, that the lane itself is asking.
  - `utils::StableVec::slots_mut_unchecked` returns a `SlotsMut` iterator. Wrap a `StableVec` in a `LaneRanges` to change its values from several lanes without `unsafe`.

- More of a physics step runs on every lane. In the physics benchmark on an Apple M4, a step of the pile of 65,536 bodies takes 5% less, and a step of the pile of 128 takes the same. The simulation does not depend on the number of lanes, as before. It differs a little from the last version, because the grid that pairs of bodies are looked for in is laid out from other boxes.
  - Lanes publish the transforms of the bodies they move, where one lane published them all. Transforms of one lane's bodies come in slot order, and the lanes' runs follow each other as they finish, so the order of a step's transforms is no longer the same from one run to the next.
  - `core::channel::Channel::send_many` publishes many messages at once. `DefaultChannel` reserves room for a run of them with one step instead of one for each message, so publishers that each send many do not contend for every slot. Messages of other publishers can come between two runs.
  - Lanes merge the runs of the swept bounds' order that they repaired and write the sorted bounds, each a part of them, where one lane moved the bounds that changed runs and wrote all of them. That lane's work took between 0.5 and 1.5 ms of a 20 ms step, most when many bounds changed runs at once. Have every lane call `physics::SweepBounds::merge` between `repair` and `lay_out`.
  - Sorting the contacts into batches reads the bodies of each contact as two numbers, and keeps the batches of the body whose contacts it is passing over at hand. This is still one lane's work, about 0.7 ms of that step: each contact's batch depends on the batches of the contacts before it.
- Physics steps always run as an execution of the alley, and leave less work to one lane. `physics::dynabit::World::update` and `gameplay::World::update` take the alley as their last argument, and `update_with_alley` is gone: the step that ran on the calling thread without lanes was a second implementation of the same simulation. A step that the world's `StepLanes` give one lane still runs on the calling thread, because `Alley::execute_phased` runs a single lane there instead of waking a worker. In the physics benchmark on an Apple M4, steps of piles of 16,000 to 64,000 boxes, spheres, capsules, and mixed shapes take 5% to 12% less, and steps of 4,000 take up to 6% less. The simulation is the same as before, on any number of lanes.
  - Every lane now applies gravity to its share of the bodies, gives the solver what it needs of them, and works out the bounds they sweep through. At the end of the step, every lane gives its share of the bodies their new velocities and moves them. One lane used to do each of these, in a pass over all bodies each.
  - Lanes repair the order of the swept bounds, each a run of it, before one lane moves the few bounds that belong in another run. `physics::SweepBounds::stage` no longer sorts or returns whether there are cells to fill: call `SweepBounds::repair` with every part and then `SweepBounds::lay_out`, which returns it.
  - The impulses that the next step's contacts start from are kept in a table that every lane adds its own contacts' impulses to at the same time. A stamp in each slot tells the last step's impulses from older ones, so the table is never emptied.
  - Lanes note the bodies each contact changes while they find the contacts, so sorting the contacts into batches, which one lane does, reads neither the contacts nor the bodies again.
  - `utils::StableVec::slots_mut_unchecked` returns the values in a range of slots for one thread to change while other threads change other slots. It is `unsafe`: the caller keeps the ranges apart and everything else away from them.
  - The physics benchmark has two rows, where it had sixteen for the alley and as many for the calling thread, and runs in about half a minute. `small/128` steps a pile of 128 bodies, which shows what a step costs whatever its size, and `large/65536` steps a pile of 65,536, which shows what a step costs as a world grows. Both piles mix spheres, boxes, capsules, boxes that rotate, and convex hulls, so their times do not compare with the earlier rows.
- Physics steps on the alley take less time. In the physics benchmark on an Apple M4, alley steps of piles of 4,000 to 16,000 spheres, capsules, and mixed shapes take 7% to 21% less, steps of 4,000 boxes that rotate take 30% less, and steps of 4,000 prisms that collide as hulls take 16% less. Steps of boxes that only rest on the ground take about 3% less. The simulation is the same as before.
  - An `Alley` dispatch runs any number of collective sections that return a value without size, such as `()`. It used to run 32 sections of any kind. Sections that return other values still have room for 32, because a dispatch keeps their values until it ends. Return `()` from `ConcreteLane::broadcast_mut`, `each_ref`, `broadcast`, and `each` when they run in a loop. One set of counters now keeps the lanes together through every section in turn, and starting a dispatch no longer writes the storage for all 32 sections: in the alley benchmark an empty dispatch on four lanes takes about 2.6 µs where it took 3.7 µs.
  - `World::update_with_alley` shares every batch of 32 or more contacts between lanes. It used to share the first four, which was all the sections of a dispatch allowed, and one lane prepared and solved the rest: a fifth to a third of the contacts of a pile of spheres or capsules, and more than half of those of a pile of boxes that rotate.
  - Lanes split the search for contacts by how long each lane's share took in the last step, where they used to take equal shares of the swept bounds. In a pile, one lane's share often took half as long as another's, and every lane waited for the slowest. The contacts come out in the same order whatever the shares are.
- Physics steps take less time. In the physics benchmark on an Apple M4, steps of piles of 16,000 to 64,000 boxes, spheres, and capsules take 4% to 12% less, on one thread and on the alley, and steps of 4,000 prisms that collide as hulls take 21% to 24% less: 13.5 ms on one thread and 4.7 ms on the alley, from 17.7 ms and 6.0 ms.
  - The contact solver keeps what a step's contacts need to know about each body in one cache line: where its center of mass is, its inverse mass and inverse inertia in world space, its elasticity and friction, and its velocity. It is worked out once for each body, on the lanes of an alley step, where it used to be worked out from the body for every contact the body is in, which is four or five for a body in a pile. A ball, and a body that does not rotate, needs no rotation for it at all. Simulations do not repeat an earlier build's results in the last bits, because a body's inverse inertia is now kept as the symmetric tensor it is.

Its flat sides are where the hull's are. The body is every point within the margin of the hull's core, which is the hull with each side moved in by the margin, so while two cores are apart the contact follows from their closest points, and only bodies deeper in each other than their margins take the expanding polytope algorithm. In a pile of hulls that is one overlapping pair in five, where it was all of them. A pointed corner ends up to a few margins short of where it is in the hull: the tip of an octahedron 0.015 units, the corner of a cube 0.015 as well, and an edge of a cube 0.008.

The search starts along it, and for most pairs that are apart, which two thirds of the pairs with overlapping bounds in a pile of hulls are, that one direction shows it.
  - `ConvexHull::support_point` looks at four corners at a time. For the benchmark's prisms with twelve corners that changes nothing, and with 32 corners a step takes 9% to 14% less than looking at one corner at a time.
- Physics bodies rotate. A body's shape now collides turned the way the body is, and contacts turn the body: a box dropped on an edge falls onto a side, a capsule lies down, and a static box that is turned is a slope. `Body::with_rotation(false)` turns this off for one body, which then is only ever moved by contacts and collides as its shape was made whatever its orientation, as every box and capsule did before. Use it for a character, so that its capsule stays upright when it is pushed and while an animation turns its transform. Bodies rotate unless told otherwise, so existing boxes and capsules start to tumble; add `with_rotation(false)` to keep them as they were.
  - Bodies that rotate and touch along a stretch or over a flat side get up to four contacts, at the corners of the patch they touch over, where they used to get one. Held at one point, a box rocks on it. Each contact starts from the impulse that the contact at the same corner needed in the last step.
  - A contact can have a negative depth, for a corner of a patch that has not reached the other body yet. The bodies may close that gap in the step and no more, so a box settles onto all four corners without one of them dropping out of the patch and coming back.

- BESL `if` and `match` can produce values, as in Rust, which replaces the `condition ? if_true : if_false` ternary added earlier in this release: `let shade: f32 = if (lit) { 1.0 } else if (rim) { 0.5 } else { 0.25 };`, or a `match` whose arms are values or blocks such as `1 | 2 => { let t: f32 = k * k; t * 0.5 }`. Baking turns the modules into one simulation kernel and one draw pipeline with their values as constants, so a system runs no code for modules it doesn't list; the asset stores a `ParticleSystem` resource plus `#simulate` and `#draw` pipelines and their generated shaders, and an invalid file fails to bake with a message naming the field. `ParticleSystemAssetHandler` is part of the default handlers, and `schemas/particles.schema.json` gives editors completion. Place a system with a `ParticleEmitter` and a `Transform` through the world; its `rate` and `burst` override the asset's, publishing it again on the same handle changes it, and deleting the handle stops it while particles in flight finish their lives. `setup_particles` installs the runtime after the scene pipeline, and the default graphics setup includes it. The engine ships `byte-engine/particles/sparks.particles`. Particles live and move entirely on the GPU: each frame the CPU uploads only spawn counts and spawning emitters' transforms, a one-thread pass per system sizes its simulation, one indirect dispatch spawns, moves, and packs the survivors into the other half of a ping-pong buffer, and one indirect draw per system and camera draws them, with the draw's vertex count doubling as the live count. Particles add their light to the scene color before post-processing and hide behind scene depth without writing it. Systems with no live particles record no work.
- `BoundRasterizationPipelineMode::draw_indirect` records a non-indexed draw whose vertex and instance counts the GPU reads from a `BufferHandle<[[u32; 4]; N]>` of `[vertex_count, instance_count, first_vertex, first_instance]` records. Use it when earlier GPU work decides how much to draw.
- Raster pipelines support premultiplied-alpha blending with `BlendMode::Premultiplied`, or `"blend": "premultiplied"` in a `.pipeline` attachment. An alpha of `0` adds the color, which suits emissive effects that don't need sorting.

- BELD's default bake memory budget is never less than a quarter of the installed memory. On macOS, sysinfo's available memory subtracts compressed pages and reads zero under memory pressure, which gave a 0 MiB budget that paused every independent bake while any other bake retained memory. A fresh bake of the model viewer assets on a 16 GiB Apple M4 under pressure took about 19.4 s with the 0 MiB budget and about 4.4 s with a real one.
- The offline GPU worker no longer blocks asset workers, and it keeps up to four material textures in flight at once. Asset bakes submit a request and await it, so a compio worker keeps baking other assets while the GPU filters and compresses a texture, and the worker overlaps one texture's upload and readback with other textures' dispatches on per-request pyramids. On an Apple M4, 32 mixed BC7, BC5, and RG8 textures submitted from eight threads bake in about 410 ms instead of about 700 ms. `MipGenerationBackend` and `CPUMipGenerationBackend` are replaced by the `MipGenerator` enum, whose `encode_mip_chain` is `async` and falls back to its CPU path; `process_image_in` is `async`, takes the image's `Semantic` and `Gamma` directly, and takes an optional `MipGenerator`, which replaces `process_image`, `process_image_with_mips_in`, and `ImageDescription`, and `IBLGenerator` awaits its GPU environment-map worker the same way. `Context::poll_synchronizer` is implemented on Vulkan and DX12, and mapping a Metal or Vulkan texture readback now waits only for the submission that recorded it instead of the whole context. Metal releases completed internal uploads without waiting whenever a detached recording starts or a synchronizer is polled, so offline contexts no longer retain every upload until a frame starts; the 32-texture batch holds about 240 MB resident instead of about 440 MB. The CPU BC5 encoder repacks RGBA levels into RG surfaces row by row, which takes a 2K normal map's chain from about 7.8 ms to about 5.5 ms in release builds, and the ignored `single_texture_phase_timing` test splits one 2K bake into its copy, upload, GPU, readback, and CPU-encode phases, for a noisy and a smooth image. The GPU BC7 encoder ranks partitions with weighted sums instead of masked adds, skips the alpha arithmetic of the ranking for opaque blocks, and fits indices by rounding the projection without checking neighboring palette entries; a 2K BC7 chain encodes in about 49 ms instead of about 90 ms with the same quality on every level, and the 32-texture release batch takes about 185 ms across eight threads instead of about 310 ms.
- glTF metallic-roughness textures that every material reads only through green and blue bake as two-channel `RG8` images, or `RG16` from sixteen-bit sources, with roughness in red and metallic in green; the generated materials read those channels. Filtering is per channel, so every mip level stores the same values as the four-channel image did. An image any material also reads through another channel, such as an occlusion-roughness-metallic texture, keeps all four channels. In the Sponza bake, the 20 metallic-roughness maps take 37.0 MB of storage instead of 50.7 MB and half the GPU memory. `Formats::RG16` is new, and `Semantic::MetallicRoughness` is the packed semantic; `Semantic::Metallic` and `Semantic::Roughness` still store every channel, which name-guessed standalone maps rely on. Rebake glTF models, because the stored images and their generated material shaders changed together.
- Material textures compress to BC7 on the GPU. `MaterialMipGenerator` filters the mip chain and then encodes every level, base level included, with a BESL kernel that uses the same search as the `fast` profile of `intel_tex_2`, reading the blocks straight into the stored payload. On an Apple M4, the full chain of a 1024 × 1024 albedo texture takes about 39 ms instead of about 610 ms on one CPU core, at slightly higher quality: 46.45 dB against 46.30 dB over 12 Sponza textures. A block stops its search at the first candidate that encodes it without error, which saves about 10% on sprites and other flat-colored art. The kernel compiles on the first BC7 texture, which takes about 115 ms in release builds. `MipGenerationBackend::generate_lower_levels` is replaced by `encode_mip_chain`, which writes the whole encoded chain into a buffer sized with the now-public `encoded_mip_chain_size`, from a base level in the now-public `filtering_format`. `CPUMipGenerationBackend` remains the fallback when no compatible GPU is available and now uses the `fast` BC7 profile instead of `basic`, which halves its encoding time for about 0.1 dB. Rebake textures with `beld bake --force`, because stored textures keep their previous BC7 data.
- MSL generation works out once per function which hidden resource and SIMD-lane parameters it needs, instead of again at every call site. Generating the BC7 kernel's MSL takes about 2 ms instead of about 64 ms in release builds, and about 27 ms instead of about 1 s in dev builds.
- Resource storage identifies payloads with rapidhash V3 instead of MD5. rapidhash V3 is non-cryptographic, and its output stays the same across crate versions and platforms. On an Apple M4, it hashes 65 to 77 GB/s in release builds, against 0.7 to 0.9 GB/s for MD5. Payload file names and the IDs of generated material shaders, `#shaders/<hash>`, come from this hash and change, so bake resources again.
- Resource storage checks whether a payload of 128 KiB or more is worth compressing before it runs LZ4 over all of it. It compresses four 16 KiB samples spread across the payload and stores the payload raw when they save less than 6.25%. BC7 textures, which rarely compress, skip the full pass, and RGBA8 textures stay compressed. In the Sponza bake, every payload keeps its previous encoding.
- glTF and FBX meshes are processed while their materials and textures bake, instead of after them. `MeshPrimitiveSource::material` is replaced by `material_slot`, which returns an index into a material list the importer resolves separately. Pass the resolved materials, in slot order, to `MeshProcessorSession::finish`, `finish_into`, or `finish_into_resource`. The stored mesh still lists each distinct variant once, in first-use order.
- BESL functions take arrays of any fixed size as parameters, passed by value. MSL declares local, parameter, and constructed arrays as `metal::array`, and HLSL declares them in C position and initializes them from braces. A function that returns an array of more than four elements, or of non-scalar elements, now fails to link, because HLSL can't return arrays; return a vector or struct instead. HLSL generation rejects a larger array constructor outside a `let` or constant initializer. The VM indexes vector components with a runtime index, as in `words[i]`, and MSL casts the arguments of the unsigned `min`, `max`, and `clamp` overloads, which Metal rejected as ambiguous with literal arguments.
- `Creator::publish` takes the entity's `Handle` and returns nothing. Allocate the handle first and pass it in, as in `creator.publish(handle, value)`, instead of passing `Option<Handle>` and reading the returned handle.
- Input triggers are described by their default value only. `TriggerDescription::new` takes just `default`; the `rest`, `min`, and `max` values, and `Axis2::min_value`, `Axis2::max_value`, `Axis3::min_value`, and `Axis3::max_value` that fed them, are removed. `Function::Boolean` and `Function::Threshold` are removed because they mapped values like `Function::Linear`; use `Function::Linear`.
- The single-implementation traits `TriggerRegistry`, `AudioSystem`, and `Inspector` are removed. Call their methods directly on `InputCollector`, `DefaultAudioSystem`, and `DefaultInspector`, and take `EntityHandle<DefaultInspector>` where you took `EntityHandle<dyn Inspector>`. `register_mouse_device_class`, `register_keyboard_device_class`, and `register_gamepad_device_class` take `&mut InputCollector`.
- `DefaultInspector::post_message` takes the payload as JSON text (`&str`) instead of a parsed JSON value.
- `simple_compute::Pipeline::bind` no longer takes a `RenderPassBuilder` and returns the `Pass` directly instead of a `Result`.
- `utils::InlineCopyFn` names its argument and output types directly: write `InlineCopyFn<Input, Output>` instead of `InlineCopyFn<fn(Input) -> Output>`. `RefCall1`, `RefCall2`, and `RefCall3` are removed.
- Unused engine APIs are removed: the audio `Synthesizer`, `Source`, `Sound`, `Emitter`, and `RoundRobin`; the physics `World` and `Collider` traits, `Intersection`, and `Shapes::ConvexHull`; the gameplay `AnchorSystem`, `Sphere`, `Cube`, `KillMessage`, and timer; the core `Task` and `EntityContainer`; `WeakHandle` and `Handle::weak`; and `utils::StaleHashMap`, `utils::partition`, `SendBoxedFuture`, and `SendSyncBoxedFuture`.
- `utils::RangeAllocator` tracks free ranges for the animation pool, the audio sample pool, and upload staging. As a result, `AnimationPool` merges freed clip regions with their free neighbours again; before, an exact-fit allocation could reorder its free list so later frees stayed fragmented and large clips were evicted or rejected while enough memory was free.
- BESL resolves a bare name only to declarations in scope. Before, a name such as `x` could silently bind to a field of any struct in the program, such as a built-in vector's `x`, to a member of a buffer descriptor or push constant, or to another function's parameter or local, so an undeclared name linked instead of failing. It now fails with `LexError::AccessingUndeclaredMember`; reach a field through its value or resource, as in `light.intensity` or `push_constant.index`. `NodeReference::get_main` returns only a function named `main`, never a struct member or local with that name.
- BESL supports Rust-style `match` statements over `bool`, `u8`, `u16`, `u32`, and `i32` values, with literal, `_`, and `|` patterns. As in Rust, the first matching arm runs, a match must cover every value, and `break` and `continue` in an arm act on the enclosing loop. GLSL, HLSL, and MSL lower it to a `switch`, and the VM runs it with a new `Switch` instruction. `besl::Nodes::Match` holds the checked match with distinct case labels and a default arm. `Nodes::conditional_children` is now `Nodes::branch_children` and also walks match arms. Comparison and logical operators now infer as `bool`.
- BESL supports `else` and `else if` branches on every backend and in the VM. Variables declared inside a branch are only visible in that branch. `besl::parser::Node::conditional` and `besl::Node::conditional` take the else branch as a third argument, and `Nodes::Conditional` gains an `else_branch` field: `None` for an `if` without `else`, `ElseBranch::Block` for an `else` block, or `ElseBranch::If` for an `else if` link.
- Scene color is stored as packed R11G11B10 floats instead of RGBA16F, halving the bandwidth of the lit target and of every HDR pass that follows it. The atmosphere sky, bloom and its mip chain, the lens flare targets, and the sky's transmittance, multiple-scattering, and sky-view LUTs use the same format. Tone mapping, color grading, and sRGB display encoding write RGBA16F, because the packed format's 6 bit mantissa bands display-referred values; the UI layer stays RGBA16F for its coverage. The atmosphere sky is now a scene background instead of a post-scene pass: scene pipelines draw it after opaque surfaces and before transparent ones, so transparent surfaces blend over the sky and scene color needs no alpha. `setup_atmosphere_sky_render_pass` installs it the same way, `render.pass.atmosphere sky` still enables or bypasses it, and bypassing it leaves the background black. `Renderer::set_scene_background_for_all_sinks` registers a scene background, and scene pipelines create it with `RenderPassBuilder::create_scene_background`. `AtmosphereSkyRenderPass::new` takes the scene's `SceneBackgroundTargets`, and the `Atmosphere Sky Output` target is gone; the sky writes the scene's `Lit` target. `Formats::RGBu11u11u10` reports a floating-point encoding, pipelines accept the `rg11b10_float` attachment format, and the HTTP inspector captures the format as PNG or EXR. Shaders that read scene color through storage images declare them without a format, and the Vulkan backend now requires `shaderStorageImageReadWithoutFormat`. Rebake materials, because the generated material-evaluation shaders changed.
- Directional shadow cascades shrink on the GPU to the surfaces the camera sees in each slice, so the sky, the space in front of the nearest surface, and whatever lies behind a wall take no texels. After the opaque visibility layer, a compute pass reads the camera's depth and records the box each cascade's surfaces fill, and a one-workgroup pass shrinks each cascade from its frustum fit to that box, with the same 17-texel margin, eighth-octave size steps, and world-fixed texel grid. A cascade never grows past its frustum fit, grows at once when its surfaces need it, and shrinks only once they fit two size steps smaller, so surfaces hovering at a step do not switch its size every frame. A cascade without surfaces keeps its frustum fit. The shadow maps are now drawn right after the fit, where the GPU can run the screen-space passes alongside them; in `third_person` the GPU's busy time per frame stayed within run-to-run noise of the previous path. A surface outside its cascade's square, such as a transparent one the fit did not see, moves to the first coarser cascade that holds it and is lit when none does. `CascadeFitting::Frustum` keeps the previous behavior, with the shadow maps drawn first; pass it with `VisibilityPipelineSettings::with_cascade_fitting`, or set the `render.directional-shadows.fitting` parameter to `frustum`. Only the first sink fits the cascades, because they are made for its camera. Rebake materials, because the generated material-evaluation shaders changed.
- Each directional shadow cascade covers the smallest square, in the light's view, that holds its slice of the camera's view, instead of a sphere around the slice, so its texels cover less of the scene: 10 to 30% less wide, depending on the sun's angle. The square keeps a margin of 17 texels for the widest filter, and its size is rounded up to eighth-octave steps, so turning the camera changes texel size only when the slice outgrows a step. Cascades now also lie on a texel grid fixed in the world; before, the grid followed the camera, so moving it moved shadow edges across texels.
- Directional shadow cascades are 4096 × 4096 texels instead of 2048 × 2048, so their texels are half as wide, and store 16-bit depth instead of 32-bit, so the four cascades take 128 MB instead of 256 MB at the new size. Each cascade's view reaches a fixed 100 meters toward the light past its bounding sphere, instead of the camera's far plane, so a longer view distance no longer coarsens stored depth; a depth step stays under a centimeter in every cascade. The receiver's depth margin is set in 16-bit steps. The cascade depth pyramid holds one maximum per 8 × 8 texels instead of 4 × 4, so the occluder search still covers the same distance in meters. Rebake materials, because the generated material-evaluation shaders changed.
- Directional shadow cascades divide their range 80% logarithmically instead of 95%, so a camera about five meters from a character keeps its shadow in a finer cascade: with a 75° field of view, texels between 5.5 and 12.5 meters shrink from about 2.3 to 1.4 centimeters. `CascadeSplits` sets how far directional shadows reach, 100 meters by default, and the split blend; pass it with `VisibilityPipelineSettings::with_cascade_splits`, or set the `render.directional-shadows.distance` and `render.directional-shadows.split-blend` parameters. Surfaces past the shadow distance receive no sun shadow. `csm::make_csm_views` takes the splits as a new argument.
- Contact shadows are soft and filtered. The trace fades an occluder's shadow out over the second half of the ray's reach and near its thickness limit, instead of stopping at a hard line, and a new depth-aware 5×5 filter pass smooths the trace's dithered result into the `Contact Shadows` target material evaluation reads, without crossing onto other surfaces. The unfiltered result is the `Contact Shadow Trace` target.
- Directional shadows are percentage-closer soft shadows: penumbrae widen with the distance between an occluder and the surface it shades, and stay sharp where they touch. `DirectionalLight::angular_radius` sets how fast they widen; it defaults to the sun's `DirectionalLight::SUN_ANGULAR_RADIUS`, about 0.27°, and `DirectionalLight::with_angular_radius` sets a larger disk for softer shadows. Each receiver searches a cascade's max-depth pyramid for nearby occluders, then filters with the same noise-free tent as before, with its taps spaced one, two, or four texels apart and blended between spacings. A larger light searches a coarser cascade, so the search covers occluders up to two meters above the receiver, and a penumbra wider than eight texels of the receiver's cascade is filtered in a coarser cascade that holds it, fading between the two so no seam shows. `AtmosphereSkyRenderPassSettings::sun_angular_radius` is removed: the sky draws its sun disk at the light's angular radius. Rebake materials, because the generated material-evaluation shaders changed.
- Directional and cone shadows have smooth, noise-free soft edges that stay still from frame to frame. They filter the shadow map with a tent that is two texels wide on each side of the receiver, over the 4×4 texels it covers, instead of 8 point samples with a random rotation per pixel. That rotation changed every frame the camera moved, which made penumbrae boil. Point shadows keep their 8-sample kernel, but its rotation now depends on the shadow-map texel the surface falls in, so it no longer changes as the camera moves. Rebake materials, because the generated material-evaluation shaders changed.
- The PBR visibility pipeline buckets lights on the GPU. A compute pass splits each sink's view into 16 × 8 × 24 clusters, with depth slices that grow exponentially, and marks which lights reach each one; material evaluation then shades a pixel with only its cluster's lights. A point or cone light reaches as far as its exposed illuminance stays above 1/1024 lux, so lights keep their inverse-square falloff without a visible edge. The light table grows from 16 to 1,024 lights and is now a storage buffer. The cone and point shadow pools keep their limit of 16 maps each, and shadow selection ranks each light once per sink instead of once per pool slot. Rebake materials, because the generated material-evaluation shaders changed.
- BESL gains `find_lsb(u32) -> u32`, which returns the index of the lowest set bit, or `0xFFFFFFFF` for zero, on every backend and in the VM, and a scalar `log2(f32) -> f32` overload.
- The HTTP inspector captures render targets at full precision and several at a time. `GET /screenshots` takes `format=exr` for a lossless OpenEXR image that keeps HDR values, such as half-float lighting buffers, or `format=raw` for the texture bytes as the GPU stores them; PNG stays the default. Every image response reports the texture's format and size in `X-Byte-Engine-Format`, `X-Byte-Engine-Width`, and `X-Byte-Engine-Height`, and raw responses add `X-Byte-Engine-Bytes-Per-Row`. `previous=true` reads the copy of a history target, such as `Diffuse Radiance History`, that the previous frame wrote, which is what the current frame's passes read as history. `POST /screenshots` takes a JSON list of up to 16 captures from any sinks and capture points, reads them all from the same frame, and returns one `multipart/form-data` part per image. `Inspector::request_screenshot` is replaced by `Inspector::request_screenshots`, which takes a list of `ScreenshotSelection` values and answers with unencoded `Screenshots`; transports encode each readback with `ScreenshotFormat::encode`, so encoding no longer runs on the graphics thread. GHI gains `CommandBufferRecording::transfer_texture_with_frame`, which reads another frame's copy of a per-frame image.
- The bloom pass is a real HDR bloom: a 13-tap prefilter and downsample after Jimenez, with a luma-weighted first level so a single bright texel cannot flicker the glow, a tent-filtered upsample as wide as `BloomPassSettings::radius`, and a composite that adds the glow onto the scene. `BloomPassSettings::max_brightness` holds each texel to a ceiling before it glows, six stops above display white by default, so a sun reflection at the half-float limit stays a highlight instead of flooding the frame. Overflowed scene texels can no longer smear into black: the prefilter reads texels unfiltered and clamps them, the composite stays within the half-float range, and the ACES tone mapper maps an infinite input to white. Install it with `setup_bloom_render_pass` after the passes that write scene light and before tone mapping.
- The atmosphere sky includes multiple scattering, following Hillaire's 2020 approximation: a 32×32 LUT, built once with the transmittance LUT, holds the light from every scattering order after the first, including sunlight the ground reflects back up. The sky is up to about twice as bright near the horizon and bluer overhead. `AtmosphereSkyRenderPassSettings::ground_albedo` sets the ground's reflectance and defaults to 0.3.
- The atmosphere sky takes its brightness and color from the newest `DirectionalLight` instead of a fixed intensity, so the sky and sunlit surfaces share units and one camera exposure fits both. The sun disk's radiance is the light's illuminance over the disk's solid angle, capped to stay finite in half-float targets. `AtmosphereSkyRenderPassSettings::sun_intensity` is removed, and without a directional light the sky is black.
- Cameras have an exposure, set in stops with `Camera::with_exposure` or `Camera::set_exposure`. Each stop halves or doubles the light the camera shows, and `0.0` keeps today's output; a photographic EV100 converts to `-(EV100 + log2(1.2))` stops. The PBR visibility pipeline and the atmosphere sky multiply scene light by it as they write it (pre-exposure), so real-world intensities, such as a 100,000 lux sun on a glossy surface, stay within the half-float scene image, and bloom and tone mapping receive exposed light. `Sink::exposure_scale` carries the linear factor to render passes.
- `Environment::with_illuminance` calibrates an environment map to the lux it delivers to an upward-facing surface, so it lights the scene in the same units as analytic lights. The loader measures each map's upward illuminance from its baked diffuse irradiance; without a calibration, the map's own values are used.
- Loading a mesh no longer solves its materials. A `Mesh` stores each distinct material variant once in `Mesh::materials`, and `Primitive::material` is an index into it (`Mesh::material` returns a primitive's variant). Request a variant by its ID when you need it; the visibility renderer already does, so a mesh load drops from a storage read per primitive for its variant, material, shader, and every image to reads of the mesh and its skeleton only. `PrimitiveModel`, `SubMesh`, and `SubMeshModel` are removed; `Primitive` is both stored and loaded.
- `ResourceManager::request` and `ResourceManager::query` read each requested resource once. Implement the new `StoredModel` trait to make a model requestable; it builds the reference from the record storage already returned, and `Reference::from_stored` takes the resource's ID, hash, size, and streams from that record. `ReferenceModel` solves through `StoredModel`, and the request bounds are now `T::Model: StoredModel<Resource = T>`.
- Material, variant, and flipbook solves read their shaders, parameters, variables, and images concurrently. Packed resource stores map only the pages that hold a payload instead of the whole packed file for every read, and resources without a payload, such as materials and variants, no longer open a file.
- Baking commits each resource without waiting for the disk and makes a whole root bake durable with one flush when it finishes, instead of one full flush per stored resource. `WriteStorageBackend::persist` is the new hook that makes committed resources durable; a crash before it runs rolls the resource database back to the last persisted bake.
- glTF and FBX textures bake as their own image fragments through the dependency pool, once per container, instead of inline and once per material. They decode, generate mips, and compress in parallel, and an image fragment requested directly now bakes exactly like one requested by a material: same semantic, and mips when a material mip generator is installed. FBX gains `images/<index>` fragments, and a glTF image fragment reads only its own buffer view.
- Generated glTF and FBX materials that lower to the same BRDF graph share one compiled shader, stored as `<container>#shaders/<hash>`. Material texture variables are named by slot (`material_texture_0`, …) instead of by source image index, and unique shaders compile concurrently. On macOS, each shader compiles and links in one `metal` invocation instead of separate `metal` and `metallib` runs.
- `AssetManager::rebuild_resources_baked_before` makes every resource stored before a given time stale, so the next bakes rebuild each root and each shared dependency exactly once. `beld bake --force` uses it with the time the command starts, so forced glTF and FBX bakes also recompress their embedded textures. Stored resources record when they were baked.
- `beld bake` skips assets whose stored resource is current with its source files, so repeated bakes only process what changed. `beld bake --force` rebakes everything selected, which is needed after an asset processor or `--texture-compression` changes. `AssetManager::bake_if_stale` exposes the same check to library callers, and `beld::bake` takes a `force` argument.
- UI components no longer share the engine's state. Every write a component makes, such as declaring an element, an `update_*` call, `remove`, `reparent`, `adopt`, focus requests, and starting a `component` or `mount`, is a future that writes straight into the engine when awaited, in the order it was awaited; the next layout and the components polled after it see the change. An edit of a removed element or a reparent cycle is logged and changes nothing. Reads are futures that complete at once: `Context::geometry`, `Context::pointer`, and `Context::drag` are awaited, and `Context::ctx` is replaced by `ctx.with(|app| ...).await`. The host reads and changes the application context with `Engine::ctx` and `Engine::ctx_mut`. UI wait futures such as `RenderFuture` and `WaitFuture` take the engine's context type, and the free `ui::wait` and `ui::seconds` functions are replaced by `Context::wait` and `Context::seconds`.
- UI elements are declared and edited with setup functions that set their properties in place, such as `ctx.element("panel").container(|c| c.width(240.into()).clip(false)).await` and `panel.update_container(|c| c.opacity(0.5)).await`. Each setter writes into the element where the engine stores it. The element builders, such as `Container::default().width(..)` and `Text::new(..)`, and the `set_*` methods are removed; a plain function over `Properties` holds a reusable look for declarations and edits alike. Text is formatted straight into the element from any `Display` value, such as a number or `format_args!`, image pixels are copied from any byte slice, and `style` takes any layers, such as an array. The engine keeps the storage of removed elements, dropped render entries, and ended components and reuses it, so a screen that closes and opens again allocates only its component tasks.
- UI components are async closures or async functions: `Engine::mount`, `ElementContext::component`, and `ElementContext::mount` take an `AsyncFnOnce(&mut EvaluationContext<C>)` instead of a closure returning a boxed future, and `UiFuture` and `MountedUiFuture` are removed. `animate` takes an `AsyncFnMut`, so one frame can edit several elements.
- UI element keys are explicit. `Context::element` takes an `ElementKey`, made from a name or a `(name, index)` pair, and an element's id is a 64-bit hash of its parent's path and its key, so the same key under the same parent always has the same id. Siblings declared from one list need distinct keys, such as `("row", index)`; declaring one key twice under the same parent in one frame is logged and ignored. The implicit per-frame numbering of repeated names is removed, and `ui::Id` is now a `NonZeroU64`.
- Reworked input around two classes: every source event is recorded into an `InputCollector`, and each consumer owns an `InputSink` that declares its actions, pulls them once per tick, and answers `Capture::Captured` to keep the source event from later sinks. `InputEvents`, `ActionProcessor`, and `InputManager` are replaced; `GraphicsApplication::input_system` is replaced by `GraphicsApplication::input`, and manual action queuing is removed in favor of publishing `ActionEvent` values directly.
- A value driven by a record is no longer repeated a second time in the same tick by `TickPolicy::WhileActive` or `TickPolicy::Always`.
- Retained control values live in a dense per-seat, device, and trigger table instead of a hash map, each sink keeps a sorted control-to-action index so a record only visits the actions bound to it, and binding gates are classified when resolved. `InputCollector::has_trigger` is replaced by `InputCollector::trigger`, which returns the handle for recording without a name lookup, and the public `TriggerMapping` alias is removed.
- `InputCollector::end_tick` is removed. Each sink reads from its own position in the queue, and a record is retained and dropped once every sink has pulled past it.
- `process_default_window_input` records into the collector itself and discards the seat on focus loss, minimize, close, and resize, returning whether it did.
- The UI `Engine` owns the pointer drag: `Engine::press`, `Engine::drag_to`, `Engine::release`, and `Engine::drag` replace the standalone `Drag` type, components read the held source through `Context::drag`, and `Engine::cancel` ends the interaction in progress. A changed viewport size cancels from `Engine::evaluate`.
- The UI engine hit-tests pointer gestures itself: `Engine::press`, `Engine::drag_to`, and `Engine::release` take normalized window coordinates, `press` grabs the surface under the pointer from the last evaluated frame, and `Engine::hit` answers what is under a point. `HitTest` is no longer needed to drive a drag.
- The UI engine delivers drag gestures to components as events: the grabbed surface gets `Events::Grabbed` on press, `Events::Dragged` once per evaluation with the offset from the press point in `UiEvent::delta`, and `Events::DragEnded` when the grab ends with the surface it was dropped on in `UiEvent::source`. `Events::Dropped` reaches the surface under the release point and its ancestors with the released source in `UiEvent::source`, before the source's `DragEnded`. `UiEvent` gains that `source` field.
- `EvaluationContext::reparent` moves a retained UI element under another parent as its last child, keeping its id and properties, and `EvaluationContext::adopt` moves another element under this one.
- UI depth is local to each container. `Depth::relative` orders a child among its siblings only, and a container paints and hit-tests as one block with everything inside it, so no depth set inside one component can put its elements over another's. `Depth::absolute` layers leave their parent and sit above all ordinary content wherever they are declared, from the lowest value to the highest, in tree order among equals, and above the layer they were declared in. Depth used to be one number added up along the tree, so a deep or raised element could show through a modal mounted earlier in the tree, and its backdrop blur skipped it. A layout element's depth is now its rank in that paint order.
- `Container::absolute_position` is now an offset from the parent's top-left corner rather than the viewport's, so nested widgets keep their internal placement wherever their parent's flow puts them. Containers with `Depth::absolute` still start from the viewport.
- Components spawned inside a mounted UI scope end when that scope is removed, and finished components release their runtime slot. Previously both stayed in the runtime, and components waiting on frames kept running after their elements were gone.
- `Context::element` accepts an owned `String` or `format_args!`, so elements created from runtime data can be named from that data; the slot is keyed by the text's content, and `format_args!` is hashed without allocating.
- `EvaluationContext::remove` removes one UI element with everything declared under it, including the components started there. Declaring the same key again reuses its id.
- `EvaluationContext::update_curve` edits a retained curve in place. `Properties::clear_segments` and the segment setters, such as `line` and `cubic`, re-route it while reusing its segment storage, and changing only the segments repaints without replaying layout.
- A container's `Transform` scale now reaches the curves and text under it: segment points, stroke widths, and font sizes scale with the inherited transform the way rectangles, hit bounds, and clipping already did.
- The UI engine reports the pointer passing over surfaces: `Events::PointerEntered` and `Events::PointerExited` reach the surface under the pointer and the ancestors that started or stopped containing it, a held drag source is skipped, `DragCapture::over` names the surface beneath a dragged item, and `Engine::hovered` answers at the application level.
- `hit_width(width)` in a curve's setup makes it a pointer target within `width` layout units of its stroke, so wires can be hovered, clicked, and dropped on. `HitTest` retains the same polylines.
- Absolutely positioned containers keep negative layout coordinates instead of being snapped to the viewport's edge; visual transforms preserve them as well.
- `Context::remove` is available to components, so a component can remove its own elements and end itself.
- GHI windows are pumped by one `ghi::window::App` per process instead of per window, matching how Win32, AppKit, and Wayland deliver events. Create windows with `App::create_window` and drain `App::poll`, which yields `ghi::window::Event`: either an application event such as `AppEvents::Quit`, or a window `Events` value tagged with the `WindowId` it targets. Input targets the window with focus. `Window::new`, `Window::poll`, and `Renderer::update_windows` are removed; `Renderer::poll_windows` replaces the latter, and the graphics application publishes `ghi::window::Event` instead of `ghi::window::Events`.
- Multiple GHI windows no longer steal each other's events on macOS, Win32 reports `WM_QUIT` and keeps handling messages sent between polls, and every Wayland window shares one compositor connection. The macOS dock's Quit item now asks the application to close instead of ending the process.
- The `render-on-demand` application parameter renders a frame only when something changed. Window changes, new UI renders, and screenshot requests ask for frames; call `Renderer::request_redraw` after changing the scene. Idle ticks keep handling events at the `max-frame-rate` pace. Render passes report pending output through the new `RenderPass::needs_frame`, which defaults to `false`.
- A UI `update_*` call that writes the values an element already has no longer advances the render revision, so unchanged frames reuse the retained render and on-demand rendering stays idle.
- Ticks that present nothing, such as idle on-demand ticks, now run at the refresh rate of the fastest display showing a window instead of a fixed 60 per second, or at the `max-frame-rate` pace when that is slower. GHI windows report their display's refresh rate through `Window::refresh_interval` and the new `Events::DisplayChanged` event on macOS, Win32, and Wayland, and `Renderer::refresh_interval` returns the fastest one.
- An idle `render-on-demand` application now waits in the window system instead of ticking. It keeps ticking while a frame is being shown, and wakes for window events, inspector requests, and anything that wakes its `LoopWaker`. After a wait, `Time::delta` is capped at one frame while `Time::elapsed` includes the wait.
- Systems the application loop drives report when they next need a tick, wired explicitly: `GraphicsApplication::waker` hands out a `LoopWaker` (which converts into a `std::task::Waker`), and `GraphicsApplication::schedule_tick` takes the instant of the next tick they need. A UI engine answers both with `Engine::set_waker` and `Engine::next_tick`, so animations keep running at the display rate and UI timers fire on time.
- `ghi::window::App::poll` and `Renderer::poll_windows` take a `Wait` that lets them wait for the first event, and `App::waker` returns an `AppWaker` that ends such a wait from any thread.
- Simulation can step at its own rate: `GraphicsApplication::tick_stepped_with` takes a `simulate` callback, run zero or more times per tick with a fixed step from the new `simulation-rate` parameter (default 60), and a `frame` callback run once with the display-derived time. The world and physics advance with the steps. A frame that falls more than eight steps behind drops the outstanding time. `tick_with` keeps simulating once per frame and panics when `simulation-rate` disagrees with the rate frames are presented at.
- Frames show the world interpolated between the two most recent simulation steps, one step behind. `PipelineManager::step` marks the end of a step, transforms read in it are that step's sample, and `PipelineManager::prepare` receives `alpha`, how far the frame lies between the two latest steps. The visibility pipeline moves each renderable between its samples and holds transforms written outside a step where they are; `Transform::interpolate` blends two transforms.
- `.flipbook` assets declare `frames_per_second` and the ordered `images` of a sequence. The standard setup bakes them together with their images into a `Flipbook` resource that owns its solved image references.
- `PipelineManager::prepare` receives `time`, the frame clock's elapsed time, after `alpha`, so managers can drive playback such as flipbooks at the display rate instead of the simulation rate.
- UI text is drawn from glyph outlines on the GPU with the Slug algorithm, following Eric Lengyel's reference shaders. Glyph curves and bands are packed once per glyph into two storage buffers and the fragment shader computes each pixel's coverage, so text stays sharp at any size and a zoom, a resize, or an animated font size rasterizes and uploads nothing. Horizontal glyph positions are fractional and baselines snap to whole pixels. The CPU glyph atlas renderer is kept; set `UI_TEXT_MODE` in `ui/render_pass.rs` to `UiTextMode::Atlas` to use it.
- The UI is drawn by one ubershader without vertex or index buffers. Every rectangle layer, glyph, image, backdrop blur, and curve piece is one 80-byte record in a storage buffer that the vertex shader pulls quads from, so a frame is one draw per damaged region plus one per backdrop blur, instead of one per depth level, curve, and image with a pipeline and buffer rebind each. The eleven per-type raster shaders and six pipelines are replaced by `ui-vertex.besl`, `ui-fragment.besl`, and two pipelines. Clips and feather masks are shared through a table instead of being repeated in every vertex, a square fill skips the corner, stroke, and mask math, circular corners skip the superellipse math, and images and the glyph atlas share one texture array that holds 31 images at once. The damage clear runs in the first draw's pass, and damage covering the viewport uses the attachment's clear.
- UI elements of different types now paint in exact depth and element order. Previously each type was batched per depth level, so a rectangle could paint under an earlier text or curve of the same depth. A backdrop blur paints under its own element's layers.
- UI curves are evaluated analytically on the GPU instead of being flattened, clipped, and cached on the CPU. Each segment is drawn in a few pieces, each the exact distance to a quadratic, so lines and quadratics are exact and cubics stay within 0.05 pixels. Strokes have no seams between pieces, and path ends and corners are round instead of butt ended.
- A backdrop blur now respects the rounded corners of a feather mask, as every other UI primitive already did.
- UI text measurement reads size-independent advances from glyph outlines instead of rasterizing every measured glyph, and line metrics scale from one entry instead of being cached per size.
- BESL descriptor arrays (`count:`) are indexable everywhere, not only inside `sample`: `texture_lod`, `texture_size`, `fetch`, and the downsample intrinsics accept `textures[i]` with any index expression, and MSL and HLSL pair the element with the sampler at the same index. They used to lower to a member access that no backend compiler accepts. GLSL marks every descriptor-array index `nonuniformEXT`.
- BESL has a `break` statement that leaves the innermost `for` loop. It lowers to GLSL, HLSL, and MSL, runs in the BESL VM, and ends its block for the optimizer like `continue` does.
- `ghi::BufferDescriptor` converts from a `BaseBufferHandle`, for binding a buffer whose element type was chosen at runtime.
- Fixed release and bench builds of `byte-engine-resource-management`: a stray `#[cfg(debug_assertions)]` removed `LoadMessages` from builds without debug assertions.
