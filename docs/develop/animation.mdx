Read this note before you change animation playback: the animation system, its
animators, the graph runtime, or the clip pool. Its behavior is specified in the
[animation reference](/docs/reference/animation). This note explains how the
system is built and why, states the rules a change must keep, and names the
tests and benchmarks that guard them. The code lives in
`crates/byte-engine/src/animation`.

## Where the code is today

The animation system is being built to replace the standalone graph player.
Until it lands, `AnimationGraphPlayer` in `animation/graph/runtime/player.rs`
plays one character per call and differs from this design in four ways:

- `advance` decides routes and samples poses in one pass. `hand_over` and
  `begin_handover_blend` sample in the middle of a tick, as soon as a route is
  chosen.
- Each player keeps about 15 pose buffers the size of its skeleton, most of
  them scratch space that only `advance` reads.
- Entering a state allocates. `RuntimeMotion::new` builds the state's samples,
  a pose map for every clip, and its weights, for every player that enters it.
- Every call takes the clip pool mutably, because requests, prefetches, and
  `acquire` pins go through it, so two players can't advance at once.

Move the code toward the design below; don't extend the player's API.

## What animators share

Many characters play one graph, so everything that doesn't depend on one
character's playback is shared:

| Shared data | Held once per | Holds |
| --- | --- | --- |
| Graph | Graph | States, routes, and clip resource IDs. Animators refer to it, never copy it. |
| Graph binding | Graph and canonical skeleton | For every clip of the graph: its pose map onto the canonical skeleton, its duration, and its frame rate. It's built once, when the canonical skeleton is resident, and animators refer to clips by their index in it. |
| Clip pool | System | Packed clips in one arena. |
| Lane scratch | Lane | The pose buffers that only evaluation reads: the blend samples, one clip's poses at the start and end of a step, the loop seam poses, and the global matrices before they're posted. |

An animator keeps only what must survive from one step to the next: its
playback, which holds the playing and destination states, their clip indices,
their weights, and their phases; its pending route; its remembered blend
positions; the last step's delta; the posted local pose and the one before it;
its inertializer; the destination poses while a transition runs; and the look
chain's eased angles. Weights fit a fixed array of three, the most clips a
motion samples. None of this grows after the animator is adopted.

## How a step runs

A step runs in four phases. Only the evaluate phase runs on several lanes.

| Phase | Runs | Does |
| --- | --- | --- |
| Intake | Serially | Adopts and removes animators, applies the latest requests and look targets, and admits loaded clips into the pool. |
| Resolve | Serially | Decides each animator's routes, phases, and hand-overs for the step, and writes them as a plan. Requests and prefetches clips, and pins every clip a plan samples. |
| Evaluate | On the alley's lanes | Carries out each plan: samples clips through the graph binding, blends, inertializes, extracts root motion, applies the look chain, builds the global pose, and posts both updates. |
| Release | Serially | Unpins the clips. |

A plan is small and fixed in size. It holds at most two segments, one before a
hand-over and one after it, because the time left in a step after a hand-over
plays on the next state. Each segment lists the motions to sample, with their
clip indices, weights, and the phase each starts and ends at, and the events
that start the segment, such as a transition and its duration, or an
inertializer seeded from the posted pose.

### Why resolve never reads a pose

Every decision that resolve makes depends on time, the graph, and clip
durations and frame rates: when a wait point is reached, how much of the step
is left after a hand-over, which route a request takes. None of it depends on
pose values. The work that does, such as seeding an inertializer from the pose
on screen and its velocity, is an event in the plan, and evaluation carries it
out.

The split keeps the pool's mutable access in one short serial pass. Evaluation
then reads the pool, the graph, and the binding through shared references and
writes only its own animator and its lane's scratch, so lanes need no locks and
an animator's result can't depend on which lane ran it.

### Why scratch lives on lanes

Scratch pose buffers are only live while one animator is evaluated, so a
character crowd needs one set for each lane instead of one for each character.
That's most of the 15 buffers a player keeps today. Keeping them on the lane
also keeps them warm in that core's cache from one animator to the next.

### Evaluation order

Resolve orders the evaluation work by the first clip each plan samples, so a
lane samples characters that play the same clip back to back while the clip's
keys are in cache. The order is only a performance choice: results never depend
on it.

## Rules a change must keep

1. Resolve never reads or writes a pose. Evaluation never takes the pool, the
   graph, or the binding mutably, and never reads another animator.
2. An animator's pose, root motion, and state depend only on its own requests,
   look targets, and the step deltas. They don't depend on the lane count, the
   evaluation order, or the other animators.
3. Every clip a plan samples stays pinned from resolve until the step's updates
   are posted.
4. Nothing allocates in a step for an animator that's already adopted, except
   the matrices a pose update owns. Plans, scratch, and animator state are
   retained.
5. Every update of a step is posted before the step returns, so code that reads
   after the step in the same frame sees the root motion of the pose it's about
   to draw.
6. A graph is bound once for each canonical skeleton. Adopting another animator
   of a bound graph resolves no pose maps.
7. The look chain runs after root motion is extracted and never changes it.

## Tests and benchmarks

The playback tests in `animation/graph/runtime/player.rs` guard the routing,
phase, hand-over, redirect, and root motion rules of the reference. Keep them
passing as the code moves into the system; move them, don't drop them.

| Guard | Rules |
| --- | --- |
| Playback tests in `animation/graph/runtime/player.rs` | 1, 7 |
| `pool_evicts_lru_entries_and_evaluation_leases_pin_arena_regions` | 3 |
| `characters_root_motion` and `characters_transitioning` benchmarks | 4, 6 |
| `active_pose`, `active_root_motion`, and `inertialized_transition` benchmarks | The cost of one animator by skeleton size |

Rules 2 and 5 have no guard until the system lands. Add these tests with it:
animators that share a graph post what each would post alone, a step posts the
same updates on any lane count, and root motion arrives in the step of its
pose.

The `characters_*` benchmarks time one frame of 1, 64, and 1,024 characters
with 64-node skeletons that share one graph and clip pool. The root motion case
plays one looping clip; the transitioning case keeps every character inside an
inertialized transition, the most expensive path. Each character starts at its
own phase, so characters don't sample in lockstep.

Run the tests, then the benchmarks before and after your change:

```bash
cargo nextest run -p byte-engine -E 'test(/animation/)'
cargo bench -p byte-engine --bench animation_graph
```

Compare builds run by run: keep each build's benchmark binary and run them in
turns, because other load on the machine shifts results from one run to the
next.
