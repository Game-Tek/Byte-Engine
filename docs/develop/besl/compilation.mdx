Read this page before you change the BESL parser, linker, optimizer,
reflection, a backend generator, or the VM. Byte Engine turns authored BESL
into a linked semantic graph before it generates platform shader source or
executes the program in the VM. The language itself is specified in the
[BESL reference](/docs/reference/besl).

## Follow the compilation path

1. `parse` tokenizes the source and builds a syntax tree.
2. [Module files](#link-modules) are parsed and attached to it.
3. An optional `ProgramTransform` adapts that tree to the renderer, such as by
   adding the helpers its shaders share. Material programs start here instead:
   a renderer's `ProgramGenerator` builds their whole tree, bindings and entry
   point included, from the material's [BEMX graph](/docs/reference/bemx).
4. `lex` resolves names, types, members, calls, overloads, and references into a
   semantic graph. It normalizes `StageInput`, `interface`, `output`, and record
   returns into the stage input and output nodes that the VM and generators use.
   Then it [packs `bool` members](#pack-bool-members) into bytes.
   Before it links, it [expands signatures](#link-layers-and-signatures), and
   after, it records the layers `main` takes and erases layer parameters.
   `compile_to_besl` combines parsing and linking and can link the source to a
   supplied parent scope.
5. The optimizer removes semantically dead portable code.
6. Reflection evaluates the reachable graph, the
   [stage rules](#generate-ray-tracing-shaders) check the program against its
   stage and the output language, and the active generator emits GLSL, HLSL, or
   MSL. Tests can compile the same graph for VM execution.

`lex` recognizes a closest-hit shader by its signature: a `main` whose only
parameter besides `StageInput` comes last and has the type that `main` returns.
It keeps that payload parameter, checks that its type can be a
[payload](/docs/reference/besl/interface#ray-tracing-entry-points), and leaves
every other `main` as before. `invoke` isn't a registered intrinsic, because its
signature depends on the payload: the first `invoke` call of a program
instantiates it for the payload type it passes, and every later call must pass
the same type.

`lex` links each scope's declarations in order, each against the ones before
it, after moving the scope's `main` last, which is the
[declaration order rule](/docs/reference/besl/language#declaration-order).
When a declaration fails on an undeclared name that a later declaration of the
same scope declares, or on an undefined type that a later struct declares, the
scope reports the use as out of order instead, naming both declarations. The
check runs only after a failure, so linking a valid program does no extra
work. A member that its owner lacks reports its own error rather than an
undeclared name, so a later declaration with the member's name never reads as
the cause. `declarations_use_only_the_declarations_before_them` guards the
rule and the errors.

Standalone `.besl` assets use this path during baking and take their stage
settings from the adjacent
[`.besl.bead` file](/docs/reference/besl/interface#standalone-stage-metadata).

On macOS, baking keeps a precompiled header of the Metal standard-library
texture types in the system temporary directory, named
`byte-engine-msl-prelude-<hash>.pch`. Every shader compile reuses it, which
roughly halves the time a bake takes. Byte Engine builds one header for each
Metal toolchain and deployment target, and compiles without it if the compiler
rejects it, so you can delete these files at any time.

## Link modules

BESL does no file I/O, so the host that reads a shader also reads its
[module files](/docs/reference/besl/language#modules). `modules.rs` gives the
host three pure steps, which it repeats until nothing is pending, because an
attached file can declare modules of its own:

1. `pending_modules` lists the module path of each `name: mod;` that has no
   source yet. The parser keeps such a declaration as `Nodes::FileModule`.
2. `module_files` names the two files a path may live in. This is the only
   place the lookup rule lives.
3. `attach_module` replaces the `FileModule` with a `Nodes::Scope` that holds
   the file's declarations, after it checks that a module may hold them. The
   inline `mod` parser runs the same check.

The standalone BESL asset handler, `read_module_files` in
`asset/handler/implementations/besl.rs`, reads both files of every module
through `BakeContext::resolve`, even after it finds one. Every read records the
file as a bake dependency, and `TrackingStorageBackend` records a file that
doesn't exist as missing. Editing, creating, or deleting either file therefore
makes the shader and every pipeline that inherits its dependencies stale, and
the watcher rebakes them in development builds. The handler parses the files
again in `parse_standalone_program`, so reading stays apart from linking.

A path is one token: the tokenizer joins `a::b::c` and `a::*`, so every parser
site that reads a reference takes a path through `next_path`, and declaration
names, read through `next_identifier`, can't contain `::`.

Linking keeps each module a namespace. `find_in_scope` in
`lexer/resolution.rs` searches a scope's own declarations, then its `use`
imports, and never the modules inside it. Code inside a module still sees the
modules around it, because the scope chain holds them, so built-in types and
layer declarations resolve by name. `resolve_path` handles `crate`, `super`,
`self`, and module names, and a path call resolves overloads among one module's
declarations. A `use` links to a `Nodes::Use` that holds its target weakly,
since a module can import its own ancestor, and backends emit nothing for it.

Backends emit every declaration by its own name, so `check_unique_names` rejects
a struct, constant, or function name declared in two modules before linking
starts. Engine-built scopes, such as `Common` and `Visibility`, are modules too:
their generators add `use <Scope>::*;` after each one.

`crates/besl/tests/modules.rs` guards loading, paths, `use`, and the module
rules. `standalone_besl_handler_links_module_files_and_depends_on_them` guards
the bake dependencies.

## Link layers and signatures

[Layers and signatures](/docs/reference/besl/interface#layers-and-signatures)
are compile-time types: they shape what a shader consumes, and generated code
has no trace of them.

Signatures expand on the parsed tree, before linking, in `signatures.rs`.
`expand_signatures` resolves the signature each `name: Signature { ... }` names,
flattens its `+` parts, and replaces the implementation with a plain function.
It runs on the parsed tree because entry normalization reads `main`'s parameters
as parsed. The expanded function records the module path of the signature in
`types`, so its parameter types resolve where the signature was declared, not
where the shader implements it. `resolve` in the same file mirrors the linker's
path rules on the parsed tree; a change to path resolution changes both.

A layer links to `Nodes::Layer`, whose descriptors become ordinary bindings with
`layout` set to the layer's path. `layer.member` links to the member itself, in
`lexer/layers.rs`, so the linked graph reads the binding directly. After
linking, `record_entry_layers` notes on each layer which of `main`'s
parameters takes it, `place_descriptors` places every binding in the program's
descriptor sets, and `erase_layer_parameters` removes layer parameters and
arguments everywhere. Backends, reflection, and the VM therefore see only plain
bindings, each with its placement.

### Place descriptors

`place_descriptors` in `lexer/layers.rs` is the one place that decides where a
binding lives. It groups the bindings by `layout`, orders the groups into the
program's sets, and writes a `besl::Placement` on each binding:

- `set`: the set's position. Layers come in `main`'s parameter order, then
  layouts a backend adds, such as tile outputs, then the shader's own
  descriptors. A layer `main` doesn't take gets no placement.
- `resource`: how many descriptors the bindings before this one in its set
  hold. An array of `count` descriptors takes one binding number and moves only
  this offset.
- `sampler`: how many application-bound samplers come before it, for backends
  that keep samplers in a heap of their own.

Each set numbers its bindings from 0, so a layer's offsets are the same in
every shader that takes it, and a set built once from the layer binds wherever
a shader takes it. A set's position is the same whether or not `main` reads
from it; only the `used` mask that reflection computes depends on reachability.
Placing again is cheap and idempotent: tile lowering calls it after it turns
outputs into a set of its own.

Every consumer reads the placement instead of regrouping the program:
reflection orders `SetUsage` by it, the MSL generator binds set `n` at buffer
`16 + n`, the GLSL and HLSL generators index the descriptor heaps at set `n`'s
base plus the `resource` or `sampler` offset, and the VM keys resources by
`ResourceSlot { set, slot }`, where `slot` is the `resource` offset. A shader
reads at most `besl::MAX_DESCRIPTOR_SETS` sets, and each generator rejects a
program past it. See [Descriptor sets](/docs/develop/rendering/descriptor-sets)
for how each backend binds them.

Shared layers live in modules from the asset root, which load once per shader
and sit under a hidden scope named `::`. `write` prints each one as
`::path: mod { ... }`, which `parse` places back under that scope, so a program
with its modules attached writes as one file that links again without them.

A change must keep these true:

- A layer's set has the same bindings in every shader that takes it, so its
  identity matches the set Rust builds with `SetLayout::from_layer`.
- Sets follow `main`'s layer parameters, then layouts that backends add, then
  the shader's own; a layer `main` doesn't take forms no set. A set's position
  doesn't depend on which of its descriptors `main` reaches.
- Each set numbers its bindings from 0 without gaps, and an array takes one
  number.
- A program holds at most one push constant block across its layers and itself.

`crates/besl/tests/signatures.rs` guards signatures, layer access, erasure, and
the push constant rule, `crates/besl/tests/descriptor_sets.rs` the placement,
and `crates/besl/tests/modules.rs` the modules from the asset root and their
written form.

## Pack bool members

A `bool` has no byte form that every backend shares: Metal stores one byte, and
GLSL and HLSL store four. So a linked program never stores one. After linking,
`lex` runs `pack_bool_members` in `lexer/bools.rs`, which turns each run of
contiguous `bool` members of a struct, buffer block, or push-constant block into
`ceil(N / 8)` hidden `u8` members named `_besl_bits<k>`, and rewrites every
access in place:

- a read becomes `(u32(byte) & mask) != 0`;
- a write becomes `byte = u8((u32(byte) & ~mask) | (value ? mask : 0))`; and
- a constructor call assembles each byte from its `bool` arguments, in order.

The [Bool members](/docs/reference/besl/language#bool-members) reference states
the resulting layout. Backends, reflection, the optimizer, and the VM see only
`u8` members, so none of them has `bool` storage rules. The pass runs once per
linked graph: a second run finds no `bool` members left.

Each backend stores a `u8` member in one byte. HLSL has no 1-byte member type,
so the DX12 generator declares each `uint16_t` window that holds `u8` members at
their scalar offset, `_besl_bytes<offset / 2>`, in place of those members, and
reads and writes each byte with shifts. `evaluation/byte_windows.rs` plans the
windows, and reflection rejects, on every platform, a stored layout whose window
would cover a byte of another member or lie past the layout's end. A `u8` array
member stays a `uint` array on DX12, one word per element.

The VM places buffer members with the same scalar alignment that reflection
uses, so host code reads the bytes a GPU writes.

A change must keep these true:

- A write to a packed `bool` reads its byte, so the pass rejects one through a
  write-only buffer, or through a place whose index calls a function, which
  would run twice. The second rule covers every `u8` write, since a DX12 window
  write reads its word too.
- Writes aren't atomic on any backend.
- Every backend and the VM agree on each member's offset and each struct's size.

`bool_members_pack_into_bits_in_declaration_order` and
`buffer_members_start_on_their_scalar_alignment` guard the VM layout,
`bool_members_reject_what_bits_cannot_store` the rejections,
`packed_bool_and_byte_records_reflect_one_stride_on_every_backend` and
`reflection_rejects_bytes_dx12_cannot_window` the shared layout, and
`byte_members_lower_to_two_byte_windows` the HLSL generator.

## Extend a program from Rust

Some graph features are intentionally available only to engine and render-model
code. They aren't syntax you can write in a `.besl` file.

| Generated feature | Rust entry point | Use |
| --- | --- | --- |
| Specialization value | `ParserNode::specialization` | Add a host-selected typed value at a pipeline constant id. Vector components take consecutive ids, so give each specialization its own range. Pipelines receive values through `SpecializationMapEntry` at the same ids, and the VM receives them by name through `SpecializationValues`. See [Shader variants](/docs/develop/rendering/shader-variants) for when to use one. |
| Custom intrinsic | `ParserNode::intrinsic` or `ParserNode::intrinsic_with_parameters` | Register a generated callable operation and its typed body. |
| Generated struct | `ParserNode::r#struct` with `ParserNode::member` fields | Expose a Rust record shape to the BESL parent scope. |
| Parent scope | `compile_to_besl(source, Some(parent))` | Let authored source resolve generated types, values, bindings, and helpers. |
| Modules from embedded sources | `ModuleLoader::load(source, read)` then `attach_modules` | Attach the modules a program names from sources the host holds in memory, such as a renderer's embedded layer modules. |

A program has no backend-specific code. Add an intrinsic, and lower it in each
backend, when portable BESL can't express a feature.

## Write a program back as source

`write` turns a parsed syntax tree, or one a generator built, back into BESL
source. Bakes use it to show the program each shader compiles from; see
[Intercept intermediate products](/docs/develop/resource-management/assets#intercept-intermediate-products).

A change to the parser or the syntax tree must keep this rule true: source
that parses writes as source that parses back to the same tree. Every node
writes in the form the parser reads, with parentheses only where operator
precedence needs them. A parsed group, `(a + b)`, stays a group, so writing
twice gives the same text. When you add a node or a syntax form, add its
written form to `writer.rs` and a case to its round-trip tests.

The features in [Extend a program from Rust](#extend-a-program-from-rust)
have no source form. They write in the nearest form a reader understands:
bindings as descriptors, and specializations and intrinsics as comments. The
[BELD reference](/docs/api/beld#intercepts) lists each one. A program that
holds them doesn't parse back, and doesn't need to.

## Understand optimization

`optimization::optimize` operates on functions reachable from `main`. It:

- removes unread local declarations when their initializer has no observable
  effect;
- removes statements after a `return`, `continue`, or `break` in the same block; and
- repeats until removing one local doesn't expose another dead local.

Calls, atomics, image writes, barriers, and assignments outside a
local value remain intact. The pass is idempotent and reports how many dead
locals and unreachable statements it removed.

## Understand reflection

The resource-management shader layer reflects descriptors into stable metadata:

- authored name, binding number within its set, and set;
- buffer, sampled-texture, storage-image, or acceleration-structure kind;
- texture view shape and resource count;
- storage-buffer stride for the active layout target; and
- read and write usage.

Reflection groups the descriptors into descriptor sets: one for each
[layer](/docs/reference/besl/interface#layers) with descriptors that `main`
takes, in parameter order, and one for the descriptors the shader declares
itself. Each set holds its layer's whole layout and marks the
descriptors that code reachable from `main` uses. Two sets with the same
descriptors have the same identity, whichever shader they were reflected from.

Reflection also describes the ray tracing payload, which baking persists in
`ShaderInterface::ray_payload`: the payload that a closest-hit `main` takes, or
the one that a program's `invoke` calls pass. It records the payload's name, its
size in the active backend's storage layout, and a 64-bit Fowler–Noll–Vo 1a
hash of its name and its members' names and types in declaration order. Ray tracing
pipeline assembly compares the hashes of a pipeline's shaders, because Metal
links visible functions whose payloads differ without an error. Keep the hash
input in declaration order, so that reordering a payload's members changes it.

It rejects distinct bindings that take one binding number of one set. Reflection also classifies
the reachable output as `Opaque`, `NonOpaque`, or `Unknown` for material
decisions.

Express resources and outputs in BESL whenever possible. Reachable declarations
let Byte Engine validate, reflect, optimize, and test the program consistently.

## Lower static samplers

A [sampler declaration](/docs/reference/besl/interface#samplers) isn't a node of
the linked graph. The linker records each one as it reaches it, and puts its
state, `besl::SamplerState`, on every texture binding that names it, in
`BindingTypes::CombinedImageSampler`. Reflection carries the state into the
persisted interface, so it's part of the layout identity. The renderer then
declares the texture as a `ghi::ResourceKind::SampledImage`, and the
application binds only the image.

Each backend reads the sampler in its own way:

- Vulkan and DX12 write the 36 fixed samplers once, at the start of the sampler
  heap. The GLSL and HLSL generators read a fixed sampler at the literal index
  `besl::SamplerState::fixed_index` returns, and the texture's set holds no
  sampler for it. The GHI writes the table in the same order; the
  [fixed sampler table](/docs/reference/ghi#descriptor-sets) is the contract
  between them.
- Metal compiles it into the shader: the MSL generator declares a program-scope
  `constexpr sampler`, and leaves the sampler out of the argument buffer and
  the kernel parameters.

Only Apple10 GPUs reduce in a Metal sampler, and a baked shader doesn't know
which GPU runs it. So the MSL generator gives a `min` or `max` sampler no
reduction, and lowers each read through it, and each `downsample_min` or
`downsample_max` call, to a helper that gathers or reads the four texels and
reduces them. That emulation is why the reference limits a reducing sampler to
one-channel 2D textures, clamp addressing, a nearest mip filter, and
explicit-LOD reads in the function that names the texture: the helper can
reproduce exactly those reads. A runtime `ghi::sampler::Builder` that asks for a
min or max reduction on an older Metal GPU panics instead of averaging.

Keep these rules when you change a backend:

- A sampler the shader fixes takes no argument ID, binding, or register of its
  own. The MSL argument-buffer layout and the GHI's `argument_bases` must agree
  on that, or every binding after the texture shifts.
- A sampler the shader fixes reads every level of its image: no LOD clamp.
- The VM reads through the declared state in place of the sampler the test
  binds, so VM tests of reducing shaders don't depend on their fixtures.

## Generate ray tracing shaders

The MSL and GLSL generators lower ray tracing. Each follows the contract
between its GHI backend and the shaders it links, which the
[ray tracing design note](/docs/develop/rendering/ray-tracing) defines. For
Metal, a ray generation shader becomes a compute kernel, and a closest-hit
shader becomes a `[[visible]]` function that the kernel calls through the
visible function table at buffer 14. For Vulkan, a ray generation shader
becomes a `raygen` shader, and a closest-hit shader becomes a `callable` shader
that the ray generation shader calls through the shader binding table's
callable region.

Before any generator runs, `platform::Generator::lower` checks the program with
`validate_stage`, in
`crates/resource-management/src/shader/besl/backends/stage_rules.rs`. It
checks the `main` signature of ray tracing stages, that a closest hit declares
no descriptors of its own, which stages call `intersect`, `trace_occlusion`,
`invoke`, and the launch and hit values, and that ray tracing stages use no
workgroup storage, barriers, subgroup intrinsics, compute invocation values, or
`discard`. For HLSL, it rejects ray tracing stages and every ray tracing
call. Each error names the stage, the shader, and the rule, and links the
reference section that states the rule. The HLSL generator also refuses ray
tracing stages and acceleration structures itself, for callers that skip
`lower`.

| BESL | Generated MSL |
| --- | --- |
| `Hit` | A struct with the members in reference order. Its vectors are packed, as in every struct a buffer holds, so a hit has one 52-byte layout in buffers and in calls. `distance` is a reserved name in MSL, so that member is `besl_distance`. |
| `intersect` | `_besl_intersect`: an `intersector<instancing, triangle_data, intersection_function_buffer>` with the default, empty function buffer, because only that tag reports `function_id`, the hit's record. A miss returns the hit that the reference specifies for one, with a `distance` of `-1.0`. |
| `trace_occlusion` | `_besl_trace_occlusion`: an `intersector<instancing>` that accepts the first intersection and reports no triangle data. |
| `invoke(hit, payload)` | `_besl_invoke`, which calls the table entry of `hit.record` when the hit's distance is zero or more. For a negative distance or one that isn't a number, it returns the payload unchanged. |
| `launch_index`, `launch_size` | The kernel's `[[thread_position_in_grid]]` and `[[threads_per_grid]]`. The GHI dispatches the exact launch size, so the kernel checks no bounds. |
| Hit values | Members of the `Hit` that the closest hit receives. Packed vectors convert to `float2` and `float3`. |

Both intersectors force opacity and assume triangles, because every geometry is
opaque. Each helper is emitted only into shaders that call it.

A kernel and the closest hits it calls agree on two declarations, which every
ray tracing shader emits:

- `_besl_ray_context` holds the addresses of the push constant and of each
  descriptor set, as `constant void*`. The kernel fills it from its own
  parameters, and a closest hit casts each address back to its set's struct.
- `_besl_closest_hit` is the type of every closest hit:
  `void(thread P&, thread const Hit&, thread const _besl_ray_context&)`, where
  `P` is the payload. A closest hit's `besl_main` unpacks its push constant and
  sets from the context, calls the shader's `main` with the payload and the
  hit, and stores the payload it returns.

A change to this lowering must keep these rules:

- **A ray generation kernel takes every set and the push constant its program
  declares**, used or not, because a closest hit can read what the kernel
  doesn't. Every other stage takes only the sets that its reachable code uses.
- **A closest hit takes every set its program declares too**, so a closest hit
  that reads a later set still finds it at its position in the context.
- **Hidden values reach helpers as trailing parameters.** A helper function
  that reads a launch or hit value or a resource takes the hit in a closest hit,
  and the launch index and size in a ray generation shader, plus the function
  table and the context when the shader calls `invoke`. The push constant and
  every set follow.
- **The kernel builds the context only when it calls `invoke`.**
- **Only shaders that use ray tracing include `<metal_raytracing>`:** a ray
  tracing stage, a ray query, or a `Hit` or an acceleration structure that the
  shader or one of its sets declares. Other shaders generate the same MSL as
  before.
- **The prelude declares `Hit` once.** The lexer rejects a struct named after a
  built-in type, so a `Hit` in the program is always the built-in one, and the
  generator skips it.

### Lower ray tracing to GLSL

| BESL | Generated GLSL |
| --- | --- |
| `RayGeneration`, `ClosestHit` | `#version 460`, with `#pragma shader_stage(raygen)` or `#pragma shader_stage(callable)` and `GL_EXT_ray_tracing`. |
| `Hit` | A struct with the members in reference order. `distance` is reserved in GLSL, so that member is `besl_distance`. |
| `AccelerationStructure` | `uniform accelerationStructureEXT` at its binding, with `GL_EXT_ray_query`. |
| `intersect` | `_besl_intersect`: a ray query with `gl_RayFlagsOpaqueEXT`. A hit's record is the committed intersection's instance shader binding table offset plus its geometry index. A miss returns the hit that the reference specifies for one. |
| `trace_occlusion` | `_besl_trace_occlusion`: a ray query with `gl_RayFlagsOpaqueEXT` and `gl_RayFlagsTerminateOnFirstHitEXT`, which reports whether it committed any triangle. |
| `invoke(hit, payload)` | `_besl_invoke`, which writes the payload and the hit into the callable data and calls `executeCallableEXT(hit.record, 0)` when the hit's distance is zero or more. For a negative distance or one that isn't a number, it returns the payload unchanged. |
| `launch_index`, `launch_size` | `gl_LaunchIDEXT` and `gl_LaunchSizeEXT`. |
| Hit values | Members of the hit in the callable data, `_besl_call_data.hit`. |

A ray generation shader and the closest hits it calls agree on one
declaration, which both emit right after the payload's struct:
`struct _besl_call { P payload; Hit hit; }`, as the ray generation shader's
`callableDataEXT` and the closest hit's `callableDataInEXT`, both at location 0.
A closest hit's `main` becomes `_besl_closest_hit_main`, which takes and returns
the payload, and the shader's `main` passes it the callable data's payload and
stores the result back. Every stage of a Vulkan pipeline reaches the same
descriptor bindings, so the GLSL lowering passes no addresses and adds no hidden
parameters. Shaders that use no ray tracing keep `#version 450` and generate the
same GLSL as before.

These tests guard the lowering. The Metal compile tests run on macOS only, and
the glslang compile tests on Linux only. The GPU test runs on both, with a GPU
that traces rays, and needs the `gpu-processing` feature, which workspace runs
enable.

| Test | Guards |
| --- | --- |
| `generated_ray_generation_stage_compiles_with_metal` | The kernel's parameters, the context it builds, the hidden parameters of a helper that calls `invoke`, and that Metal compiles the kernel. |
| `generated_closest_hit_stage_compiles_with_metal` | The visible entry point, how it unpacks its sets, hit values in `main` and in helpers, and that Metal compiles it. |
| `ray_queries_compile_in_compute_shaders` | `intersect`, `trace_occlusion`, and `Hit` construction in a compute kernel. |
| `generated_ray_tracing_shaders_match_the_vm` | Baked shaders write on the GPU what the VM writes: both hit groups, a mask that skips an instance, misses, occlusion, and a direction twice the unit length. It runs on Metal and on Vulkan. |
| `generated_ray_generation_stage_compiles_with_glslang`, `generated_closest_hit_stage_compiles_with_glslang`, `ray_queries_compile_in_compute_shaders` | The GLSL stages, callable data, and ray query helpers, and that glslang compiles them. |
| `calls_that_a_stage_does_not_allow_are_rejected`, and the other `stage_rules` tests | The stage rules in MSL and GLSL, and their rejection of HLSL. |
| `lowering_reports_the_stage_rule_a_shader_breaks` | `lower` checks the stage rules before a generator runs. |

## Generate task and mesh shaders

BESL lets one invocation set a task workgroup's mesh grid and keep running, the
way Metal runs task stages. SPIR-V and DXIL instead require every invocation to
make that call once, in uniform control flow, and SPIR-V ends a task invocation
at its call. So the GLSL and HLSL generators reshape the task stage. The mesh
counts need no reshaping: BESL requires every invocation to set them, as SPIR-V
and DXIL do, and the MSL generator sets Metal's counts from one thread itself.
The GLSL lowering lives in
`crates/resource-management/src/shader/besl/backends/glsl/generator/mesh_shading.rs`:

| BESL | Generated GLSL |
| --- | --- |
| `task_payload` arrays | Members of one `_BeslTaskPayload` struct, in declaration order, held by the one `taskPayloadSharedEXT` variable that GLSL allows. A mesh stage declares the same struct for the arrays it declares. |
| `set_task_mesh_output_count(count)` | A store to the workgroup variable `_besl_task_mesh_count`. |
| A task stage's `main` | `_besl_task_main`. The entry point clears the count on invocation zero, runs `_besl_task_main`, and after a barrier calls `EmitMeshTasksEXT` with the count, so every invocation reaches the call, including one that returned early. |
| `set_mesh_output_counts(v, p)` | `SetMeshOutputsEXT(v, p)`. |
| An interface field of type `primitive<T>` | A `perprimitiveEXT` input, `flat` too for integers, and `GL_EXT_mesh_shader` in the fragment shader. |

A change to this lowering must keep these rules:

- **The task entry point emits the grid after BESL's `main` returns**, from
  every invocation. An early `return` in `main` returns from
  `_besl_task_main`, not from the entry point.
- **A task workgroup that sets no count emits no mesh workgroups**, because the
  entry point clears the count before `main` runs.
- **The payload struct lists the arrays in declaration order in both stages**,
  so the task and mesh stages agree on its layout.
- **A fragment input is per-primitive exactly when the mesh output it reads
  is.** Vulkan validation rejects a pipeline whose two stages disagree, with
  `VUID-RuntimeSpirv-OpVariable-08746`. Metal and DXIL link by location and
  need no marker, so the MSL and HLSL generators ignore `primitive<T>`.

## Execute BESL in the VM

The VM runs portable BESL semantics on the host. Use it for behavior tests that
shouldn't depend on one generated shading language.

The VM supports:

- scalar, vector, matrix, struct, array, function, expression, and control-flow
  semantics;
- descriptor buffers, sampled textures and samplers, storage images, push
  constants, and stage input and output layouts;
- texture mips, explicit level of detail, texel fetches, array layers, image
  operations, and
  atomics;
- invocation coordinates, configurable subgroup collectives, workgroup shared
  storage, and barriers through the workgroup scheduler; and
- task payloads and output counts plus captured mesh counts, positions,
  triangles, and render-target array indices; and
- ray queries against a scene, and ray tracing pipelines whose ray generation
  program runs closest-hit programs through `invoke`.

Buffer layouts place each member on its scalar alignment and round a struct up
to its largest alignment, as reflection does for the GPU backends.

Compile a linked graph with `ExecutableProgram`, bind its resources through
`DescriptorBindings`, and call `run_main`, `run_main_with_config`, or
`run_workgroup`. A resource's key is its set's position and its descriptor's
offset in the set; `ExecutableProgram::slot` returns it for a descriptor name, so
tests bind by the names shaders give their resources. `ExecutionConfig` sets instruction and call-depth limits,
invocation coordinates, subgroup size, and task or mesh output limits.

### Trace rays in the VM

Build a scene from `BottomLevelStructure` triangle lists placed by `Instance`
values, pass the instances to `AccelerationStructure::new`, and bind the scene
with `DescriptorBindings::bind_acceleration_structure`. A compute program then
runs its ray queries through `run_main`. For a pipeline, pass a ray generation
program and one closest-hit program per hit group to `RayTracingPipeline::new`,
and call `trace_rays` with the shader binding table's records and the launch
size. Record `i` runs hit group `records[i]`, as `write_shader_binding_table`
records do on the GPU.

The VM trades speed for results you can predict. A change must keep these rules,
which `crates/besl/tests/ray_tracing.rs` guards:

- Ray queries test every triangle, in instance, geometry, and triangle order,
  with the Möller–Trumbore test. There's no hierarchy, so keep VM scenes small.
- A ray moves into each instance's object space through the inverse of the
  instance's affine transform, which keeps the ray's distance and the
  barycentrics of each point, as a world-space test would.
- Every triangle is opaque and both faces hit. Both ends of the ray's interval
  belong to it.
- Of equally near hits, the first in test order wins, where the GPU may report
  any of them.
- Where the reference leaves the GPU result undefined, the VM returns an error
  instead: an invalid ray interval, or a record past the end of the shader
  binding table.
- `invoke` runs only in a ray generation invocation. `RayTracingPipeline::new`
  rejects a hit group that isn't a closest hit, a closest hit that calls
  `invoke`, `intersect`, or `trace_occlusion`, and a closest hit whose payload
  type differs from the one the ray generation program passes.
- Launch values exist only in a ray generation invocation, and hit values only in
  the closest hit it invokes. Ray tracing invocations have no peers, so
  workgroup barriers and subgroup collectives are errors in them, and so is
  `discard`, which only fragment shaders run.
- A closest hit reads the descriptor bindings of the ray generation program that
  invokes it. The VM doesn't model descriptor sets, so it doesn't check that a
  closest hit's sets are the first sets of the ray generation shader.
