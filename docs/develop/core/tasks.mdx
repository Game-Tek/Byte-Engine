Read this note before you change the gameplay task runtime, which polls an
application's async gameplay from its tick. To use it, see
[Script gameplay with tasks](/docs/use/gameplay-tasks). The code lives in
`crates/byte-engine/src/gameplay/tasks.rs`.

## How a poll runs

The runtime keeps the futures of live tasks in a vector indexed by task slot.
Everything else it shares with the `Tasks` handles through one `Rc<RefCell>`:
the clock, each task's waits, and the ready queue. Runtime methods and wait
futures borrow the shared state only briefly, never across a task's poll. A
task can therefore spawn and wait from anywhere in its code, including inside
`with`.

`poll` pops the ready queue until it's empty. Each poll of a task gets a new
number, which the task records as its latest poll. The application's state goes
to the task through `ContextBuilder::ext`, which `with` downcasts. A task that
finishes is removed, and its future drops once the shared state is released,
since a destructor may reach it.

## How waits register and cancel

A wait records the number of the poll that made it. Polling a pending wait
future records the current number again. A wait counts only while its number
equals the latest poll of its task, so a future the task dropped, or stopped
polling, stops counting after that poll. The UI engine's runtime uses the same
scheme.

Stale waits are also removed, so they don't pile up. A sleep future that drops
while registered flags its task's poll, and once that poll ends the runtime
sweeps the task's waits and keeps only the ones the poll registered. Polls that
drop nothing skip the sweep, which keeps a tick's cost flat.

- **Messages.** The runtime keeps no messages. Tasks await the message bus
  through `DefaultListener::recv`, which registers the task's waker on the
  channel's topic when nothing is queued. A send stamps its slot, then loads the
  topic's waiting flag and wakes every registered waker when it's set. Both
  sides use sequentially consistent operations, so either the send sees the
  flag or the listener's read after registering sees the message. A listener
  registers once per wake, and a dropped one costs at most one spurious wake.
- **Ticks.** A task's tick waits live with the task, and the task joins a list
  that the next `advance` walks, keeping only the waits of the task's latest
  poll. A tick wait first polled in a poll takes over
  the earliest wait the task didn't poll again in that poll. This keeps ticks
  counting when a `select!` loop drops its tick branch, and lets a new loop
  resolve its tick in the same poll.
- **Sleeps.** A min-heap orders deadlines. `advance` pops the due ones and wakes
  the task when its wait still counts. A sleep polled again after a sweep
  removed it pushes a new deadline. Swept and ended sleeps leave their entries
  in the heap, so the runtime rebuilds the heap once more than half its entries
  are dead.

The runtime's tick and sleep waits wake tasks directly, without a `Waker`. Each
task also has one for channel listeners and other futures. Its wakes go through
a locked queue that `poll` drains, so they can come from any thread, such as
alley lanes that send during a system's step.

## Rules a change must keep

1. Tasks never read wall-clock time. The clock moves only by the deltas that
   `advance` receives.
2. One poll order for one input sequence: tasks run in the order they woke, and
   nothing iterates a hash map to decide an order.
3. A wait counts only while the latest poll of its task registered it.
4. The shared state is never borrowed while a task's code runs or a future
   drops.
5. Tasks spawned on an entity end at the first `advance` after the world deletes
   it.
6. Per-tick work grows with the tasks that wait, not with every live task.
7. Nothing outlives its task. An ended task leaves no waits, and dropping the
   runtime drops every future it kept, including tasks it never polled.
8. A send on a channel nobody awaits pays one flag load and no lock.

## Benchmarks

The `tasks` benchmark guards rule 6 at the scale of one task per entity. It
times one tick of 4096 tasks: `tick_waits` wakes every task for the tick, and
`listener_waits` sends one message on a channel every task awaits through its
own listener, which is the fan-out of one broadcast. Divan reports the time per
task. Rule 8 is guarded by the `channel` benchmark, whose sends never have a
waiter.

```bash
cargo bench -p byte-engine --bench tasks
cargo bench -p byte-engine --bench channel
```

Run it before and after a change to the runtime. Keep each build's benchmark
binary and run them in turns, because other load on the machine shifts results
from one run to the next.
