Use the early UI module to build retained, asynchronous interfaces inside the
Byte Engine render loop.

An asynchronous component function receives a layout `Context`. It creates
elements in stable keyed slots, waits for events, and can mount child components
that return values. The runtime keeps state between evaluations, so your
application does not rebuild each interaction from the beginning.

## Choose the main API

- `layout::engine::Engine` evaluates retained UI and produces render data.
- `Context` and `ContainerContext` are the component-facing construction and event APIs.
- `Container`, `Text`, `TextField`, `Image`, `Curve`, and `Shape` are the current built-in primitives.
- `UiRenderPass` turns evaluated UI render data into GPU draw work.
- `ConcreteStyle`, `ConcreteLayer`, `Transform`, and `Visual` hold styling, animation-oriented transforms, and opacity.

The layout layer stays small by design.
Containers own sizing, positioning, flow, clipping, style, and visual data.
Flow functions such as row, column, grid, and centered variants place children.
Transforms are best treated as animation and presentation state, while position and sizing describe stable layout.
A transform applies to the whole subtree: a scaled container scales its
descendants' rectangles, hit bounds, clipping, curve points, stroke widths, and
font sizes together, so one transform on a content layer zooms a canvas.

## Handle events and focus

UI events are futures that your component can await.
A component can wait for pointer-style events, keys, text edits, timers, or render ticks.
Text input is app-owned: `TextField` emits edit deltas such as inserted and deleted characters, and application state decides how to apply them.

Components request and release focus explicitly. Send key and text-edit events to
the focused element.

## Read and change engine state

A component never holds the engine. Changes it makes, such as declaring an
element, `update_container`, `remove`, `reparent`, and focus requests, are sent
to the engine right away and applied after the component yields, in the order
they were made. The next layout sees them, and so do components that run after
it in the same evaluation. Because an edit runs later, its closure owns what it
uses: write `move |container| ...` and copy or clone the values it needs.

Reads are futures that complete at once. Await them in the component:

```rust
let bounds = card.geometry().await;
let pointer = ctx.pointer().await;
let held = ctx.drag().await;
let score = ctx.with(|app: &App| app.score.get()).await;
```

`Context::with` lends the application context you passed to
`Engine::with_context`. The host reaches the same value between evaluations
through `Engine::ctx` and `Engine::ctx_mut`.

## Understand component lifetime

A component started with `component` runs until its future returns or until the
scope that started it is removed, whichever comes first. A scope is the one a
`mount` created: when the mounted future completes or is dropped, its elements
are removed and every component started inside it ends, including components
those components started. Components started outside any mount live until they
return or the engine is dropped.

`EvaluationContext::remove` removes one element together with everything
declared under it: its descendants and the components started there. The
context it was called on stays valid only to declare the same key again, which
gets the same id. A mounted component awaited from outside the removed element
keeps running until its own future ends; its elements are gone, so its updates
change nothing.

## Build content at runtime

`Context::element` takes an `ElementKey`. An element's id is computed from its
parent's path and its key, so the same key under the same parent always
resolves the same retained element. A static name identifies a fixed part of a
component. An owned `String` names an element created from data, such as one
node of a graph, and the slot is keyed by the string's content:

```rust
let mut node = canvas.element(format!("node-{id}")).container(node_frame(position));
let mut wire = canvas.element(format!("wire-{from}-{to}")).curve(wire_between(a, b));
```

Siblings under one parent need distinct keys. For a list, pair a name with the
item's index:

```rust
for (index, row) in rows.iter().enumerate() {
    list.element(("row", index)).container(row_frame(row));
}
```

Declaring the same key twice under the same parent in one frame is an error:
the engine logs it, ignores the second declaration, and fails a debug assertion.

Keep the element contexts as the handles to that content. Re-route a wire while
its ends move with `EvaluationContext::update_curve`, editing the path in place
so its segment buffer is reused; changing only the segments repaints the curve
without replaying layout. Remove a node or a wire with
`EvaluationContext::remove`:

```rust
wire.update_curve(move |curve| {
    let path = curve.path_mut();
    path.clear();
    path.push_cubic(from, from + tangent, to - tangent, to);
});
node.remove();
```

## Drag a UI item onto an application target

The engine owns one pointer drag. Create a position action with
`ActionBindingDescription::new("Mouse.Position").dragged_by("Mouse.LeftButton")`
in your UI's input sink and forward its phases to the engine in normalized
window coordinates. `Engine::press` grabs the surface under the pointer from
the last evaluated frame and returns whether it found one. In this example,
`accept_drop` maps the released source to your data and validates the
application target before changing application state:

```rust
match phase {
    ActionPhase::Started => {
        engine.press(window_position);
    }
    ActionPhase::Updated => {
        engine.drag_to(window_position);
    }
    ActionPhase::Ended => {
        if let Some(drop) = engine.release(window_position) {
            accept_drop(drop);
        }
    }
    ActionPhase::Cancelled => {
        engine.cancel();
    }
}
```

Capture the gesture in your UI's sink before gameplay processes the same
input, and continue forwarding motion and release outside the source.
`Engine::hit` answers what is under a point when a sink needs that for its own
capture decisions, such as refusing a drop over UI.

The grabbed surface receives the gesture as events, so it can react on its own.
It gets `Events::Grabbed` on press. Once the pointer travels past the drag
threshold, it gets `Events::Dragged` at the start of each `Engine::evaluate` in
which the pointer moved, with `UiEvent::delta` set to the offset from the press
point in layout units. When the grab ends by release or cancellation it gets
`Events::DragEnded`, with `UiEvent::source` set to the surface the drag was
dropped on, if any. Await all three in one loop, because an event with no
component waiting for it is discarded, and a press and release can arrive in
the same frame:

```rust
let mut origin = None;
loop {
    let event = select! {
        event = card.on(Events::Grabbed) => event,
        event = card.on(Events::Dragged) => event,
        event = card.on(Events::DragEnded) => event,
    };
    match event.kind {
        Events::Grabbed => {
            origin = card.geometry().await;
            card.update_container(move |card| card.depth = Depth::absolute(1));
        }
        Events::Dragged => {
            if let (Some(origin), Some(delta)) = (origin, event.delta) {
                card.update_container(move |card| card.set_transform(placed_at(origin.x() + delta.x, origin.y() + delta.y)));
            }
        }
        _ => {
            origin = None;
            card.update_container(move |card| {
                card.depth = Depth::relative(1);
                card.set_transform(Transform::identity());
            });
        }
    }
}
```

`Depth::absolute` lifts the card out of its parent's flow and places it from
the viewport, so a translation by the drag offset from its grabbed geometry
follows the pointer. When scaling a preview, use
`Transform::origin(UiPoint::zero())` to keep its top-left corner anchored.

The surface under the release point, and then each of its ancestors, gets
`Events::Dropped` with `UiEvent::source` set to the released source; the source
itself is skipped when finding that surface. The engine resolves the target at
the start of the next `Engine::evaluate` from the previous frame's hit
geometry, before components run, and queues the source's `DragEnded` after it,
so a target claims the source before the source settles. A target takes a
dropped element into its own layout with `EvaluationContext::adopt`, which
makes it the target's last flow child while keeping its id and properties:

```rust
loop {
    let event = stack.on(Events::Dropped).await;
    if let Some(card) = event.source {
        stack.adopt(card);
    }
}
```

While a source is held, the surface under the pointer other than the source is
available as `DragCapture::over`, so the source can preview where a release
would land.

`Engine::release` still returns the `DragDrop` for applications that apply
drops outside the UI, so either side can act on it. An element can also move
itself under another parent with `EvaluationContext::reparent`.

`Engine::cancel` ends the interaction in progress: it restores the held source
and discards queued clicks, scrolls, key presses, and text edits. Call it when
the window loses focus or the user cancels. A changed viewport size cancels
from `Engine::evaluate`, because layout distances and the source's place move
with it. The UI supplies the gesture and geometry; your application decides
which targets accept the item and how to apply it.

## React to the pointer passing over a surface

Each `Engine::evaluate` compares the surface under the pointer with the previous
frame's. When it changes, the old surface gets `Events::PointerExited` and the
new one `Events::PointerEntered`, each followed by the ancestors that stopped or
started containing the pointer. An ancestor containing both surfaces hears
nothing, so a panel keeps its hover state while the pointer moves between its
children. A held drag source is skipped, so a drop target under a dragged item
still receives `PointerEntered`. `Engine::hovered` answers the same question at
the application level, for a cursor shape for example.

Curves take part once given a hit width: `Curve::hit_testable(width)` lets the
pointer find the curve within `width` layout units of its stroke, along its
whole length even where it runs beyond its declared size. A wire can then be
hovered, clicked, and dropped on like a container. The width follows the
inherited transform scale.

A container with an absolute position may sit partly outside its parent,
including at negative coordinates, so a canvas can be panned past its edge
without snapping its content. Flow-placed children are still kept inside the
viewport.

## Work within the current limits

<Callout type="info" title="Primitive UI layer">
	The module isn't a complete widget toolkit yet. Treat it as a retained
	primitive layer with an asynchronous interaction model.
</Callout>

Build higher-level widgets through small composed components before you add
runtime machinery.

When you add a UI feature, follow the existing route:

- build or update a primitive
- let layout evaluate geometry, clipping, and retained identity
- let `UiRenderPass` consume the render data

That path keeps UI code testable and avoids coupling application widgets directly to renderer resource ownership.

## Retention and invalidation

Unchanged UI must cost nothing beyond the draw calls themselves, so every stage
retains its result and reuses it while its inputs repeat. The contract is one
chain of revisions:

- The retained tree advances a revision whenever an element is added, removed,
  or handed out for mutation through `update_container`, `update_text`,
  `update_curve`, and the other update methods. Every such call counts, so only call them when state
  actually changed. Re-declaring the same element path on a later frame does
  not count.
- `Engine::evaluate` reuses the retained layout while the tree revision and the
  viewport size repeat. Input routing and task polling still run every frame.
- `Engine::render` returns a reference to the render retained by the engine.
  It keeps the same `Render::revision` while the tree, its layout, and the
  viewport are unchanged, so clone it only when the revision moved.
- `Engine::render` also reports damage: `Render::damage` returns the previous
  revision and the layout-unit rectangles whose pixels differ from it, built
  from the same per-node revisions. A consumer holding pixels for that base
  revision redraws only inside those rectangles; anyone else redraws everything.
  A viewport change reports no base, meaning everything changed.
- `UiRenderPass` keeps a persistent transparent UI layer. Each frame it clears
  and redraws only the damaged pixel regions (plus every visible backdrop blur,
  which samples the scene rendered that frame), then composites the scene under
  the layer. Primitives, uploads, and glyph residency are rebuilt only for the
  elements touching that damage, and only when the adopted render revision, the
  viewport extent, the glyph generation, or the damaged regions change. A frame
  with no damage records only the composite.

Applications should publish a render only when `Render::revision` changes. The
render source deduplicates repeated revisions anyway, so a republished unchanged
render never makes a sink rebuild.

Anything that must change pixels has to go through the tree: mutate elements
through the evaluation context rather than by keeping visual state outside the
engine. Placement, style, opacity, clipping, and transforms all live on retained
elements, so the revision covers them. Changing the viewport size is the one
input outside the tree, and both evaluation and rendering key on it.

## Depth

Depth decides what paints over what, and what a pointer hits first. It is local
to each container. `Depth::relative(n)` orders a child among its siblings: a
container paints first, then its children from the lowest depth to the highest,
and children at the same depth in the order they were declared. A child that is
not a container counts as `Depth::relative(1)`.

A container and everything inside it paint as one block. No depth set inside a
component can put one of its elements over or under another component, so a
widget can use whatever depths it likes for its own overlays.

`Depth::absolute(n)` is for layers that must cover the rest of the UI, such as a
modal or a toast. The container leaves its parent and paints above all ordinary
content, wherever it is declared. Absolute layers stack from the lowest `n` to
the highest and in tree order among equals. A layer declared inside another one
paints over it, so a dialog opened from a modal covers that modal.

## Drawing

`UiRenderPass` draws the whole UI with one shader pair and no vertex or index
buffers. Every rectangle layer, glyph, image, backdrop blur, and curve piece is
one 80-byte primitive in a storage buffer, written in painter order: by depth,
then by element, across all element types. The vertex shader pulls six vertices
from each primitive, and the fragment shader branches on the primitive's kind.
A primitive is constant across its quad, so each branch is coherent, and a plain
square fill skips the corner, stroke, and mask math entirely.

A frame is one draw per damaged region. Only a backdrop blur adds draws, because
it reads the layer drawn below it: the primitives before it are drawn, its
compute passes run, and its own quad starts the next draw. Damaged regions are
cleared by the same shaders with blending disabled, in the same pass. When the
damage covers the viewport, the attachment's clear does it instead.

Things to know when you build UI:

- Clips and feather masks are shared. A primitive stores an index into a small
  table, so a masked container costs one entry however many elements it holds.
  A frame can use 4,096 distinct combinations.
- Images are bound through one texture array, so the UI can show 31 distinct
  images at once. An image the UI stops showing gives up its slot. Images past
  the limit are skipped and reported once in the log.
- One frame holds 131,072 primitives. A glyph is one primitive and a curve is a
  few per segment. Past the limit, the rest of the frame is skipped and
  reported once in the log.

### Curves

Curves are evaluated on the GPU. The CPU doesn't flatten, clip, or cache them:
it converts each segment to a cubic in pixels, picks how many pieces to draw it
in, and writes that many copies of the control points. The vertex shader cuts
piece `k` out of the cubic, fits the quadratic closest to it, and bounds it
with a box along its chord. The fragment shader finds the closest point on that
quadratic in closed form and shades by the exact distance. A line or a quadratic
is exact, and a cubic stays within 0.05 pixels.

The piece count grows with how far the curve bends and with zoom, so a straight
line is one piece at any length and a typical node-graph wire is six to eight.

Each pixel is shaded by exactly one piece of a segment, the one whose part of the
curve it is closest to, so translucent strokes have no seams. Path ends and
corners are round. Where two segments meet smoothly, neither draws a cap. At a
corner, the segment that starts there rounds it, and a translucent stroke is
blended twice where that cap overlaps the previous segment.

A curve's clip is tested per pixel because its quads aren't axis aligned.
Every other element is still trimmed on the CPU.

## Text rendering

Text is drawn from glyph outlines on the GPU with the
[Slug algorithm](https://github.com/EricLengyel/Slug) by Eric Lengyel. The text
system reads each glyph's quadratic curves from the font once, in em units that
don't depend on a font size. The render pass packs them into two storage
buffers: the curves, and bands that list the curves crossing each horizontal and
vertical slice of the glyph. Every visible glyph becomes one primitive, drawn in
painter order in the same draw as rectangles, curves, and images, and the
fragment shader computes each pixel's exact coverage from the few curves in its
bands.

Measurement and placement use the same size-independent advances, so layout and
drawing never disagree.

Consequences for application code:

- Text is sharp at every size. A zoom, a resize, or an animated font size
  rasterizes nothing and uploads nothing; glyph data is uploaded once per glyph,
  not once per glyph and size.
- Idle text costs no CPU work, and moving or restyling a label regenerates its
  primitives only.
- Horizontal positions stay fractional, so letter spacing is exact. Baselines
  snap to whole pixels, which keeps horizontal strokes crisp.
- Clipping trims glyph quads and the outline area they sample together, and
  feather masks apply in the shader exactly as they do for rectangles.
- Fonts with cubic outlines work too: cubic segments become quadratic curves
  within 1/4096 of an em when the glyph is first read.

The glyph buffers hold a few thousand glyphs. When they fill up, they're emptied
to hold only the glyphs of the current frame. This advances the glyph generation,
which invalidates prepared frames automatically. Glyphs that still don't fit are
skipped and reported once in the log.

### Switch to the glyph atlas renderer

The previous renderer is still in the engine. It rasterizes each character on
the CPU once per whole pixel size, packs the coverage into one atlas texture,
and draws pixel-aligned quads that sample it. Use it to compare output or
performance, or on hardware where per-pixel curve evaluation costs too much.

To switch, set `UI_TEXT_MODE` in `crates/byte-engine/src/ui/render_pass.rs` to
`UiTextMode::Atlas` and rebuild. Both renderers emit primitives for the same
shader and share the draw list, clipping, and damage rules, so nothing else
changes. The atlas is the first element of the image texture array.
