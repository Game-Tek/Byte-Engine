Read this page before you change the layout engine, `UiRenderPass`, or the
text system. It explains how every UI stage reuses its result while its inputs
repeat, how one draw covers the whole UI, and how text is drawn from outlines.
To build an interface with the module, follow
[Build a user interface](/docs/use/gui). Its depth order and limits are in the
[UI reference](/docs/reference/gui).

## Add a UI feature

When you add a UI feature, follow the existing route:

- build or update a primitive
- let layout evaluate geometry, clipping, and retained identity
- let `UiRenderPass` consume the render data

That path keeps UI code testable and avoids coupling application widgets directly to renderer resource ownership.

## Retention and invalidation

Unchanged UI must cost nothing beyond the draw calls themselves, so every stage
retains its result and reuses it while its inputs repeat. The contract is one
chain of revisions:

- The retained tree advances a revision whenever an element is added, removed,
  or changed through `update_container`, `update_text`, `update_curve`, and the
  other update methods. The engine compares the element before and after each
  edit, so an edit that writes the values it already has changes nothing, and
  re-declaring the same element path on a later frame doesn't count either.
- `Engine::evaluate` reuses the retained layout while the tree revision and the
  viewport size repeat. Input routing and task polling still run every frame.
- Visual transforms and container display sizes are visual edits. The tree
  lists the edited elements instead of advancing the placement revision, and
  `Engine::evaluate` recomputes only those subtrees' boxes from the retained
  placement, in `update_visual_subtree`. Each placed element keeps two boxes:
  the logical box, which flow placement, hit testing, geometry reads, and
  transform origins use, and the display box, which painting, descendant
  clipping, and damage use. Keep that split: the display size must never feed
  measurement, flow placement, or hits, or an animated size starts reflowing
  children and moving hit targets. `display_size_edits_reuse_flow_placement_and_match_fresh_scenes`
  guards it.
- `Engine::render` returns a reference to the render retained by the engine.
  It keeps the same `Render::revision` while the tree, its layout, and the
  viewport are unchanged, so clone it only when the revision moved.
- `Engine::render` also reports damage: `Render::damage` returns the previous
  revision and the layout-unit rectangles whose pixels differ from it, built
  from the same per-node revisions. A consumer holding pixels for that base
  revision redraws only inside those rectangles. Anyone else redraws everything.
  A viewport change reports no base, meaning everything changed.
- `UiRenderPass` keeps a persistent UI layer. Each frame it clears and redraws
  only the damaged pixel regions (plus every visible backdrop blur, which
  samples the scene rendered that frame), then presents the layer. Primitives,
  uploads, and glyph residency are rebuilt only for the elements touching that
  damage, and only when the adopted render revision, the viewport extent, the
  glyph generation, or the damaged regions change. A frame with no damage
  records only the presentation.
- The pass presents the layer in one of three ways, which `Presentation` picks
  once from where the pass sits in the sink's graph. Only the last writes a
  second full-screen image, which costs about as much as the display pass that
  reads it back, so the pass takes it only when it must:
  - Over a `main` it can blend onto, one triangle blends the premultiplied
    layer onto `main` in place with `layer-over.pipeline`, inside a scissor
    that holds everything the UI paints. The scene is neither copied nor
    written anew, and a UI that paints nothing records nothing.
    `RenderPassBuilder::draw_over_main` returns that `main`: an image in the
    layer's format, or, for a UI registered after the last pass that replaces
    `main`, the sink's final target, which the pass requests the pipeline
    for. A backdrop blur then resolves its backdrop from the final target.
  - On a sink without a scene pipeline, and not as the terminal pass, the layer
    is `main`. It clears to opaque black, so later passes read finished pixels,
    and a frame with no damage records nothing. A UI-only application
    allocates no scene color or depth.
  - Otherwise `composite.besl`, or `layer-composite.besl` without a scene,
    writes the scene under the layer into a replacement `main`. A pass over a
    scene-linear `main` presents this way, because that format holds too few
    bits for the UI's colors. So does the terminal pass of a sink with no
    `main`, which writes the final target over black.
- The scissor comes from `Render::painted`: the union of the footprints of
  every element that draws, which the layout engine keeps with the damage. A
  container without a layer, such as a root that only lays out its children,
  draws nothing and stays out of it. The pass adds the margin damage takes.
- A shadow's caster clears its footprint with the first primitive record, which
  stays transparent. A layer that is `main` clears its damage with an opaque
  record placed after the frame's records.

## Fit sizing and extent feedback

A fit axis makes a container's logical size depend on its descendants, which
breaks the rule every other sizing keeps: a box resolves from the space its
parent offers alone. Layout handles it with a content pass, and the engine
stops there. It reports the resolved size back to components and never animates
it, so motion stays in application code, next to the display size that carries
it.

### Content pass

`Measure` in `ui/layout/mod.rs` resolves sizes for one layout pass. A fit
container runs its flow over its children from a zero cursor before it's
placed, with 0 as the parent size on each fit axis. Its size on that axis is
the largest child offset plus the child's size, so trailing gaps don't count,
plus the padding on the far side; the offsets already include the near side,
since the flow starts past it. `inside_padding` gives the space within the
padding, which both passes hand the flow and the children.
Children with an absolute position or depth are skipped.

`on_fit_axes` decides what each child is offered: on a fit axis, the space the
fit container itself was offered, and on the other axis, its resolved size.
The content pass and `place` both call it, so a relative child measures the
same in both. Offering the child the fit size instead would make the child
depend on the size it decides.

The per-element measurement cache keys on the element's own revision, which
doesn't change when a descendant does, so fit containers skip it. Their sizes
live in `Measure::fits`, a frame-allocated vector indexed by element. Each fit
subtree is measured once per pass, however deeply fits nest. Any edit inside a
fit container already advances the placement revision, so the full replay that
remeasures it always runs.

### Content extent

`place` records each container's content extent in `LayoutElement::content`,
from the child offsets it already computes, so the flow never runs twice. It
applies the fit extent's rule against the resolved size: the far edge of each
flow child, from the container's position, plus the far padding. On a fit axis
it records the logical size instead: the content pass already sized that axis to
its children, and placement runs a centered flow there against a different
parent size, which would report an overflow that isn't there. Leaves record
their logical size. Transforms run
after placement and never touch the field, so a component that scrolls its
content with a transform never changes the extent it reads.

### Extent waits

The runtime publishes a `Published` record for each laid-out element: the
transformed `ElementGeometry` that reads return, and the `LayoutExtent`, the
logical and content sizes layout resolved before transforms. `ExtentChangeFuture`
compares that untransformed extent with the one the component last knew, so
neither a transform nor a display size edit completes it. The component's own
animation or scroll can't feed back into the wait that drives it.

Each task keeps `extent_waits` registrations, kept and dropped by the same
poll-numbering rules as frame and timer waits. After `build_layout` publishes
geometry, it calls `Runtime::wake_extent_changes`, which wakes the tasks whose
element's extent now differs. A layout that keeps the topology republishes only
the elements whose position, size, display size, or content extent changed, so
a child that grows inside a fixed-size container still reaches its waits. Those tasks
are polled in the same evaluation, after layout, so a component sees a new
extent before the next layout. An extent wait never asks for a tick on its own:
it wakes only when a layout that something else caused changes the extent.

### Rules a change must keep

- Fit is resolved only for container width and height. `Sizing::calculate`
  asserts on any other use, such as a display size, which resolves against the
  logical size and has nothing to fit.
- The content pass and placement offer each child the same space, inside the
  container's padding, and start its flow at the same place past the padding.
- Extent waits compare the untransformed logical size and content extent.
- The content extent comes from placement, never from transformed bounds, and
  leaves out the children that the fit extent leaves out.
- The engine holds no motion state for sizes. A resize animation is a display
  size, or an outer logical size, that a component writes through a run; see
  [Animations](#animations).

The fit tests in `ui/layout/mod.rs` and `extent_change_tests` in
`ui/layout/engine/futures.rs` guard these rules.

### Fill

A fill axis is the flexbox grow factor of 1: what a flow's other children
leave, shared equally. `Measure::fill_shares` works it out once per container,
before `place` or the content pass sizes the children. It finds the flow's main
axes by asking the flow where its cursor goes past a 1 by 1 child at the
origin, so `FlowFunction` needs no axis of its own and every flow, custom ones
included, gets one. Reading the main axis from the cursor this way is a
construction of this engine, not a published method. It then runs a probe pass
of the flow with every fill child at 0 on its filled axes, and divides what's
left of the parent size the flow sees among the fill children. `offer_share`
then offers each fill child its share as the available space, where
`Sizing::Fill` resolves as full, so the measurement cache keys on the share like
any other offered space.

A container whose children don't fill pays only for a scan of its children's
sizings. A probe measures each child twice per pass, at 0 and at its share,
and both land in the measurement cache.

- The content pass and `place` compute shares the same way, from the same
  parent size and offered space.
- Off a flow's main axis, and for children outside the flow, fill is full.
- A fill child of a fit axis gets nothing, since the flow sees 0 there.

The fill tests in `ui/layout/mod.rs` guard these rules.

### Optical centering

Centering a vector icon by its box looks wrong when the icon's ink isn't
balanced in that box: a play triangle looks pushed toward its point. Layout
passes each child's visual center to its parent's flow in `FlowInput`, and the
centering flows center that point instead of the box's middle. The flow stays a
plain function. A custom flow that centers can read `child_center` too, and
one that ignores it still works.

Layout never measures ink. A container carries an optional `visual_center`,
as fractions of its box, and `Measure::visual_center` reads it; every other
element reports the middle of its box. Vector images supply the point:
`draw_vector` in `ui/vector.rs` stacks the image's layers in one container and
sets that container's visual center from the image's optical shift. The shift
is measured once per image, when its SVG bakes or when `Vector::new` builds it
from layers, so a layout pass costs nothing extra for it.

The measurement lives in `resources/vector.rs` in resource-management, where
the SVG bake and the UI both call `optical_shift`:

1. Each layer's outline is flattened to polylines within 1/1024 of the
   layers' extent, and its fill rule is applied with i_overlay's polygon
   boolean operations, so overlaps, crossings, and either winding resolve into
   polygons that cover each point once.
2. The layers' polygons are unioned, so area two layers share counts once.
3. The area and its first moments come from the polygon form of Green's
   theorem, and the bounds from the polygons' points. The optical center lies
   halfway from the bounds' midpoint to the centroid.

The flattening, the boolean operations, and the moments are established
methods. Moving the midpoint of the bounds halfway to the centroid is a
judgment call: the pure centroid overcorrects shapes like a play triangle, and
designers commonly split the difference, but no published source fixes the
factor.

`PlacementInputs::Container` holds the visual center, so changing it replays
placement.

- Measure optical shifts where images are made, at bake time or in
  `Vector::new`, never during layout.
- Every built-in centering flow centers `child_center` on each axis it centers,
  through `centered` in `ui/flow.rs`.
- Elements without a visual center report the middle of their box, so their
  placement doesn't change.

The optical shift tests in `resources/vector.rs`, the visual center test in
`ui/layout/mod.rs`, and the centering tests in `ui/flow.rs` guard these rules.

## Animations

Motion belongs to the component that asks for it. An `Animation` in
`ui/animation.rs` holds every piece of motion state: the target, and one lane
state per number of the value, as its `Motion` keeps it. A component either
keeps the animation and plays it with a run, or hands it to the engine behind an
`AnimationHandle`. Either way, the state lives in one `Animation` that the
component's handle or run reaches, so nothing outlives the component that owns
it, and two animations never share hidden state.

### Lanes and motions

`Animatable` splits a value into lanes by index, and joins lanes back into a
value, so `Animation` keeps one `Motion::State` per lane in a `SmallVec` that
stays inline for up to four lanes. A motion moves one lane: `retarget` decides
what carries over when the target changes, which is the value and speed for a
spring and the value alone for a curve and a smoothing. Retargeting with an
unchanged target is a no-op, so a component can set its target every loop
without restarting a curve.

### Runs

`EvaluationContext::animate` returns an `Animate`, which is a builder and the
run's future at once, in `ui/layout/engine/futures.rs`. It holds the element's
id and a mutable borrow of the animation, never a borrow of the context, so a
run can wait in a `select!` beside other waits on the same element. Each poll:

1. On the first poll, it writes the start and the first frame through one
   `RetainedTree::update_element`, the same path `update_container` takes.
2. It waits with a `RenderFuture` it owns, so it keeps the frame wait's
   registration rules.
3. On each frame, it steps the animation by `Runtime::frame_time` and writes the
   frame. Once the animation settles, it writes the end in the same edit and
   completes.

A dropped run can't edit anything from its destructor. When it has an end
callback, it boxes it with the values it wrote last and sends it as
`UiCommand::Edit`, the channel dropped mounts send their removals through.
`UiPoll::apply_commands` applies those before every direct write, so the end of
an interrupted run lands before the start of the run that replaces it.

### Handles

A run advances only while its task polls it, so a loop that retargets an
animation would have to keep a run in every `select!`, rebuild it after each
retarget, and guard it so a settled run doesn't resolve at once and spin. A
handle moves that clock into the engine, as Flutter's `AnimationController` and
the Web Animations API do: the component decides where the animation goes, and
the engine ticks it.

`EvaluationContext::animation`, in `ui/layout/engine/animations.rs`, puts the
animation and its every-frame callback in a `Slot`, which `Runtime::animations`
owns as a boxed `dyn Tick` beside its tick count and waiting tasks. The handle
holds only the slot's id, so every handle method is a `direct` future that
downcasts the slot from the `UiPoll` its task's poll lends. The methods borrow
the handle shared, so a `select!` can wait on `moved()` or `settled()` while
another branch retargets. The handle's drop can't reach the runtime, so it
sends `UiCommand::RemoveAnimation`, which lands before the next tick.

1. `AnimationHandle::update` marks the slot changed when the change moved the
   target or the current value.
2. `tick_animations` runs in `Engine::evaluate` right after
   `Runtime::begin_frame`, before the frame's tasks are polled. It applies
   pending commands, then steps each slot that moves or changed by
   `Runtime::frame_time`, calls its callback with an `AnimationFrame` that edits
   the tree through `RetainedTree::update_element`, counts the tick, and wakes
   the tasks waiting on it.
3. `Moved` compares the slot's tick count with the count on its first poll;
   `Settled` checks that the slot neither moves nor changed. A pending one
   records its task on the slot, and the next tick wakes it. A task that
   stopped waiting is woken once for nothing.

`Runtime::needs_tick` asks for a frame while any slot moves or changed, so the
engine idles once every animation is at rest.

### Frame clock

`Runtime::begin_frame` takes the frame time from the engine's `FrameClock`. It
reads the wall clock until `Engine::advance_clock` is called, then counts only
what the host advanced. Runs read the frame time, so a test steps any frame of a
run; timers keep the wall clock.

### Rules a change must keep

- All motion state lives in `Animation`. The engine reaches a handle's animation
  only through the handle's slot, and never keeps it past the handle.
- A run's start and first frame land in one edit, and a settling frame and its
  end land in one edit.
- An interrupted run's end is applied before any later change.
- A run asks for frames only while it's pending, and a handle only while its
  animation moves or changed.
- Handles tick before the frame's tasks run, so a task woken by `moved()` reads
  where the animation stands this frame.
- `moved()` never resolves while the animation is at rest; `settled()` resolves
  at once when it is.

The tests in `ui/animation.rs` guard the motions and retargeting,
`animation_run_tests` in `ui/layout/engine/futures.rs` guards runs, interruption,
and the frame clock, and the tests in `ui/layout/engine/animations.rs` guard
handles.

## Reactive values

A component follows outside state through a `Reactive` in `ui/reactive.rs`: a
`Source` and the last value it handed out. `Reactive::next` asks the source to
write the newest value into that slot and resolve when it changed. A
`Subscriber` resolves on a watch version it hasn't seen and clones the value
into the slot with `clone_from`, so no lock is held while the component works.
`Polled` reads the application context and compares.

### Polled reads

A frame wait asks for ticks, so a component that rechecked state on every frame
kept the whole interface awake. A polled value instead registers a read wait,
`UiTask::read_wait`, that never counts in `Runtime::needs_tick`.

`UiPoll::written` records that the application context was lent mutably: by
`Engine::ctx_mut`, or by a `With` read. `poll_reads` in
`ui/layout/engine/runtime.rs` runs in `Engine::evaluate` after the first ready
tasks and before layout. While the context is written, it clears the flag,
wakes every task with a read wait, and polls the ready tasks; a task that
writes again starts another round, at most `READ_ROUNDS`. Changes it makes are
laid out in the same evaluation. `Engine::next_tick` asks for a tick only while
a write is left unread and a task waits on a read.

### Ticks a host can skip to

`Engine::next_tick` is complete, so a host such as the editor's `present` in
`editor.rs` evaluates only when it comes or the viewport resizes. Besides frame
waits, woken tasks, and unread writes, it's now in two more cases:

- `Engine::input` is set by every input method, such as
  `Engine::pointer_moved` when the position changed, and cleared at the
  start of `Engine::evaluate`.
- An unlaid edit: the tree's revision differs from the one the retained layout
  was built from. Event handlers run in the second `poll_ready_tasks`, after
  `build_layout`, so their edits would otherwise wait for an unrelated tick.

### Rules a change must keep

- A first wait resolves on its first poll, with no change needed.
- A read wait never asks for a tick by itself. Only an unread write does.
- Polled reads borrow the context shared and don't count as writes.
- Reads run before layout, so their changes don't wait a frame.
- Every input method sets `Engine::input`, and every tree change after layout
  leaves the next tick now, so a host that skips evaluations misses nothing.

`reactive_tests` in `ui/layout/engine/futures.rs` guards these rules, the tests
in `ui/watch.rs` guard watch versions, and the hint bar test in
`editor/shell/hint_bar.rs` guards that a hesitation waits on one timer.
`input_asks_for_a_tick_and_an_edit_made_for_it_for_one_more_to_lay_it_out` in
`ui/layout/engine.rs` guards input and unlaid edits, and
`the_editor_asks_for_frames_only_while_its_drawer_moves` in `editor/shell.rs`
guards that the editor goes idle.

## Pointer gestures

Pointer input reaches the engine through one path: `Engine::pointer_moved`,
`Engine::pointer_pressed`, `Engine::pointer_released`, and `Engine::cancel`, in
`ui/layout/engine.rs`. Every press that hits a surface is held by `Drag` in
`ui/drag.rs`, and the release decides what the press was, as a DOM `click`
follows `pointerdown` and `pointerup` on one element. A release short of the
drag threshold, over the held source, is a click, and a release past it drops the source. Hosts
feed one position action bound with `dragged_by`, so a click and a drag can't
disagree about where the press landed.

`Grabbed`, `Dropped`, and `DragEnded` go out from the call that caused them, so
a cancel or a resize before the next evaluation can't lose them. A click is
queued in `Engine::clicks` instead and becomes `Events::Actuated` as
`route_input_events` delivers hover, after layout. Delivered from the release,
it would reach a wait that its task abandoned since the last evaluation, since
a wait expires only when its task polls again, and a handler's edit would be
laid out before the frame the host measured the click against.

`Engine::find` hashes a key path through `slot_path`, the same function that
names elements when they're declared, and reads the geometry that every layout
publishes to `Runtime::geometry`. It walks no tree and allocates nothing.

### Rules a change must keep

- A press hit-tests the last evaluated frame and never waits for layout.
- A gesture that crossed the drag threshold never actuates, even when it returns.
- A click routes with hover and scrolls, after layout, never from the release.
- An id is a pure function of its key path, so `Engine::find` agrees with the
  tree without reading it.

`a_release_actuates_the_pressed_surface_only_when_it_lands_there_short_of_a_drag`,
`find_reaches_an_element_through_its_key_path_from_the_last_evaluated_frame`,
`dropping_an_event_wait_discards_events_until_the_next_wait`, and
`press_activates_after_the_threshold_and_release_yields_the_drop_once`, in
`ui/layout/engine.rs`, guard these rules.

## Collections

`EvaluationContext::each` and `each_by` in
`ui/layout/engine/evaluation_context.rs` start one task, `follow_collection`,
under a fixed slot of the element. Each item gets a component scope at
`slot_path` of the task's path and the item's key hash, so removing an item is
the existing scope removal, which ends its task and its elements together, and
its elements are children of the collection's element with no wrapper.

The task wakes on a `proactive` read of one hash over the keys in order, so a
write that leaves the keys alone costs a walk of the slice and no allocation.
On a change it removes the scopes of keys that left, ranks every item, and then
declares the new ones. The closures are `Clone` rather than shared: the
`proactive` read owns one copy of `items` and the key, each item's task owns a
copy of the component, and the change read borrows the task's own copies.

Order is the tree's job. `RetainedTree::ranks` maps an item's scope path to its
rank, and the children declared directly in a ranked scope keep rank order
among their parent's ranked children, in the slots those children already
hold, so the element's own children, such as a list's empty message, keep
their places. `set_ranks` reorders when ranks change, and `add_element` places
a new child by its rank. That matters because an item's elements are declared
later, when its task first runs, after the collection already ranked it. Scope
removal drops the ranks of removed scopes.

### Rules a change must keep

- A read of an unchanged collection allocates nothing.
- Ranks are set before new items are declared, so each lands in place.
- A kept item's component is never restarted, and a removed one's task and
  elements go together.
- Unranked children keep their slots when ranked ones reorder.

`each_keeps_one_component_per_item_in_list_order` and
`each_by_keeps_an_items_component_while_its_key_stays` in `ui/layout/engine.rs`
guard these rules.

## Focus

`Runtime::focus` in `ui/layout/engine/runtime.rs` holds at most one `Focus` per
layer: the element, and the absolute-depth container that starts its layer, or
`None` for the base layer. `RetainedTree::layer_of` finds that container among
the element's visual ancestors when a focus request is applied, so a request
needs no layout. `Runtime::focused` picks the entry whose layer container paints
highest in the last layout; the base layer ranks under every other.

A press never gives focus; it only takes it. `Engine::release_pressed_focus`
runs in `Engine::pointer_pressed`, against the last evaluated frame, and releases the focused element of the pressed layer
unless the press hit that element, an element inside it, or
`RetainedTree::holder_of` it, the nearest hit-testable ancestor, such as a text
field's well. A component learns that its
element lost focus through `FocusChangeFuture`, which registers
`UiTask::focus_wait`; every focus change wakes all such tasks, since focus
changes are rare and the woken future checks its own element.

### Rules a change must keep

- Each layer keeps its own focused element, and a press or request in one layer
  never changes another's.
- A press on nothing counts as a press on the base layer.
- A focus wait never asks for a tick by itself.

The focus tests in `ui/layout/engine.rs`, such as
`a_press_elsewhere_in_a_layer_takes_its_focus_and_a_press_on_the_holder_keeps_it`
and `a_press_on_another_layer_or_on_nothing_takes_only_that_layers_focus`, guard
these rules.

## Drawing

`UiRenderPass` draws the whole UI with one shader pair and no vertex or index
buffers. Every rectangle layer, glyph, image, backdrop blur, and curve piece is
one 64-byte primitive in a storage buffer, written in painter order: by depth,
then by element, across all element types. The vertex shader pulls six vertices
from each primitive, and the fragment shader branches on the primitive's kind.
A primitive is constant across its quad, so each branch is coherent, and a plain
square fill skips the corner, stroke, and mask math entirely.

### The primitive record

`UiPrimitive` in `ui/render_pass/data.rs` and `Primitive` in
`rendering/ui/layouts/ui.besl` are the same record. Every redrawn frame copies
each record to the GPU and every shaded pixel reads from it, so its size is a
cost on both sides. It takes 64 bytes, one cache line.

- Positions and the shape rectangle are single precision. A half float holds
  11 bits, which can't place a pixel on a screen thousands of pixels wide.
- Colors, corner radii, stroke widths, and the other per-kind values in `radii`
  and `sides` are half precision. The layer the UI draws to holds half floats,
  and a half resolves a radius under 512 pixels to a quarter pixel or better.
  Build them with `half` in `data.rs`.
- `header` packs the kind, the index into the mask table, and the index into
  the paint table. `data0` packs what a kind needs in integers: a rectangle's
  corner exponent, its rounded and stroked flags, and its edge fade's mask
  index; a sector's full turn flag; a curve piece's slice and caps. The helpers
  in `data.rs` (`shape_bits`, `curve_bits`, and the `UiPrimitive` accessors)
  pack them, and the decoders at the end of `layouts/ui.besl` read them.
- A gradient's axis and end color, and a material fill's placement, live in the
  frame's paint table, `UiPaintTable`, which a record names by index. A flat
  fill, the common case, names entry zero, and the shader never reads the table
  for it.
- A Slug outline's band scale and offset and its last bands live at the start
  of the outline's band data, which every glyph drawn from it shares, so a glyph
  record holds only the band data location.

The fragment stage reads a record's members where a kind needs them, and
`shade` resolves the paint after the coverage. A kind that brings its own
color, such as an image or a backdrop blur, never reads the paint table. The
mask table is a second read through an index, so `turned_edge_coverage` and
`mask_coverage` test the record first and follow the index only for a
primitive that has a mask.

Rules a change must keep:

- Declare the members in the same order in both files, and the paint table's
  entry too. The shader tests write records by member name, so they don't
  catch a reordered member; the `ui_primitive_` layout test in
  `ui/render_pass.rs` does.
- Keep the header's and `data0`'s bit layouts the same in `data.rs` and
  `layouts/ui.besl`, and keep the header's mask and paint widths wide enough
  for `MAX_UI_MASKS` and `MAX_UI_PAINTS`. Compile-time assertions in `data.rs`
  check the widths.
- Give a retained record its mask, fade, and paint indices each frame, after
  the surface cache returns it: the tables belong to one frame.
- Keep entry zero of the mask table as no clip, no mask, and no turn, and entry
  zero of the paint table as a flat paint. The shaders skip both tables for
  index zero.
- Don't narrow a position to half precision.

### What every primitive pays for

One fragment shader shades every kind, so its cost isn't only the work a kind
runs. The GPU gives each fragment thread room for the most values the shader
holds at once anywhere in it, and runs fewer threads when that peak grows. A
value computed early and held across a heavy call therefore slows every
primitive, including the kinds that never make that call.

On an Apple M4, with the whole screen redrawn every frame and the GPU kept
busy, the time of flat fills moved in steps as the fragment shader's structure
changed, with no change to what a fill runs:

| Change to the fragment shader | Flat fills |
| --- | --- |
| Resolve the paint before the coverage instead of after | 13 percent slower |
| Compute the clip and mask before `shade` instead of after | 15 percent slower |
| Measure an inset shadow's shape before its blur instead of after | 5 percent slower |
| Remove shadows, backdrop blurs, and sectors from the shader | 6 percent faster |
| Remove every kind but the rectangle | 13 percent faster |

The steps depend on the whole compiled shader, so they can't be read from the
source. Time a change instead of reasoning about it.

Rules a change must keep:

- In the fragment stage's `main`, call `shade` first and compute the clip,
  mask, and fade after it.
- In `shade`, resolve the paint after the coverage. Kinds that bring their own
  color return before it.
- In the shadow arm, measure an inset shadow's shape after the blur.
- After a change to `shading.besl` or the fragment stages, time flat fills and
  the kind you changed. A faster kind can make every other kind slower.

To time the UI pass on the GPU, redraw the whole screen every frame, stack
enough primitives that a frame takes longer than the tick, and compare the
`pass.ui` time of each frame from a per-tick `metrics-out` file. Below that
load the GPU lowers its clock when a frame gets lighter, so a faster shader
can read slower.

### Materials

A fill painted with a UI material draws with the material's own pipeline. It
isn't an arm of the ubershader: every arm raises the peak the GPU sizes every
fragment thread for, so one application's grid would slow every flat fill in
every application. A material pays only for itself, with one pipeline bind and
one draw per run of its records.

- **Bake.** A `.bema` material whose `domain` is `UI` bakes through
  `UiShaderGenerator` in `ui/material.rs`. The generator lowers the graph's
  `base_color` and `opacity` into a fragment entry point that first calls
  `material_coverage` from `rendering/ui/material.besl`. That function gives the
  same shape, clip, mask, fade, and turned edge as a plain fill, so a material
  only changes the color. The vertex stage is the ubershader's, through
  `ui-material.pipeline`, which lists no fragment stage. The render pass requests
  each material's shader into it with `request_pipeline_with_fragment`.
- **Record.** A material fill is a normal rectangle or sector record. Its paint
  table entry's axis, which a material doesn't use as a gradient, holds the
  pixels per element unit along x and y and where the element's entries start in
  `material_parameters`. The color's alpha holds the element's opacity.
- **Parameters.** Every value parameter, static or dynamic, takes one `vec4f`
  entry per element, in declaration order. An element can override any of them,
  and variants don't fork pipelines through specialization constants.
  `place_materials` writes the entries each rebuild.
- **Runs.** The prepared frame lists the records that don't draw with the still
  ubershader as sorted, disjoint ranges tagged `Moving` or `Material`, and
  `draw_runs` walks a draw in record order, switching pipelines between runs.
  Neighbouring records of one material share a run. A material record never
  joins a moving run, so materials draw without motion blur.
- **Loading.** `UiMaterialLoader` is a `LoadPipeline`, like the scene's
  material and particle loaders: its lane reads each material's layout on the
  loading thread, and its pipeline compiles through the pipeline manager. The
  application spawns one loader with its first UI pass, and every UI pass,
  editor windows included, shares it through `UiMaterials`, so a material is
  read once. Until the material is read and its pipeline compiled, its records
  rasterize nothing. Once every material the frame waited on settles, `needs_frame` drops
  the prepared frame and the layer, so a render-on-demand application redraws.

Rules a change must keep:

- Don't add per-material code to `shading.besl` or the ubershader's fragment
  stages.
- Keep `material_coverage` the same shape math as the ubershader's rectangle and
  sector arms, so a material fill and a plain fill of one element cover the same
  pixels.
- Keep the material ranges disjoint from the moving ones.
- Read the paint axis of a material record only as the material layout
  above.

`ui/material.rs` tests that the editor's grid graph lowers to a fragment shader
for the platform, and that a scene-only input or surface input fails with the UI
domain's message. `draws_split_into_still_and_moving_runs_in_record_order` in
`ui/render_pass.rs` checks the run walk.

### Corners and borders

A container's corners and its stroke sides are four values each. The render pass
turns the radii into pixels and fits them as CSS does, with `fitted_radii` in
`ui/components/container.rs`, then writes them into the primitive's `radii`
slot and the side widths into `sides`. Two flags in `data0` say whether any
corner is rounded and whether any side is stroked, so the shaders still skip
square corners and fills with one test.

`box_distance` in `shading.besl` is the one shape function for fills, strokes,
and clip masks. It picks the corner by the point's quadrant, and each corner has
a radius across and a radius down. Inside a corner it divides the superellipse
field, measured in units of those radii, by its gradient. That's exact for a
circle and a first-order distance for an ellipse or a superellipse, which is
what anti-aliasing needs. A corner with exponent 2, a circle or an ellipse,
takes two square roots and no power. A superellipse corner takes three powers:
its gradient reuses the powers the field took, divided by the point and by
their sum. A stroke covers the outer shape minus the inner one:
the box moved in by each side's width, with each corner's radii less the
adjacent widths, as CSS draws a border. A clipping container's mask uses the
same inner corners, from `inner_corners`, so children never cross the border.
Shadows integrate each row between that row's left and right reach, which the
top or bottom corners on each side decide.

Rules a change must keep:

- Radii are fitted once, on the CPU, so the shaders' clamps only guard bad input.
- A stroke's inner corners and a clipping container's mask agree, so children
  clip exactly to the border's inner edge.
- The rounded and stroked flags in `data0` stay true whenever any corner or
  side is, since the turned-edge and moving-fragment paths test them to skip
  work.

`ui_fragment_besl_vm_rounds_each_corner_by_its_own_radius`,
`ui_fragment_besl_vm_strokes_each_side_by_its_own_width`, and
`ui_fragment_besl_vm_shades_a_shadow_with_its_own_radius_per_corner` guard the
shaders, and
`descendants_clip_to_a_border_with_its_own_width_per_side_and_radius_per_corner`
guards the clip.

A frame is one draw per damaged region. Only a backdrop blur adds draws, because
it reads the layer drawn below it: the primitives before it are drawn, its
compute passes run, and its own quad starts the next draw. Damaged regions are
cleared by the same shaders with blending turned off, in the same pass. When the
damage covers the viewport, the attachment's clear does it instead.

### Backdrop blur

A backdrop blur is a separable Gaussian run in compute passes, in one of three
paths chosen by its standard deviation. Up to 4 pixels, it filters at full
resolution. From 6 pixels, it filters on a half-resolution lattice. Between the
two, it runs both and blends them in the ubershader. Each path filters along x,
then y, and each pass reads two taps per bilinear texture read.

The kernel reaches 4 standard deviations, the cut-off OpenCV's
`getGaussianKernel` uses for floating-point images, and is renormalized over what
it keeps. Its support is even, so every bilinear pair reads two weighted taps,
and it never passes 22 taps, which only the largest radius reaches. The filter
shader stops after the kernel's last pair, so a small blur reads less.

The first stage fills the region the filter reads. A shadow draws its caster
there. A backdrop blur resolves the scene and the layer drawn so far into a
full-resolution backdrop, which the half path then reduces onto its lattice
with the binomial `[1, 3, 3, 1] / 8` weights on each axis. Merging the resolve
and the reduction into one pass was measured slower on an Apple M4: its 32
loads per half-resolution texel cost more than the full-resolution write and
read it saves.

The blur images hold one blur at a time, not the screen. Every blur of a frame
takes its turn with them: its chain runs, and the draw right after it samples the
result before the next blur overwrites it. So the images grow to the largest
backdrop a frame resolves, in 64-pixel steps, and never shrink while the viewport
stays the same, so their allocation settles instead of following every blur. Each
blur gets a window: the screen pixel at the images' first texel. The window
starts on an even pixel, so the half-resolution lattice keeps its phase. Where a
blur reaches the viewport's far edge, its window ends the images on that edge,
and the images keep the viewport's parity so that edge is reachable. Sampling
past the edge then clamps to the edge texel exactly as on viewport-sized images.
The filter and reduction stages take their regions in image coordinates; the
resolve, the caster draw, and the ubershader take the window.

A blur runs again only when its result can change. Over a scene, every visible
blur runs each frame, because the renderer draws a new scene under it. Without
a scene, a blur reads only the layer, so it runs again only when the frame's
damage reaches the pixels it reads. It then damages its whole footprint, which
can reach another blur in turn. A UI whose only change is elsewhere keeps its
blurred pixels in the layer and skips the chain.

A change to the blur must keep these rules:

- Composite each source texel before weighing it. Averaging the scene and the
  layer apart, then compositing, changes translucent edges.
- Plan every dispatch region backward from the quad through the kernel's own
  support. `blur_backdrop_reads` returns what the first stages read, and
  `blur_read_margin` must cover it, because damage reaches that margin around
  every visible blur so that the layer it reads is drawn up to the blur in
  painter order. `blur_step` asserts this.
- Keep each blur's image reads inside the regions earlier stages wrote. The
  scratch images keep stale texels outside them.
- Damage a blur whenever anything it reads may differ from the frame that last
  ran it. A redraw that samples a blur that didn't run reads whatever the images
  last held: another frame, or another blur's window. `frame_damage` adds GPU
  image damage before blur damage for that reason.
- Size the blur images with `blur_image_extent` from every blur of the frame
  before placing any window with `blur_window`, which asserts that the images
  hold the blur.

`backdrop_blur_production_besl_chain_sweep_preserves_positive_filtering` runs
the production shaders across radii, display scales, and patterns.
`backdrop_blur_regional_production_chain_never_samples_stale_texels` fills
scratch images with NaN and checks that no stage reads one.
`backdrop_blur_production_chain_in_its_window_matches_viewport_sized_images`
runs the chain in a window at the far corner of an odd viewport and inside it,
against viewport-sized images.
`damage_a_blur_reads_redoes_it_and_every_blur_its_footprint_reaches` and
`blurs_without_a_scene_stay_clean_while_nothing_they_read_changes` guard when a
blur runs.

### Curves

Curves are evaluated on the GPU. The CPU doesn't flatten, clip, or cache them:
it converts each segment to a cubic in pixels, picks how many pieces to draw it
in, and writes that many copies of the control points. The vertex shader cuts
piece `k` out of the cubic, fits the quadratic closest to it, and bounds it
with a box along its chord. The fragment shader finds the closest point on that
quadratic in closed form and shades by the exact distance. A line or a quadratic
is exact, and a cubic stays within 0.05 pixels.

The piece count grows with how far the curve bends and with zoom, so a straight
line is one piece at any length and a typical node-graph wire is six to eight.

Each pixel is shaded by exactly one piece of a segment, the one whose part of the
curve it's closest to, so translucent strokes have no seams. Path ends and
corners are round. Where two segments meet smoothly, neither draws a cap. At a
corner, the segment that starts there rounds it, and a translucent stroke is
blended twice where that cap overlaps the previous segment.

A curve's clip is tested per pixel because its quads aren't axis aligned.
Every other element is still trimmed on the CPU.

### Motion blur

A moving element is blurred analytically, in the same draw as everything
else, by the primitive's own shader. The UI keeps no velocity buffer, no
per-layer images, and no history beyond what damage already keeps. Its rules
are in the [UI reference](/docs/reference/gui#motion-blur).

Motion comes from the difference between two renders, never from animation
state, so a drag, a scroll, and a run blur alike, and the engine still holds no
motion state.

1. The visual-edit path, `update_visual_subtree`, keeps each element's
   display box and turn from before its first edit since the last render in a
   `MovedBox`. The engine holds one per tree index, stamped with a render
   generation, so recording and lookup never search or sort, and advancing the
   generation forgets every record. A layout replay advances it too.
2. `Engine::build_render` reads the current record of each element. When the
   tree's placement revision is unchanged and the box, turn, clip, or mask
   differs from the previous render, it pushes a `RenderMotion` with the
   previous values and stores its index in `RenderPlacement::motion`. The
   render also carries the frame time evaluated since the previous render.
3. `Engine::moving` lists the moving elements with the area both places span,
   which is their damage. The next build revisits them even when nothing else
   changed and repairs that area, `Engine::next_tick` asks for that build, and
   `settle_motion` makes `Engine::render` rebuild once an evaluation ran, so a
   still element draws sharp.
4. `update_from_render` turns each motion into a `UiDrawMotion`: the affine
   map from a current unrotated point to where it was drawn, in the element's
   current unrotated frame, where its primitives are laid out. The draw entry's
   `DrawClipMask::motion` points at it.
5. `UiMaskTable::index` shapes the motion into a `UiMotionRecord` in pixels:
   the shutter's share of it, shortened so no corner travels past the maximum
   radius. The record is stored in the clip mask buffer as an entry of its own,
   so moving primitives need no other buffer, and the primitive's mask entry
   names it in `corner.z`.
6. `draw_runs` splits each draw into runs of still and moving primitives, in
   record order. Still runs bind `ui.pipeline`, whose fragment stage is the
   still path alone, so a still frame pays nothing for motion. Moving runs bind
   `ui-moving.pipeline`. Both fragment stages share the coverage and paint
   functions in `shading.besl`.
7. The vertex stage grows a moving quad, along its own axes, to hold where its
   corners were when the shutter opened. `ui-moving-fragment.besl` takes
   samples at the middle of equal shares of the shutter. Each sample warps the
   pixel back to where its point lies now with `motion_warp`, shades it with
   the ordinary `shade`, and tests the clip and mask with their edges moved.
   Square edges, which the rasterizer resolves for still primitives, are
   covered explicitly by `moving_edge_coverage`. A convex fill that a
   translation keeps covering the pixel at both ends of the shutter takes one
   sample, because every sample would agree.

The record splits the motion's linear part into its polar turn and what's left
beside it. A turn moves points along arcs about the motion's fixed point, which
is the exponential map of a rigid motion. The remaining linear change is
blended linearly, which is exact for translation and scaling. The sample count
is the farthest any point travels divided by the primitive's softness, so steps
stay under the width of an edge and no copies show.

#### Rules a change must keep

- Motion is measured only against a render of the same placement at the same
  size. A layout replay, a resize, and a first render draw still.
- A moving element is revisited by the next render, and that render is asked
  for, so no blur outlives its motion.
- Damage of a moving element is the area both places span, and the next render repairs
  the previous render's blur, never older places.
- A still primitive draws with the still pipeline, never with the moving one,
  so motion blur costs nothing where nothing moves.
- A backdrop blur's dispatch covers its swept quad, because its backdrop is
  sampled where the pixel is.
- Primitives fully outside their clip now are culled before motion is
  considered, so their trail isn't drawn.

`visual_edits_report_where_the_element_was_and_layout_replays_draw_still` and
`a_moving_render_asks_for_one_more_render_that_draws_still` in
`ui/layout/engine.rs` guard the engine's rules.
`ui_fragment_besl_vm_averages_a_moving_square_over_the_shutter` checks the shader
against a finely integrated shutter, and the `motion_records_` tests in
`ui/render_pass.rs` guard the records' shutter, radius, and turn.

## Text rendering

Text is drawn from glyph outlines on the GPU with the
[Slug algorithm](https://github.com/EricLengyel/Slug) by Eric Lengyel. The text
system reads each glyph's quadratic curves from the font once, in em units that
don't depend on a font size. The render pass packs them into two storage
buffers: the curves, and bands that list the curves crossing each horizontal and
vertical slice of the glyph. Every visible glyph becomes one primitive, drawn in
painter order in the same draw as rectangles, curves, and images, and the
fragment shader computes each pixel's exact coverage from the few curves in its
bands.

Measurement and placement use the same size-independent advances, so layout and
drawing never disagree.

A wrapping text breaks through `Lines` in `ui/font.rs`, which `measure`,
`place_outlines`, and `place_glyphs` all walk. The wrap width travels in
multiples of the font size, from `text_wrap` in layout to `RenderTextElement`
and `UiTextDrawElement`, and `Lines` compares it with the outline's em
advances. The breaks so don't depend on the size or the renderer a text is
drawn with: the atlas renderer rounds its raster size, and the outline renderer
scales by the inherited transform, and both break where layout measured. A
wrapping text takes the width offered to it, so the width its render element
carries is the width layout broke it to. The atlas renderer's cached runs
compare the wrap width too, since a resize can change the breaks of an
unchanged text.

`wrapping_breaks_greedily_at_spaces_like_explicit_newlines` in `ui/font.rs` and
`a_wrapping_text_takes_the_offered_width_and_grows_a_line_per_break` in
`ui/layout/engine.rs` guard that measuring and drawing break alike.

The glyph buffers hold a few thousand glyphs. When they fill up, they're emptied
to hold only the glyphs of the current frame. This advances the glyph generation,
which invalidates prepared frames automatically. Glyphs that still don't fit are
skipped and reported once in the log.

### Switch to the glyph atlas renderer

The previous renderer is still in the engine. It rasterizes each character on
the CPU once per whole pixel size, packs the coverage into one atlas texture,
and draws pixel-aligned quads that sample it. Use it to compare output or
performance, or on hardware where per-pixel curve evaluation costs too much.

To switch, set `UI_TEXT_MODE` in `crates/byte-engine/src/ui/render_pass.rs` to
`UiTextMode::Atlas` and rebuild. Both renderers emit primitives for the same
shader and share the draw list, clipping, and damage rules, so nothing else
changes. The atlas is the first element of the image texture array.
