Use this section when you work on the engine repository. For application
development, start with [Develop with Byte](/docs/use).

## Test your changes

Install and run the engine's default test harness from the workspace root:

```bash
cargo install cargo-nextest --version 0.9.140 --locked
cargo nextest run --workspace
```

Nextest does not run Rust documentation tests. If you add or change an example
in API documentation, run it separately:

```bash
cargo test --doc --workspace
```

The default Nextest profile skips the GHI rendering integration tests because
they need a local GPU. Run them explicitly when you change GHI rendering,
resource lifetime, or backend command behavior:

```bash
cargo nextest run --ignore-default-filter \
  -p byte-engine-ghi \
  --test rendering
```

This command runs the rendering tests for your operating system's active GHI
backend. Presentation and ray-tracing tests that are marked as ignored remain
skipped.

The loader tests need a GPU too. Run them when you change resource loading, and
read the [loading timeline](/docs/develop/rendering/loading) design first:

```bash
cargo nextest run --ignore-default-filter \
  -p byte-engine \
  --test loading
```

## Run benchmarks

Run all available benchmarks from the repository root:

```bash
cargo bench --workspace
```

To run one benchmark target, pass its name and any required features. For
example, run the audio graph benchmarks with:

```bash
cargo bench -p byte-engine --bench audio_graph
```

This Divan report compares callback-time evaluation for direct playback,
sample-rate conversion, custom processing, and pitch shifting. Graph setup,
sample loading, and buffer allocation happen before each measured loop.

To compare animation graph playback and inertialized transitions across
different skeleton sizes, run:

```bash
cargo bench -p byte-engine --bench animation_graph
```

This benchmark also prepares graphs, resident clips, and retained pose buffers
before each measured loop.

To check that one benchmark target builds and starts without collecting timing
data, pass `--test` to Divan. For example:

```bash
cargo bench -p byte-engine --bench animation_graph -- --test
```

## Measure performance

Every headed application serves its own timings while it runs, so you can
measure a change without a profiler attached. The inspector listens on
`http://localhost:6680` and keeps the last 1024 ticks.

Read a summary of the CPU time in every engine span and the GPU time of the
frame, each scene pipeline, and each render pass, in milliseconds:

```bash
curl -s 'http://localhost:6680/metrics?presented=true' | jq '.metrics[] | select(.kind == "gpu")'
```

`presented=true` drops ticks in which no window could reach the screen, such as
while the window is hidden behind another one. Those ticks render nothing and
would skew the numbers. Pass `since=<tick>` to compare the ticks after a change
with the ticks before it.

Read the ticks themselves, one JSON object per line, to see where a spike landed:

```bash
curl -s 'http://localhost:6680/metrics/frames?limit=120' | jq -c '{tick, dt, gpu: .gpu.frame, bloom: .gpu["pass.Bloom"]}'
```

Each row names the renderer `frame` it submitted, which is the same number a
screenshot of that frame reports, so you can pair a slow frame with its image.
GPU values arrive once the frame completes, so the newest rows have none yet.

To measure a run without polling, let the application close itself and write
the metrics on the way out:

```bash
cargo run -- --kill-after=600 --metrics-out=run.json
```

A path ending in `.ndjson` writes every retained tick instead of the summary.
The same spans stream to Tracy when the `tracy` Cargo feature is enabled.

## Measure code coverage

Install `cargo-llvm-cov`:

```bash
cargo install cargo-llvm-cov
```

Then generate an LCOV report:

```bash
cargo llvm-cov --lcov --output-path coverage/lcov.info
```

To view the report in Visual Studio Code, install the `markis.code-coverage`
extension.

## Write documentation

Use [ISO 24495-1 plain-language principles](https://www.iso.org/standard/78907.html)
for Rust comments and API documentation. Keep useful links between types, traits,
functions, methods, and modules even when a strict plain-language rewrite would
remove them. Developers use these links to navigate the API.

When an API participates in a larger workflow, include a short next-step hint
with a link to the type, method, or trait that a developer normally uses next.
Add these hints to modules, types, constructors, and transition methods where
they clarify the path through the engine. Skip trivial fields and accessors.

Use the [Microsoft Writing Style Guide](https://learn.microsoft.com/style-guide/)
for pages in `docs`. Address the reader directly, lead with their goal, use
familiar words, and make the next action clear.
