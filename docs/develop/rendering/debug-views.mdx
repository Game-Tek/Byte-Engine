Read this page before you add a debug view to a render pass or a scene pipeline, or before you change how the
renderer shows one. A debug view is a visualization a pass can write, such as world normals, roughness, a shadow
cascade index, or a motion vector, that the renderer shows next to or instead of the final image while someone asks
for it. Several views can be shown at once, from one pass or from several.

## Goals

- **A small pool of targets, owned by the renderer.** Passes never allocate images for debug output. The renderer
  keeps a capped pool of debug targets per sink and lends one slot to each shown view. When the pool is full, the
  renderer refuses the next view and says so; memory never grows with the number of views that exist.
- **A pass writes only the views that are shown.** Every other view costs the pass nothing on that frame. One pass
  can show several of its views in the same dispatch.
- **Selected at runtime, by name.** `render.debug.view.VisibilityPipelineManager.normals=true` through the inspector or startup
  parameters, with no rebuild and no rebake.
- **Gone from release bakes.** A project that leaves the feature out gets shaders without the branches, without the
  debug bindings, and a renderer with no pool and no present step.
- **Captured like any target.** Pool slots are named render targets, so the inspector's screenshot endpoint reads
  them with the existing `target=` selector.

## How it fits the renderer

The design reuses three things the renderer already has, so it adds no new mechanism to the frame:

| Existing mechanism | What it does for debug views |
|---|---|
| Named, sink-scoped render targets planned by node (`RenderTargets`) | Each pool slot is a named target, `Debug View 0` to `Debug View N-1`, written by the declaring nodes and read by one new node that presents them. |
| Runtime parameters through a [`ConfigurationPort`] (`render.pass.<name>`, `render.motion-blur.taps`) | `render.debug.view.<pass>.<view>` shows or hides one view; each is its own event, so `GET /configuration` reports which views are on and why one was refused. |
| Bake-time features that strip statements reading one member (`VisibilityFeatures::remove_left_out_code`) | A `debug-views` feature strips every statement that reads a member starting with `debug_view_`, and with it the descriptors only those statements use. |

The frame of a sink becomes:

```
Scene(0..n)  →  Pass(0..m)  →  Presentation  →  DebugView
```

`DebugView` is a renderer-owned node after everything else, including the copy that presents scene color when no
post-scene pass writes the swapchain. While views are shown it tiles their slots into the sink's swapchain, over
whatever the frame drew. While none is shown it records nothing and costs nothing.

The code lives in `rendering/debug_views.rs` (the handle, the registry, the catalog, and the configuration),
`render_passes/debug_view.rs` (the tiling pass), and `assets/rendering/debug-view/present.besl`.

## The Rust API

### Declaring views from a pass

A pass declares its views once, while it's built, through the builder it already gets its targets from:

```rust
pub struct DebugViews {
	/// Every slot of the sink's pool, in slot order, to bind as the `debug_view_targets` array.
	targets: SmallVec<[ghi::BaseImageHandle; MAX_DEBUG_TARGETS]>,
	/// The pass's shown views, one bit per view, and the slot of the first of them. Atomic, because render commands
	/// capture their pass.
	shown: Arc<AtomicU32>,
}

pub struct ShownDebugViews {
	/// The pool slot of the first shown view.
	pub first_slot: u32,
	/// One bit per view, set while it is shown, with the first view in the lowest bit.
	pub views: u8,
}

impl DebugViews {
	/// The pool, in slot order. Bind it where the shader declares `debug_view_targets`.
	pub fn targets(&self) -> &[ghi::BaseImageHandle];

	/// Which of the views in `views`, a range of the declared list, are shown this frame, and the slot the first of
	/// them writes. Write `first_slot` to the shader's `debug_view_first_slot` member and `views` to the byte that
	/// holds its `bool` members.
	pub fn shown(&self, views: Range<usize>) -> ShownDebugViews;
}

impl<'a> RenderPassBuilder<'a> {
	/// Declares the views this pass can show, at most eight, in the order the shader declares their `bool` members,
	/// and returns the pool they write into.
	///
	/// Each view is selectable as `render.debug.view.<pass name>.<view name>`. The renderer records this pass as a
	/// writer of every pool slot. When the project leaves debug views out, the result reports no view shown and the
	/// targets are placeholders nothing reads.
	pub fn debug_views(&mut self, views: &'static [&'static str]) -> DebugViews;
}
```

`shown` is one relaxed atomic read, so a pass calls it in `prepare` every frame and copies the result straight
into its parameters buffer or push constant. The builder doesn't know the pass's name while the pass is built, so
each instance gets its own cell and the renderer registers every instance's cell under [`RenderPass::name`], or
the scene pipeline manager's name, once the pass exists; a selection writes every cell of that name, so one
selection changes every window. One bit per view bounds a pass at 8 views, and the shaders' `count: 15` arrays
bound the pool at 15 slots; both are far above what one screen can show.

A pass whose views several shaders write gives each shader its own range. The visibility pipeline's material
evaluation writes views `0..6` and the GI resolve that lights the frame writes `6..8`, so each gets a first slot
that counts the shown views before its range.

A post-scene pass:

```rust
let views = render_pass_builder.debug_views(&["velocity", "blur-length"]);
let blur_pass = pipeline.bind(
	"motion-blur",
	&[
		simple_compute::Resource::image("scene_texture", source),
		simple_compute::Resource::image("result", output),
		simple_compute::Resource::buffer("parameters", parameters),
		simple_compute::Resource::image_array("debug_view_targets", views.targets()),
	],
);
// in prepare:
let shown = self.views.shown(0..2);
parameters.debug_view_first_slot = shown.first_slot;
parameters.debug_views = shown.views;
```

A scene pipeline declares its views in `create_sink` the same way, because it builds its sink through the same
[`RenderPassBuilder`]. The visibility pipeline's material evaluation declares normals, albedo, roughness,
metalness, and occlusion from one table, `MATERIAL_DEBUG_VIEWS`, that both the declared names and the generated
shader statements come from. Its views are selected under the manager's type name,
`VisibilityPipelineManager`.

### Selecting views

The renderer owns the registry and the pool assignment:

```rust
pub(crate) struct DebugViewRegistry {
	/// Every pass that declared views, with its shown views and the cells its instances read.
	passes: Vec<RegisteredPass>,
	/// Where the registry publishes its state for the inspector.
	catalog: Arc<DebugViewCatalog>,
}

impl DebugViewRegistry {
	/// Shows `view` of `pass` on every sink, or hides it and frees its slot.
	///
	/// `Ok(false)` when no pass of that name has registered yet, so the caller keeps the request. Refuses, with the
	/// reason, when the pass declares no such view, when every slot is taken, or when the build has no debug views.
	pub(crate) fn set_view(&mut self, pass: &str, view: &str, shown: bool) -> Result<bool, String>;

	/// One bit per pool slot, set while a view holds it.
	pub(crate) fn taken(&self) -> u32;
}
```

Shown views hold the first slots of the pool, packed in pass registration order and then in declaration order, so
a pass's shown views always hold consecutive slots, and a shader finds every one of its views from one first slot
and its `bool` members. The cost is that showing or hiding a view moves the slots of the views after it, so a view
can move to another cell of the grid and another `Debug View <slot>` target. The catalog always reports each view's
current slot. A free list would keep slots stable, but then a shader would need a slot number per view instead of
one bit.

`render.debug.view.<pass>.<view>` arrives on its own [`ConfigurationPort`], registered next to `render.pass.`.
Its value is `true` or `false`, and the port answers `Set` with the value or `NotSet` with the reason: an unknown
view of a known pass, no free debug target, or debug views left out of this build. A view of a pass that hasn't
registered yet stays `Pending`, like a `render.pass.` state does, so a startup parameter can name a pass that a
deferred sink creates later. Each view is its own parameter so a refused one leaves the others as they were.
Startup parameters queue through the same port, so `render.debug.view.VisibilityPipelineManager.normals=true` on
the command line shows the view from the first frame.

The pool size is `render.debug.targets`, a startup parameter from `1` to `15`, default `4`. It's read when the
renderer is created, so it doesn't change at runtime.

The inspector serves one read-only route, `GET /debug-views`, from a `DebugViewCatalog` the renderer publishes to
on every registration and selection: every declared view, its slot while shown, the pool size, and whether the
build has the feature, so a tool can offer a picker without guessing names. Selecting goes through the existing
`/configuration` route.

### The pool and its memory

The renderer creates the pool per sink on the first `debug_views` call for that sink, in `RenderTargets`:
`render.debug.targets` images in the sink's color format (`SCENE_COLOR_FORMAT`), with
`Storage | Image | TransferSource` uses, named `Debug View <slot>`. They're non-member targets, so they're sized
on their own, not placed with the sink's image group:

- A free slot is sized `1×1`. The renderer already resizes non-member targets every frame from
  `RenderTargets::get_images_for_sink`, so this adds a branch there and nothing else. An idle pool of four
  costs four tiny images.
- The frame a view takes a slot, that slot is resized to the sink extent. Views write it that frame; `DebugView`
  presents it that frame. The slot goes back to `1×1` the frame after the view is hidden.

Why not group members: a slot's lifetime would span from the first declaring node to `DebugView`, nearly the whole
frame, so it would never share memory with anything and would cost a full sink-sized image even when idle.

Descriptor sets that bind a slot follow it through resizes: the backend replaces a resized image's backing behind
its handle and re-encodes every set that binds it, as it does for persistent and history targets.

Slots hold the shown view's colors in display-ready form, `0..1`, and `DebugView` tiles them to the output without
any transform. A view that wants scene-linear data on screen maps it itself, so a normal view writes `n * 0.5 + 0.5`
and a depth view writes a curve, not raw reverse-Z.

### Presenting

`DebugView` is one compute pass, `debug-view/present.besl`, that reads the shown slots and writes the sink's
swapchain in a grid: one view fills the screen, two sit side by side, three or four take a 2×2 grid, five to nine a
3×3. Each cell averages the `side × side` block of slot texels that lands on each of its pixels, so a slot is
always written at full resolution and the tiling never changes what a pass does. The slot order is the grid order,
and shown views hold the first slots, so cell `i` reads slot `i`. The pass reads its parameters, the shown view
count and the grid side, from a dynamic buffer the renderer fills each frame.

## The shader side

### One descriptor name and one member per view

Every view-writing shader declares the pool itself, under one name, as an arrayed storage image in the set it
already has; a shared layout layer would be one more descriptor set for every pipeline that writes views:

```besl
debug_view_targets: descriptor<{ type: StorageImage, binding: 3, access: write, count: 15 }>;
```

An arrayed binding takes `count` flat slots, so it goes past every other binding of the shader and of the layers it
stacks on: `3..18` in motion blur, `1100..1115` in the material evaluation layer.

Each pass adds a `debug_view_first_slot: u32` member to the parameters struct or push constant it already has,
followed by one `bool` member per view it writes, named `debug_view_` and the view's name with `-` as `_`:

```besl
MotionBlurParameters: struct {
	// ...
	debug_view_first_slot: u32,
	debug_view_velocity: bool,
	debug_view_blur_length: bool,
}
```

BESL packs contiguous `bool` members into the bits of one byte, so up to eight views cost one byte; see
[Bool members](/docs/reference/besl/language#bool-members). The Rust mirror holds that byte as a `u8`, which is
`ShownDebugViews::views`, and explicit padding after it. The `debug_view_` prefix is the contract the bake-time
strip keys on. The Rust side binds the pool with
`simple_compute::Resource::image_array("debug_view_targets", views.targets())`, or element by element through
`SetBinder::image_element`, each element a `DescriptorWrite::image` with its array element. Only the slots the pool
has are bound; a pass never indexes past the shown views' slots, so the rest of the array stays unwritten.

The BESL VM indexes a storage-image array the way it indexes a sampled-texture array, so the VM tests of a pass
with views keep running its shader.

### Writing a view

Every write is behind a conditional that tests the view's `bool` member. Shown views write consecutive slots in
view order, so a view writes the first slot plus the number of shown views before it, which a running slot local
counts:

```besl
// The blur length view writes the slot after the velocity view's when both are shown.
let blur_length_slot: u32 = parameters.debug_view_first_slot;
if (parameters.debug_view_velocity) {
	blur_length_slot = blur_length_slot + 1;
}
if (parameters.debug_view_velocity) {
	write(
		debug_view_targets[parameters.debug_view_first_slot],
		pixel,
		vec4f(scaled_velocity.x * 0.5 + 0.5, scaled_velocity.y * 0.5 + 0.5, 0.5, 1.0)
	);
}
```

Two shown views of one pass write in the same dispatch; nothing runs twice.

The order is written on both sides on purpose, like specialization ids are. A test per hand-written pass asserts
the shader declares one `bool` member per view, consecutive and in the order the Rust list declares them: the pass's
BESL is already `include_str!`-ed into its tests. Generated shaders take both from one table instead.

Rules:

- **Read a `debug_view_` member in the condition, and only around writes to `debug_view_targets`.** The strip
  removes every statement that reads such a member, at any depth. A `let` that reads one goes too, with the
  statements after it that read its local, so a running slot local is safe; but a conditional that tests a local
  made from a member would lose the local and keep the conditional, so test the member itself.
- **A sum a view needs over a loop lives in an ungated `let` and is added to inside gated branches**, as the
  irradiance view does; a release bake keeps the dead local, which the platform compiler removes.
- **Keep the view's arithmetic inside the branch.** The branch is a runtime flag, so its code stays in the
  pipeline of a debug bake; see [Shader variants](/docs/develop/rendering/shader-variants) for why. Nothing
  outside the branch should exist for the view's sake.
- **Write the whole pixel of every shown view.** A slot is undefined where its view doesn't write.

Generated shaders, such as material evaluation, emit the same branches from the generator's suffix, so the
`VisibilityShaderGenerator` tests can assert a view is present in a debug bake and absent in a release one at the
generator's seam.

## Leaving it out of release

Debug views are a bake-time feature alongside GTAO, SSGI, and contact shadows:

- `VisibilityFeatures` gains `debug_views: bool`, read from `render.debug-views.enabled`. When the parameter is
  absent it defaults to `cfg!(debug_assertions)`, so a plain debug build has views and a plain release build does
  not, and a project's `config.json` can pin either.
- A left-out feature strips every statement reading a member that starts with `debug_view_` through the existing
  `remove_left_out_code` path, which runs for every engine shader in the common generator. The `debug_view_targets` descriptor is then
  unused and the backend drops it. `debug-view/present.besl` and its pipeline are excluded from the bake through
  `excludes`.
- The runtime reads the same features. With the feature off, `RenderPassBuilder::debug_views` creates no pool and
  no registry entry and returns a handle whose `shown` reports no view; the renderer creates no
  `DebugView` node; `render.debug.view.*` answers `NotSet` with the reason.

The Rust side keeps no `#[cfg]`: what remains in a release build is one atomic read per pass per frame and five
bytes the shader never reads. A Cargo feature can hide even that later, but it would be a second switch to keep
in step with the bake, for no measurable gain.

A mismatched pair, a debug bake with a release runtime or the reverse, is harmless: the shaders either carry
branches that never fire or the runtime selects a view that writes nothing and reports it as `Set`. The inspector's
`/debug-views` route reports the runtime's feature state so the mismatch is visible.

## What a change must keep true

- A pass writes a pool slot only on frames one of its views holds it; a pass with no view shown costs no extra
  dispatch, copy, or branch beyond the member reads.
- A free slot is `1×1`; a taken slot is sink-sized.
- The renderer refuses a view when no slot is free and leaves the shown ones untouched.
- `DebugView` records nothing when no view is shown and never runs before every post-scene pass.
- A release bake contains no conditional that reads a `debug_view_` member and no `debug_view_targets`
  descriptor.
- Shown views hold the first slots, so a pass's shown views hold consecutive slots in declaration order.
- The Rust view list and the shader's `bool` members agree, per pass.

## Tests that guard them

- `DebugViewRegistry`: shown views hold consecutive slots in every instance of their pass, a range of views starts
  after the shown views before it, and showing a view moves the views after it; a full pool refuses with the reason
  and changes nothing; an unknown name refuses with the known names.
- `RenderTargets`: a slot follows the sink extent only while taken; `DebugView` sorts after every `Pass` and
  before `Presentation`.
- Per hand-written pass: the shader declares one `bool` member per view, in the order the Rust list declares them.
- Generator seam: a bake with debug views reaches `debug_view_targets` from material evaluation and a bake without
  them doesn't, and the program still lowers to the platform shader language. `present.besl` lexes and, in the
  BESL VM, tiles two shown slots in slot order with black cells past the last view.
- The BESL VM writes through an indexed storage-image array.
- Configuration: `render.debug.view.<pass>.<view>` reports `Set` with the value and `NotSet` for an unknown view,
  a full pool, and a build without the feature.

## Alternatives considered

- **One descriptor per view instead of an array, rebound on selection.** Rewrites descriptor sets while frames are
  in flight and makes every pass carry as many bindings as it has views. The array keeps sets fixed after build.
- **A shared layout layer for the pool.** One file would declare the name once, but a layer is a descriptor set,
  and every pipeline that writes views would bind one more set. Declaring the pool by name in each shader costs
  nothing at run time.
- **Resizing slots in the tile instead of the blit.** Would make a pass's output depend on how many views are
  shown; passes shouldn't know about the grid.
- **One parameter holding a list of views.** One event for several outcomes; a refused entry would have no state
  of its own. One parameter per view fits the configuration port's `Set`/`NotSet` per event.
- **Generated view constants instead of members on both sides.** Only generated shaders can receive them;
  hand-written passes would still name members by hand. One rule for both is simpler, and the per-pass test catches
  drift.
- **A slot number per view.** Four bits per view, as the pool's first version packed them, keep each view in its
  slot while others come and go, but cost a pass a `u32` for eight views and each shader an unpack per view. One
  bit per view and one first slot cost five bytes and a running count.
- **Specialization constants instead of a runtime member.** One pipeline per shown set, recompiled on each
  selection, and a pipeline manager that would have to rebuild sets. The member reads are cheap and the strip
  removes them from release anyway.
- **A Cargo feature for the Rust side.** Covered above: a second switch for a `Cell` read.
