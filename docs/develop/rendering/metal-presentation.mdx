Read this page before you change how the Metal backend acquires or presents a
swapchain, or how the tick loop waits for the display. The display cadence is
specified under [tick time](/docs/reference/time#tick-time).

## Frames render into swapchain images

A Metal frame never renders into a drawable. Each frame sequence renders into
its own swapchain image, and presentation copies that image into a drawable
and presents it. That keeps the drawable out of the frame's recording, so the
frame doesn't need a drawable until the copy.

## The display link runs on the main thread

Every display-synced swapchain, which is every window someone can see, owns a
`DisplayLink` on the main thread's run loop. A display link calls back only
while its run loop turns, and the main thread turns its run loop only while
the tick waits for window events. So the link fires inside that wait. Its
delegate keeps the update in a one-update slot and posts the event that ends
the wait.

The tick waits for the display in `GraphicsApplication::wait_for_displays`. It
handles window events until `Renderer::displays_ready` reports that every
visible window has an update, then acquires. Acquisition takes the update,
keeps its drawable for the acquiring sequence, and reports the update's target
presentation time. `Frame::present` copies into that drawable and presents it
without waiting. The tick simulates to the time the display shows its frame,
at a lead of `preferredFrameLatency` refreshes, which is the frames in flight.
The layer keeps three drawables, so the link has one to hand out while one is
on screen and one is held for presentation.

## Why the wait handles events

The thread that waits for the display is also the thread that handles AppKit
events. `CAMetalLayer.nextDrawable` blocks for up to a second while the
display holds every drawable, which happens when another window covers this
one around the time a frame takes a drawable. While it blocks, the application
can't be brought back to the front. A visibility check before the call can't
prevent it: AppKit learns about the occlusion by handling an event, and the
window can be covered during the call.

Waiting inside the event call removes the problem instead of narrowing it. The
display can hold drawables back for as long as it likes; events still reach
the application, and a window that stops being visible during the wait stops
being waited for. After four frame periods, the tick's stall length, the tick
goes on, and a window still without an update skips the frame.

## The slot replaces, never queues

An update is a display opportunity, not work. The slot holds one update; a
newer one replaces and releases an update nobody took, which returns its
drawable to the layer. Keeping the older one would present late and report a
display time that's already past.

## Immediate swapchains

An immediate swapchain doesn't wait for a refresh, so it has no display link.
`Frame::present` takes its drawable with `nextDrawable` after it commits the
frame's commands, so the GPU renders while the CPU waits. Unattended runs bind
immediate swapchains for windows that are never shown, which a display link
would never fire for.

## Rules a change must keep

- Never wait for the display outside the window event wait on a display-synced
  swapchain. No call that can block on Core Animation, such as `nextDrawable`,
  runs between two event waits.
- Bind display-synced swapchains and record frames on the main thread. The
  link fires only on the main run loop, and binding panics elsewhere.
- Add the link to the run loop mode the event wait uses, the default mode.
- Present a drawable taken at acquisition from the same frame sequence that
  took it. A sequence that acquires again drops the drawable it didn't present.
- Take a link's drawable only at the swapchain's current extent. A drawable
  handed out before a resize is released and that frame skipped, since the copy
  needs both images at one extent.
- Report a target time only from a display-linked acquisition.
