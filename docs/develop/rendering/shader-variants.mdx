Read this page before you add an optional feature to a generated shader, such as
material evaluation, or before you branch on a flag inside one. It explains when
to leave code out while baking, when to select it with a specialization
constant, and how to do each.

## Why a branch that never runs still costs

The GPU compiler allocates registers, spills, and instruction cache space for
every path in a pipeline, including paths that no pixel takes. A runtime flag,
such as a push constant, keeps both sides of its branch in the pipeline.

For example, opaque material evaluation used to carry the transparent phase's
shadow-map filtering behind a push-constant flag. Moving that flag into a
specialization constant halved the opaque pipeline, from 8,664 to 4,320
instructions. Afterward, new transparent-only code no longer costs opaque
pixels anything.

## Choose how to gate a feature

| When a feature is | Gate it with | Decided |
|---|---|---|
| Never used by the program being baked | Conditional generation | While baking, in the `ProgramGenerator` |
| Part of the baked shader, but used only by some materials or phases | A specialization constant | When the loader requests the pipeline |
| Switched per frame, such as whether screen-space global illumination (SSGI) ran | A push constant or buffer value | While recording |

Prefer the earliest gate that still has the information it needs. Use a runtime
flag only for state that changes while the pipeline stays the same.

## Leave unused features out while baking

When the program alone shows that it never needs a feature, don't generate that
feature's code. The `ProgramGenerator` builds a material's program from its
[BEMX graph](/docs/reference/bemx), so it knows every value the graph reads
before it writes any code, and splices in only what the graph uses.

Material evaluation does this with `MaterialReconstructionFeatures`. While the
generator lowers the graph, its stage records each value the graph asks for: it
reconstructs UVs only when the graph samples a texture or reads texture
coordinates, and builds the tangent frame only when the graph writes a normal or
reads the tangent or bitangent. A material without textures never contains UV
interpolation.

A whole program can stay out the same way. The generator builds a material's
closest-hit shader only when surfel GI is built in, and lowers only the values a
ray's hit needs, its base color, metalness, and emission, so hit shaders never
carry normal maps or roughness.

Keep these rules:

- **Decide from the graph and its material, never from the scene.** One
  baked shader serves every material and variant that references it. Only leave
  code out when none of them can need it.
- **Splice whole statements or helpers.** Backends emit only the functions that
  `main` reaches, so a helper that no spliced statement calls disappears from
  the generated source too.
- **Test the decision at the generator's seam.** Assert that the generated
  program lexes and contains, or doesn't contain, the feature. Leave lowering to
  the backend tests.

## Select per-material features with specialization constants

When the baked shader must support a feature but only some materials use it,
declare a specialization constant and branch on it. The loader sets its value
for each material, and the platform compiler removes the unused side when it
creates the pipeline. One baked shader still serves every material.

The transparent phase works this way:

1. The generator declares the constant with an id reserved in
   `visibility/layout.rs`:

   ```rust
   Node::specialization("transparent", "bool", TRANSPARENT_SPECIALIZATION_ID)
   ```

2. The generated BESL branches on it like any other value:

   ```rust
   if (transparent) {
   	occlusion_factor = f16(sample_directional_shadow(/* … */));
   } else {
   	occlusion_factor = f16(fetch(sun_visibility, pixel_coordinates).x);
   }
   ```

3. The loader passes the value at the same id when it requests the pipeline:

   ```rust
   SpecializationMapEntry::new(TRANSPARENT_SPECIALIZATION_ID, matches!(alpha_mode, AlphaMode::Blend))
   ```

The pipeline manager compiles one pipeline per distinct shader and
specialization values, and reuses it for every material that requests the same
pair. Materials that share a pipeline also share an evaluation dispatch.
Closest-hit shaders follow the same rule inside surfel GI's one ray tracing
pipeline: each distinct shader and specialization values is one hit group, which
every material that requests the pair shares. See
[Surfel GI](/docs/develop/rendering/visibility/surfel-gi#hit-groups-keep-their-numbers).

Keep these rules:

- **Reserve every id in one place.** A scalar uses its id, and vector component
  `k` uses `id + k`. Give each specialization its own range next to the existing
  ones in `visibility/layout.rs`, so the generator and the loader can't
  disagree.
- **Keep the number of distinct values small.** Each distinct combination
  compiles its own pipeline and splits materials into separate dispatches. Use
  specialization constants for switches such as the phase. Pass values that vary
  per material, such as color factors, as material data instead.
- **Use only the types every backend supports:** `bool`, `u32`, `i32`, `f32`, and
  `f32` vectors.

Metal and Vulkan apply the values when they create the pipeline, Metal as
function constants and Vulkan as specialization constants. DX12 has no
specialization constants, so its bake compiles every set of values ahead of
time; see the next section.

## Specialize shaders on DX12

Direct3D 12 has no specialization constants, and a baked shader reaches it as
DXIL, not HLSL, so it can't recompile with the values a pipeline asks for. A
bake for Windows compiles one DXIL variant of each specialized shader for every
set of values the material variants in the store give it, and the DX12 backend
picks the variant whose values match the pipeline's. The
[resource store](/docs/reference/resource-store#shader-variants) specifies what
is stored, and the [GHI](/docs/reference/ghi#specialization) specifies how a
variant is picked.

The path works in four steps:

1. `ProgramGenerator::specializations` lists the constants a material variant
   gives each shader stage. `VisibilityShaderGenerator` answers with
   `material_specializations`: the phase and the static values for material
   evaluation, and the static values for the closest-hit shader.
2. On Windows only, `shader_variants_resources` names the assembled resource
   `byte_engine/shader-variants.variants`, which a full bake bakes after every
   material. Its bake reads every `Variant` in the store, gathers the distinct
   sets of constants per shader, generates each shader's program again from its
   material's stored program, and compiles it once per set, with a
   `#define SPEC_CONSTANT_<id>` line for each value ahead of the HLSL. The
   variants go through the bake's shader compiler, so they get the same DXC
   flags as the shader itself.
3. The pipeline manager reads a shader's variants only when its artifact is
   DXIL, and passes them with the shader in `Sources::DXIL`.
4. The DX12 backend runs the shader's own DXIL for an empty specialization map,
   and the variant with an equal map otherwise. A map no variant matches
   panics, naming the shader and the map.

Keep these rules:

- **Compute the constants in one function.** The loader specializes pipelines
  with `material_specializations`, and the bake compiles variants from the
  same function through the generator, so the two maps are equal by
  construction. A constant the loader adds anywhere else has no DXIL variant.
- **Keep the path DXIL-only.** Metal and Vulkan specialize natively. The
  variants resource is assembled only where shaders compile to DXIL, its bake
  fails on any other platform, and only a DXIL shader reads variants.
- **Keep the number of distinct values small.** On DX12 each distinct set is a
  DXC compile while baking and DXIL in the store, on top of the pipeline it
  costs on every backend.

When a DX12 run stops with a missing variant, the store was baked before the
material values it now uses, or without the variants resource. Bake it again
with `beld bake --force`.

`material_specializations_hold_the_phase_and_the_static_values` guards the
constants, `shader_variants_gather_one_set_per_distinct_set_of_values` guards
the gathering, and the DX12 backend's
`specialized_shaders_run_the_dxil_variant_of_their_constants` and
`specialized_shaders_without_a_matching_variant_panic` guard the selection.

## Check the result

A gate only helps if the compiler removed the code. Before you measure
frame time, compare the compiled statistics of the affected pipeline, such as
instruction count, register count, and spilled bytes, before and after the
change. Then compare GPU time for the affected stage with the change and
without it.

Fewer instructions don't always mean a faster frame. Code that never runs mostly
costs registers and compile time. The gain is that the excluded path no longer
taxes pipelines that don't use it.

See [Compilation and reflection](/docs/develop/besl/compilation) for the BESL
side of specialization values.
