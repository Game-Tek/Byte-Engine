Read this page before you change how the renderer creates sinks or scenes,
records a frame's nodes, or presents. The behavior an application sees is
specified under [render images](/docs/reference/rendering#render-images),
[scenes](/docs/reference/rendering#scenes), and
[windows](/docs/reference/rendering#windows).

## One sink, two ends

A sink is everything the renderer keeps to draw one view: its camera, its scene
pipeline state, its post-scene passes, and its render targets. Only where its
graph ends differs. `Renderer` keeps one `SinkTarget` per sink, either a window
with its swapchain or a render image with its image and extent, and every other
part of the sink is shared code.

The graph never asks which end it has. `RenderPassBuilder` holds the sink's
final target as a `MainRenderTarget`. `create_main_render_target` hands it to
the terminal pass, and `draw_over_main` to the overlays after it. The
presentation copy and the debug view tiling take the same target. A render image is `BGRAu8` with a swapchain's uses,
so a pass that can end a window's graph can end a render image's without
change.

## The `main` chain

Every post-scene pass reads `main`, and most write a new image that takes the
name. The handles are written into descriptor sets when the sink is built, so
the chain can't be rewired per frame. Two rules keep that from costing a copy
of the frame. Both are specified under
[pipelines and passes](/docs/reference/rendering#pipelines-and-passes).

**The final target goes to the last pass that replaces `main`.** `main_places`
gives every post-scene node a `MainPlace`: `Before`, `Terminal`, or `Over`. A
feature that answers `RenderFeature::draws_over` is an overlay, and the
overlays after the terminal pass are built with `main` as the final target, so
a UI blends onto the swapchain inside a scissor instead of compositing the
whole frame into it. When every pass is an overlay, the presentation copy fills
the final target first. A sink with neither a scene nor a pass that replaces
`main` has nothing to draw over, so its last overlay is terminal and starts
the picture itself. Overlays record as `RenderNode::Over`, after the
presentation copy.

**A pass that records nothing leaves `main` unchanged.** The pass returns
`None` and does nothing else; bypassed, idle, pending, and failed passes are
alike. The renderer makes the passes after it read the `main` before it, one
of two ways, chosen once when the pass is built:

| Way | When | Cost in an idle frame |
| --- | --- | --- |
| The replacement is placed as the incoming `main`'s image | `RenderTargets::forward_main` accepts: both are group members of one sink with the same format, extent, and divisor, the incoming `main` has every use of the replacement, and the device answers `supports_image_aliases` | None |
| `ImageBypassPass` copies the incoming `main` into the replacement | Otherwise: the replacement is the final target, changes format or extent, or the backend has no aliases | One copy |

For the first way, `RenderTargets::plan` takes the nodes that prepared no
command. It sets `ImageGroupMember::alias_of` on each idle replacement, naming
the nearest `main` before it whose node records, and extends that `main`'s
lifetime to the replacement's last use. The GHI gives the replacement's handle
the other member's texture and rewrites the descriptors that name it, as it
does on a resize. The two handles name one texture, never two textures
over the same memory, so no contents carry over between textures. This is why
targets are placed after every pass prepares.

The placement changes only when the set of idle nodes changes, and then the
sink's group is placed again, as on a resize. That suits a pass a setting
keeps idle. A pass that records every other frame would place the
group every frame.

A node's own target that no later node uses is no longer cleared when the node
records nothing, since nothing reads it. A bypassed pass used to record its
copy, which discarded such targets; without the copy they would be cleared
every frame.

## Frames

A window takes part in a frame only after its swapchain image is acquired,
which `SinkFrame::Acquired` records with the image's extent. A render image
needs no acquisition: the acquisition step records `SinkFrame::Image`, and
`prepare` takes the extent from the render image itself. That way, an extent
change that arrives after the tick acquired still applies to that frame. The
frame resizes the image like the sink's own render targets.

Pacing and presentation stay window-only. Only acquired windows give present
keys, and `presents_this_frame` counts only them, so a frame that only draws
render images paces like a frame whose windows are all hidden.

## Recording order

Every sink's scene pipelines record before any post-scene pass. The post-scene
passes then record sink by sink: every render image first, then every window.
Each sink records its passes, its presentation copy, its overlays over the
final target, and its debug view tiling before the next sink starts. A window's pass that samples a render image
therefore reads the picture of the same frame, and the command buffer's access
tracking orders the read after the write.

Scene pipelines receive their sinks in creation order instead, as
[Scenes](#scenes) explains.

## Scenes

A scene is a message scope and the scene pipelines installed for it. The
renderer numbers scenes with `SceneId`, the world first, and keeps each
scene's sun and fog apart. Every pipeline manager draws one scene: the
renderer builds a manager's per-sink state only for its scene's sinks, and
`prepare` hands it only those sinks. A window always shows the world, and a
render image shows the scene it names.

Managers stay single-scene instead of keeping state per scene, because the
visibility pipeline does its frame-wide work, such as detail levels, shadow
views, and exposure, for the first sink it gets. Before the managers prepare,
the renderer sorts the frame's sinks by scene, keeping creation order within
each scene, so each manager gets a contiguous run whose first sink is its
scene's first sink. A second instance of a pipeline keeps all its GPU state
twice, so a preview scene with the visibility pipeline costs as much memory as
the world's.

One `ShownTransforms` follows every scene's scope. Handles are unique across
scopes, so one timeline per handle serves every scene, and a manager ignores
the handles it doesn't draw.

## Rules a change must keep

- Never branch on the final target's variant inside a pass. Take the format from
  `MainRenderTarget::format`.
- Never forward `main` from a pass. Return `None` and let the renderer keep it.
- Fill the final target completely before any overlay records: the terminal
  pass, its forwarding copy, or the presentation copy does.
- Read an earlier `main` only through the name `main`. While the pass between
  is idle, an earlier `main` read by its own name is also the image later
  overlays draw onto.
- Place a sink's targets after its passes prepare, since the plan needs the
  idle nodes.
- Keep Vulkan and DX12 answering `false` to `supports_image_aliases` until
  their image state tracking follows an alias to the image it names.
- Keep render images recording before windows.
- Never present or pace on a render image.
- Keep removed sinks as `None`, so the other sinks keep their ids.
- Hand a scene pipeline only its own scene's sinks, in creation order.

## Tests

`crates/byte-engine/tests/render_image.rs` creates a render image through the
application, ends its graph with a pass that fills the final target with one
color, and reads the image back after a frame and after a resize. It needs a
GPU, so run it with
`cargo nextest run -p byte-engine --test render_image --ignore-default-filter`.
The same binary checks that each scene pipeline builds state for and prepares
only its own scene's render images, and that a scene's sun reaches only its
own sinks.

| Test | Guards |
| --- | --- |
| `overlays_after_the_last_replacement_draw_over_the_final_target` | Which node is terminal and which overlays draw over the final target. |
| `an_idle_nodes_replacement_is_placed_as_the_main_it_replaces` | The alias, the extended lifetime, and the dropped first use, for one and for two idle passes. |
| `a_replacement_in_another_format_does_not_forward_main` | A replacement built unlike its source falls back to the copy. |
| `a_target_only_its_own_node_uses_needs_no_clear` | An idle node's private target isn't cleared. |
| `image_group_member_placed_as_another_reads_its_image` (GHI, GPU) | An aliased member reads the other member's image, and gets its own back, across frames in flight. |
| `painted_rectangle_covers_only_the_elements_that_draw` | The rectangle the UI's blend is limited to. |
