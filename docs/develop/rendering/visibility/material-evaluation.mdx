Read this page before you change material evaluation, the shaders the
visibility generator builds for it, or how a bake assembles the uber shaders.
What each mode accepts and draws is specified under
[materials](/docs/reference/rendering#materials) in the rendering reference,
and how a project picks a mode is in
[Choose how materials are evaluated](/docs/use/resources/bake#choose-how-materials-are-evaluated).

## Two dispatch shapes, one surface

Both modes shade a pixel with the same statements. `shader_generator/ast.rs`
splits material evaluation into pieces, and each mode takes the pieces it needs:

- **Pipelines.** The pixel-list source reads the pixel from the list the
  material prepasses wrote for the material's evaluation slot. The material
  compiles its own shader, and each set of static values specializes it. Each
  slot runs one indirect dispatch.
- **Uber.** The tile source reads the pixel from the thread's position in an
  8 × 8 workgroup and the material from the pixel's instance. One shader per
  phase holds a `match` with one arm per material, and one dispatch covers the
  sink.

The surface prefix, the texture coordinates and tangent frame, and the lighting
suffix are shared. An arm holds the material's surface body and normal, and
its static values as `let` literals. An arm's code is therefore what a
specialized pipeline constant-folds, and an A/B of the modes compares dispatch
shapes, not code.

## The bake assembles the uber shaders

In the uber mode, the visibility generator returns no evaluation program for a
material. The material handler then stores the material's `MaterialProgram`, its
BEMX graph and parameter declarations, in place of a compiled shader.
`identity` hashes both, which is everything the generated code depends on
besides static values.

The uber shaders are resources with no asset behind them. Their IDs are
`UBER_MATERIAL_SHADERS` in `visibility/features.rs`. The material handler bakes
an ID that ends in `.uber` without reading a source file:

1. It lists every `Variant` in the store and bakes each one as a dependency.
2. It asks the generator for each variant's arm key in that phase's shader. The
   generator leaves out other render models and the other phase.
3. It keeps one material per key, and the generator builds the program with one
   arm per key, in key order.
4. It stores the compiled shader under an ID derived from its platform source,
   and an `AssembledShader` with the shader's ID and the sorted keys.

What a shader gathers isn't one of its sources, so a freshness check can't see
the set of materials change. BELD therefore bakes
`VisibilityFeatures::assembled_resources` after every other ID, every time. A
development build bakes materials on first request, so the manager rebakes a
phase's shader through `ResourceManager::rebake` when a ready material's arm is
missing. Only one rebake per phase runs at a time, and the shader's arrival
checks the materials again.

## Arm keys

`uber_arm_key` in `visibility/shader_generator.rs` hashes the program identity,
the components of the variant's static values, and the phase with the 64-bit
Fowler-Noll-Vo hash, and folds the hash to 32 bits. It never returns `u32::MAX`, which marks a material
that nothing evaluates. The bake writes the keys into the shader, and the loader
writes each material's key into the `material_evaluations` table. Keys depend on
the material only, not on which bake revision is published, so only coverage
changes when a rebake lands.

## The tile pass

Each workgroup covers one 8 × 8 tile, and each thread one pixel. Before any
thread shades, threads 0 to 35 copy the tile's 6 × 6 window of half-resolution
texels into workgroup memory: depth pyramid mip 0, SSGI normals, and SSGI
history. Then every thread waits at one `workgroup_barrier`.
The uber shaders' scope declares its own
`sample_screen_space_indirect_diffuse`, which keeps the arithmetic of the
per-material one but reads its 12 taps from that window, so both modes share
the lighting suffix. The window origin is the first tap of the tile's first pixel, so every
tap of every pixel in the tile lands inside it.

The opaque pass writes zero to the lit target and the diffuse radiance history
where no surface was drawn, as pixel mapping does in the pipelines mode. It
therefore runs on every frame, even with no opaque instance. The transparent
pass returns early for a pixel whose key isn't one of its arms, because the
instance target still holds the opaque layer where no blended surface was
drawn.

## Rules a change must keep

- **Change the shared pieces.** Both modes build from the same statement
  sources in `ast.rs`. Change a piece, never a copy of it.
- **Compute keys in one place.** The bake and the loader both call
  `uber_arm_key`. They read static values with `VariantModel::static_values`
  and `Variant::static_values`, which list the same values in the same order.
- **Fail on a collision.** Two materials with different programs or static
  values that share a key would run each other's code, so the bake fails
  instead.
- **Keep the barrier unconditional.** No thread returns before
  `workgroup_barrier`, including threads outside the image.
- **Keep every tap in the window.** A change to the upsample's footprint must
  change the window's size and origin with it.
- **Draw only covered materials.** A material in the uber mode stays unavailable
  until its phase's shader holds its arm, so no instance is admitted against a
  shader that can't shade it.

## Tests that guard it

- The visibility generator tests check that the tile upsample returns what the
  global upsample returns at even and odd extents, that an uber program links
  and lowers to the platform shader language in both phases, with arms and
  without any, and that arm keys follow program, values, and phase.
- The material handler tests check that an assembled shader holds one arm per
  distinct material and grows when a material is added, that colliding keys
  fail the bake, and that a stored and a solved variant list the same static
  values.
- The features tests check that each mode keeps its own engine assets and names
  its assembled resources, and that an unknown mode is rejected.
