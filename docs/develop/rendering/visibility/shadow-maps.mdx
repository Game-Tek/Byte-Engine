Read this page before you change which lights get shadow maps, how large those
maps are, or how often they're drawn. What an application can rely on is
specified under [shadow maps](/docs/reference/rendering#shadow-maps) in the
visibility pipeline reference. Directional lights can instead cast shadows
through [virtual shadow maps](/docs/develop/rendering/visibility/virtual-shadow-maps),
which reuse this page's sun slots, penumbra filter, and small-caster cull.

## Shadow maps share a budget

Each selected point light renders six 90-degree views into a cube map of 16-bit
depth faces, and each selected cone light renders one perspective view into a
16-bit depth map. Every shadow map comes out of one budget,
`render.shadow-maps.budget-mb`, 128 MiB by default: the sun's four cascades
cost 32 MiB at 2,048 texels per side, and a cone or point light costs what its
size class costs. The [shadow map reference](/docs/reference/rendering#shadow-maps) lists the
classes and their costs.

Selection runs with the first sink each frame. The first directional light is
placed first, then cone and point lights ranked by their projected sink pixel
coverage, then the remaining directional lights. A light that doesn't fit stays
lit without shadows and warns once. The layout is kept across frames while it
still fits, so lights don't flicker between shadowed and unshadowed as the
ranking shifts. After an IES profile reaches the GPU, its dimmed calibrated
peak candela feeds the same ranking and the automatic shadow coverage.

## Local shadow maps come in size classes

A cone or point light's map is only as large as the light looks. Selection
projects each light's shadow range into every sink, keeps the largest diameter,
and picks the power-of-two size class from 128 to 2,048 texels per side that
gives about one texel per pixel. Powers of two keep a light's size from
changing every frame, and the selection keeps each light's previous class, so a
light shrinks only once it needs well under a smaller class. Without that
margin, a light whose span hovers at a power of two would reallocate its map
every frame.

Each class has its own cone image and its own point image. Material evaluation
binds them as the `cone_shadow_maps` and `point_shadow_maps` descriptor arrays
and indexes them with the light's `shadow_size_class`. A light's `shadow_layer`
is its layer within its class's image. Selection orders cone and point lights by
class and then layer, so consecutive layers of a class have consecutive views.

A change to the size classes must keep:

- The class count and the smallest class's 128 texels, which `material-evaluation.besl`
  and the point-shadow call in material evaluation spell out. A build guard in
  `shader_generator.rs` fails when they drift.
- Views in class and layer order, which the shadow pass relies on to draw a run
  of layers in one pass.
- The point-shadow filter's tap radius and face-edge margin scaled by the face
  resolution, so every class filters across the same number of texels. The
  shader generator tests check that face-coordinate and general taps agree at
  every class.

## Shadow maps update on a budget

A map isn't drawn again every frame. The
[shadow map updates](/docs/reference/rendering#shadow-map-updates) rules decide
which maps draw, and three pieces carry them out:

- **Slots.** `select_shadow_lights` takes last frame's `ShadowSlots` and keeps
  each light at its layer while it stays in its class; a new map takes the
  lowest free layer. Layers pack from zero only when the gaps would push the
  images past the memory budget. A map's contents survive only while its layer
  does, so anything that moves a light to another layer must start it over.
- **States.** `ShadowMapStates` in `shadow_updates.rs` keeps, for every map,
  the view it was drawn with and its age, and `schedule_updates` picks the maps
  that fit the texel budget. The manager updates a copy each frame and keeps it
  only once the first sink records the frame-wide work, so a frame that waits
  on a compiling pipeline doesn't mark maps drawn that never drew.
- **Views.** Every map that doesn't draw is sampled with the view it was drawn
  with. The CPU writes those views for cone and point maps, and for cascades
  under frustum fitting. Under receivers fitting the cascade fit pass does it on
  the GPU: it fits only the cascades in the update mask, stores their fitted
  views in its persistent `drawn_views` buffer, and copies the stored view back
  for every other cascade. A cascade with no drawn map gets a projection that
  puts every receiver outside it, so sun visibility falls back to a coarser
  cascade.

The shadow pass groups the frame's draws into runs of consecutive layers with
consecutive views and draws each run in one layered render pass with
`AttachmentInformation::layers(first_layer, layer_count)`. Only those layers
are cleared, which is what keeps the other maps, and a task workgroup still
culls each meshlet against up to six views of a run at once. Each backend
starts the range at `first_layer`: Metal through a 2D array texture view of the
range, Vulkan through a view that starts at that layer, and DX12 through a
render-target or depth-stencil view of the range.

A change to the updates must keep:

- Cascades 0 and 1 of every sun drawing every frame, ahead of the budget.
- A map's drawn view and its layer moving together: a map sampled with a view
  other than the one it was drawn with shows shadows in the wrong place.
- Only the drawn layers cleared in a run's render pass.
- The cascade fit's masks and `drawn_views` in step with the CPU's states. The
  VM test `cascades_that_do_not_draw_keep_their_drawn_view_in_the_besl_vm`
  checks the shader's side, and the `shadow_updates` tests the scheduler and
  states.

## Shadow views draw coarser detail levels

A shadow view draws each instance at the coarsest detail level whose error its
texels hide, never finer than the camera's level, so a map's meshlets follow
its own resolution instead of the screen's. The shadow pass hands
`record_meshlet_dispatches` the texels across the run's maps as `view_texels`,
and the task shader does the rest; see
[Shadow views pick their own level](/docs/develop/rendering/visibility/meshlet-dispatch#shadow-views-pick-their-own-level).

A coarser caster can lie up to one texel, times `render.lod.bias`, off the
surface the camera lights, while the receiver's offset shrinks to nothing on
a surface that faces the light. If a change makes a surface shadow itself,
lower the allowance before you add a bias.

## Cascades skip small casters

Drawing a shadow caster costs about the same at any size, because the shadow
pass is bound by the meshlets it emits, not by the texels it fills. The coarse
cascades hold thousands of small instances, such as grass clumps, that each
cover a few texels. The [casters](/docs/reference/rendering#the-visibility-pipeline)
rule drops them: the task shader skips an instance whose bounding sphere spans
fewer than `MIN_CASTER_TEXELS` texels of a directional cascade.

The test measures `caster_radius` of the instance's level record, not the
level's sphere. The record takes it from the baked primitive's `caster_radius`.
For an ordinary mesh the two are the same. A
[cluster mesh](/docs/develop/resource-management/level-merging)'s sphere spans
many copies, so its primitive holds the radius of its largest copy. Without
that, a cluster of grass always passed the test and drew every clump into every
cascade: on the slate quarry that took the shadow pass from
4.6 ms to 15.5 ms. `task_main_skips_a_wide_level_whose_copies_are_narrower_than_the_minimum_extent`
guards it.

The shadow pass hands the limit to the task shader as the push constant
`minimum_caster_extent`: the narrowest width, in normalized device units, that
a view draws, which is 2 × 32 / resolution for a cascade. Camera, cone, and
point dispatches pass zero. An orthographic view maps every distance to the
same scale, so the test reads only the length of the view-projection's first
row.

On the slate quarry, skipping casters narrower than 32 texels cut the shadow
pass from about 15 ms to 8 ms. At 8 texels it saved about 1 ms. The cost is
lighter shading inside dense grass, where many small shadows add up; supply
that darkening another way, such as ambient occlusion, instead of lowering the
limit.

A change to the cull must keep:

- The limit at zero for perspective views. Their widths change with distance,
  and the test doesn't account for it.
- Skinned instances in every view, since a pose can move them past their
  bounds.
- The VM test `task_main_skips_casters_narrower_than_the_minimum_extent`
  passing.

## Sun penumbrae read every texel under their filter

A sun's penumbra is as wide as its occluder is far above the receiver, times
the tangent of the sun's angular radius: about 55 millimeters on each side for
Sponza's roof edge, 12 meters above the courtyard floor. The
[penumbra rules](/docs/reference/rendering#the-visibility-pipeline) filter it
with a tent that reads every texel within 2 to 8 texels of the receiver. The
sun visibility resolve reads them in blocks of 4x4 texels, from one block at a
radius of 2 to 4x4 blocks at 8, and issues each block's four gathers before it
compares any texel, so they're in flight together. Each block's weights and
plane depths step from its first texel, and the weight sums come out of the
same loop.

Blended surfaces lie in front of the depth the resolve reads, so material
evaluation filters the cascades for them. It calls the same code:
`sample_directional_shadow` and its helpers live in
`layouts/directional_shadows.besl`, the module of the `DirectionalShadows`
layer, which both the resolve and every material evaluation shader take. The
layer holds the cascades, their depth pyramids, and the suns' parameters. The
material shader used to keep a copy that fetched texels one by one, because the
transparent phase's code was live in every opaque pipeline and gathers there
slowed opaque materials. The phase is a
[specialization constant](/docs/develop/rendering/shader-variants) now, so an
opaque pipeline compiles none of it.

The material shader resolves the first shadowed sun before its light loop, as
the resolve handles its first sun outside its loop over suns, and the bake
removes the later suns' block when `render.lights.directional.max` is 1. The
hoist follows the resolve's spill measurements and hasn't been measured on its
own. The shared filter as a whole is a cleanup, not a speed-up: on the slate
quarry at 3840 × 2036 it measured within 0.3 ms of the copy it replaced at a
render scale of 0.67, and 0.4 to 2 ms slower at 1.

A penumbra outside the tent's 2 to 8 texels is clamped, so it comes out wider
or narrower in meters than it is. The penumbra cascade is the one where the
clamp changes it least, by the larger of 2 / w and w / 6, where w is the
penumbra's width in that cascade's texels: 2 / w is how far a 2-texel tent
widens a narrower penumbra, and w / 6 weighs the reads a wider one costs.
Between cascades whose texels differ by a factor of 2, the coarser one takes
over at 4.9 of the finer one's texels, and the fade mixes the two from 4 to 6
of them. The choice can only flip between the best cascade on each side of
√12 texels, where 2 / w and w / 6 meet, since a penumbra's width scales every
candidate alike. So the fade mixes only those two. It used to mix the two best
cascades wherever they were, and on the slate quarry, where receivers fitting
leaves cascades 2 and 3 only 1.3 times apart in texel size, nearly every
penumbra pixel in cascade 2 filtered cascade 3 as well, at a constant 80 to 20
mix that no flip called for. Receivers fitting doesn't keep the cascades in order of texel size: on
Sponza, cascade 2 can have finer texels than cascade 1, and cascade 3 sixteen
times coarser ones than cascade 2. With receivers fitting, a coarser cascade
also often doesn't hold a nearby receiver, since it's fitted to farther
surfaces; then a finer one filters the penumbra, up to 8 texels wide, 64
gathers, a cost that falls only on the pixels of wide penumbrae.

Two earlier filters show why. The first kept 16 taps and spread them up to 4
texels apart, so it skipped up to 15 of every 16 texels and drew an occluder's
edge on a grid 4 texels wide: near Sponza's courtyard floor, a staircase of
soft blocks 20 to 30 pixels long that rearranged as the camera moved its
cascade, spacing, and blend. The second read every texel but moved to the next
cascade once the penumbra spanned 4 texels, wherever it landed there. Looking
down Sponza's courtyard from the upper gallery, the roof's penumbra kept its
55 millimeters in cascade 1, and past the boundary to cascade 2, which handed
it to cascade 3, where it spanned two-thirds of a texel, the 2-texel tent
blurred it to 167 millimeters. It now stays in cascade 2 at 41 millimeters,
clamped to 8 texels.

On Sponza at 1024 × 1024 on an Apple M4, with the camera 2 to 3.2 meters
above the courtyard floor looking 35° down at the roof's shadow edge, moving
the camera up in 10-centimeter steps changed the edge's sun visibility,
compared on the floor plane, by 0.37 to 1.00 of 255 on average each step with
the spaced taps, and by 0.04 to 0.08 with every texel read, the comparison's
own noise. In that view, where most of the image is a wide penumbra, the
`screen-space` stage, which holds the sun visibility resolve, took 1.88 ms with
the spaced taps, 2.08 ms with every texel read in a loop that compared each
quad as it arrived, 1.94 ms with each block's four gathers issued first, and
1.99 ms with the cascade chosen by how little the clamp changes the penumbra,
in frames where the shadow raster matched within 2 %. From the upper gallery,
the cascade choice took the stage from 1.53 to 1.61 ms.

A change to the penumbra filter must keep:

- The penumbra cascade chosen by how much the 2-to-8-texel clamp changes the
  penumbra's width in meters, not by a texel count alone, so the blur stays the
  same width where the cascade changes. Cascades don't nest under receivers
  fitting, so neither their order nor a fixed ratio between them may be assumed.
- The fade only between the best candidates on either side of √12 texels.
  Candidates on the same side never trade places as the penumbra widens, so
  mixing them doubles the filter's reads for no seam.
- Every texel under the tent read. A filter that reaches further with the same
  taps undersamples the map and brings the staircase back.
- The filter's reach of 8 texels, plus the receiver's move off its surface,
  inside the 10-texel margin that `directional_shadow_cascade_holds` keeps from
  a cascade's edge, so the filter never reads past the map. The penumbra
  cascade is chosen only among cascades that hold the receiver, and the margin
  stays inside the 17 texels that pad every fitted cascade.
- A cascade holding a receiver only inside its depth range as well as its
  square. Receivers fitting ends each cascade at the surface farthest from the
  light in its own slice, and a receiver past that end projects outside the
  map's depth, where a sample reads as lit. Looking down Sponza's courtyard
  toward the sun, the floor near the camera lay past cascade 1's end, and
  where the cascade fade mixed cascade 1 into cascade 0, a gray band leaked
  into the floor's shadow, cut off in 8-texel steps where the fully-shadowed
  probe took over.
- One filter for every receiver, in `layouts/directional_shadows.besl`. Don't
  give a shader its own copy: a function that reads the minimum pyramid takes
  the `DirectionalShadows` layer, because BESL doesn't pass a texture with a
  reducing sampler as an argument. The VM tests
  `directional_shadow_penumbra_widens_with_its_radius_in_the_besl_vm` and
  `directional_shadow_penumbra_follows_a_shallow_edge_in_the_besl_vm` check the
  filter.

## The occluder search proves a receiver lit

The sun visibility resolve searches for a receiver's occluders before it reads
the map. `directional_shadow_occluder_distance` gathers the 4 × 4 max-depth
cells around the receiver, and when no cell rises above the receiver's plane by
more than 4 texels of its slope, the receiver is lit and the resolve reads
nothing else: the
[proven receivers](/docs/reference/rendering#the-visibility-pipeline) rule.
Only when the search finds an occluder does the resolve probe the min-depth
pyramid for a fully shadowed receiver, and only past that does the penumbra
filter run. The search is the blocker search of percentage-closer soft shadows
(Fernando, *Percentage-Closer Soft Shadows*, 2005). Taking an empty search as
proof of a lit receiver is the engine's own construction. **[own]**

The resolve used to start with a probe that compared the cells with the depth
of the receiver's center. On ground the sun doesn't meet square on, the
ground's own texels uphill of the receiver are closer to the light than its
center, so the probe failed there. A lit pixel then paid the shadowed probe,
the search, and a 2-texel filter, 16 gathers, to return 1. The search compares
each cell with the plane instead, so it settles the same pixel in 4 gathers.

The proof isn't exact. A cell counts only above 4 texels of slope, because the
receiver's own texels in a cell lie up to 3.5 texels from the cell's center.
An occluder that stays below that in every cell is missed: one whose shadow
would be about 4 texels long or shorter, such as a curb. The 2-texel filter
used to catch those. A taller occluder is found from every receiver near it,
so its shadow still reaches its foot. Contact shadows cover the first
`render.contact-shadows.distance` of what's missed.

### Coarse levels settle open ground and deep umbra in one read

Both pyramids keep mips past their 8-texel first level, down to 32 × 32-texel
cells by default. `DIRECTIONAL_SHADOW_PYRAMID_FIRST_LEVEL` and
`DIRECTIONAL_SHADOW_PYRAMID_LAST_LEVEL`, the log2 of each level's cell side,
set them; they live in `render_pass/shadows.rs` and
`layouts/shadow_depth_pyramid.besl`, which must match. The first-level pass
writes mip 0, and `directional-shadow-depth-pyramid-level` halves each later
mip from the one before it, one dispatch per level. The cascade resolution
must be a multiple of the last level's cell side, so cascades stay packed one
below the other at every level.

Ahead of the search, one maximum-reduction sample of the last level reads the
2 × 2 coarse cells that hold the search's 4 × 4 first-level cells. When even
their nearest occluder stays below the receiver's plane at its lowest over
the search, two cells of slope below the receiver, plus the 4-texel slack, no
first-level cell can count, and the receiver is lit after 1 read instead of
4. Ahead of the four first-level min-depth probes, one minimum-reduction
sample of the same coarse cells proves deep umbra the same way. The coarse
cells hold the first-level cells' bounds, so each coarse proof proves only
what the first level would: the results don't change, only their cost. A
penumbra pixel pays both coarse reads on top of the 8 it paid before. On a
slope the coarse plane bound is two cells of slope wide, so slopes fall
through to the first level more often. A last level one past the first fits
the search's block in 2 × 2 of its cells for only about half the receivers,
and at the first level never, so neither proof runs there. The coarse bound
over the plane's extreme is the engine's own construction on top of the
search's. **[own]**

A change to the proof must keep:

- The coarse proofs implied by the first level's. A coarse sample must cover
  every first-level cell the search or the probe reads, and compare against
  the plane's extreme over all of them.
- The search ahead of the shadowed probe. Under a sun most receivers are lit,
  and the search alone settles them.
- The 4-texel slack in `directional_shadow_blocker_cell`. Below it, a sloped
  receiver counts as its own occluder, and every lit slope filters again.
- The same proof in any other cascade the filter samples, which
  `sample_directional_shadow_cascade` runs when a coarser cascade decided: a
  thin occluder or gap can vanish at the coarser resolution.
- The same proof for blended receivers, which call the same search.
- Virtual shadow maps' own proof, `virtual_shadow_occluder_distance`, which is
  conservative and reads its cells once.

## The first sun resolves outside the loop

A project shadows one sun unless `render.lights.directional.max` asks for
more, and its baked resolve holds one sun's code. `main` in
`sun-visibility.besl` resolves the first sun on its own, then loops over the
later suns inside a block that reads `later_suns`. The bake removes that block
at a count of 1, as it removes the code of any
[feature left out of the bake](/docs/use/resources/bake#leave-render-features-out-of-the-bake),
and the contact-shadow trace marks its later suns the same way.

The loop costs more than the suns it runs. A value a loop body reads must stay
live to the end of the body for the next iteration, even when the count is 1
and no next iteration comes. So the receiver's position, edges, and normal
stayed live across the search and the filter, where the registers ran out, and
the compiler spilled them to the stack on every pixel. On the slate quarry at
3,840 × 2,036 and render scale 0.67 on an Apple M4, a resolve with the loop
spilled 80 bytes a thread and took 2.21 ms; the same resolve with the first sun
inline spilled 16 bytes and took 2.01 ms. Projecting the receiver again in the
filter loop, instead of keeping the search's projection live, removed the last
16 bytes and took it to 1.95 ms. Those figures come from a variant without the
virtual shadow map branch; the shipped resolve keeps that branch.

The instruction count hardly matters here. Removing 2,300 instructions that
most pixels never run changed the pass by less than 3 %, while 64 bytes of
spill on the path every pixel takes changed it by 9 %.

A change to the resolve must keep:

- The first sun's resolve outside any loop, and every later sun inside the
  block that reads `later_suns`.
  `a_project_that_shadows_one_sun_bakes_no_later_suns` checks both shaders.
- No sun in a shadow slot the baked shaders can't resolve. `ShadowBudget::suns`
  carries the project's count into `select_shadow_lights`, and
  `suns_past_the_projects_count_cast_no_shadows` guards it.
- Nothing kept live across the filter that can be worked out again for less
  than a spill costs. Measure the spilled bytes, not the instructions.

## Contact shadows trace only what can show

The [contact shadow](/docs/reference/rendering#contact-shadows) trace runs for
every opaque pixel, so its fixed cost matters more than its worst case. Three
choices keep it low:

- **One sample per pixel crossed.** A ray takes as many samples as the pixels
  it crosses on screen, from 1 to 16 (McGuire and Mara, *Efficient GPU
  Screen-Space Ray Tracing*, 2014). At a reach of 0.1 meters a ray is shorter
  than 16 pixels past a few meters from the camera, and 16 samples there read
  the same few texels again.
- **A shared depth tile.** Each 8 × 8 workgroup loads the 1/z of the 12 × 12
  pixels its surface gradients read into workgroup memory, so a pixel's slope
  costs no fetch of its own.
- **No ray from a surface that faces away.** The slope gives the pixel's plane,
  and a pixel whose plane faces away from a sun marches no ray toward it. The
  slope is atyuwen's depth-buffer reconstruction (*Accurate Normal
  Reconstruction from Depth Buffer*, 2020); using it to cull rays is the
  engine's own construction. **[own]**
  [Lighting](/docs/develop/rendering/lighting) records what that gives up.

A change to the trace must keep:

- One trace per pixel, never per block, as
  [temporal antialiasing](/docs/develop/rendering/taa) requires.
- The trace ahead of the resolve, recorded with the first stages of the other
  screen-space passes, so the GPU overlaps them.
- The march offset one step wide. The resolve's 3 × 3 mean turns it into a
  smooth ramp only while each 3 × 3 block covers a whole step.
- `contact_shadows_cast_no_ray_from_a_surface_that_faces_away_from_the_sun`
  and `contact_shadows_darken_the_floor_just_in_front_of_a_low_wall` passing.
