Use this page when you change the resource-storage contracts, ReDB
implementation, or payload-reading APIs. Read the
[resource-management reference](/docs/reference/resource-management) first if
you need the high-level resource model.

Each resource exposed by a backend has two parts:

- metadata, represented by `SerializableResource`
- binary payload bytes, exposed through a resource reader

The metadata contains the public ID, hashed UID, resource class, decoded and stored binary sizes, content hash, payload encoding, serialized typed model, optional stream descriptions, and queryable properties.
The binary payload contains the actual bytes consumed by a renderer, audio system, or other runtime system.

## Typed references

`ResourceManager::request<T>().await` returns a typed `Reference<T>`.
The reference contains the typed resource metadata and a reader for the payload.

`request` reads each resource from storage once and passes that record to the model's `StoredModel` implementation, which builds the reference and resolves its dependencies.
For example, a material reference resolves its shader and parameter resources concurrently.
A mesh reference exposes stream descriptions for packed vertex and index data, and lists its distinct material variants in `Mesh::materials` without resolving them.
Each primitive names its variant by index. Request a variant by its ID when your system needs it, so a mesh load doesn't read every material's shaders and textures once per primitive.

## Resource storage backends

A resource storage backend connects resource producers and consumers to stored
metadata and payloads. The contract defines resource operations without
prescribing a database, directory layout, or reader backing.

The resource module separates that contract by capability:

- `ReadStorageBackend` lists, reads, and queries resources. A read returns
  serialized metadata and a reader for the decoded payload.
- `WriteStorageBackend` clears or deletes resources and provides complete and
  incremental authoring paths.
- `StorageBackend` composes both capabilities for a `ResourceManager`.
- The `Dyn*StorageBackend` traits provide the same boundaries when the
  implementation is selected at runtime.

Backend implementations decide how to map resource IDs to storage, publish
metadata and payloads, support queries, and provide reader-owned backing. Code
that uses the contracts must not assume that a backend uses ReDB, files, memory
mapping, or any other physical layout.

<Callout type="info" title="Asset storage is a separate boundary">
	`asset::StorageBackend` resolves and versions authored source assets.
	`resource::StorageBackend` stores the resources produced from those assets.
</Callout>

Every model exposes at least a `name` queryable property by default. Specific
models can add properties as editor and tooling needs grow. A backend can choose
how it evaluates those queries as long as it preserves the query contract.

In development builds, `ProcessedAsset::new` also collects the IDs of the
resources a model refers to from `Model::references`, and the ReDB backend
stores them in the same transaction as the resource, for `beld browse`. When
you add a model field that holds a `ReferenceModel` or another resource's ID,
add it to the model's `references` and to the per-class table in the
[development records](/docs/reference/resource-store#development-records)
reference. Release builds neither collect nor store references, so shipped
stores don't carry them. The ReDB backend test
`references_are_stored_with_the_resource_and_removed_with_it` guards that a
replacement, a delete, and a clear keep the records in step with the
resources.

## Payload authoring and encoding

The default complete-payload authoring path uses CPU LZ4 compression. `compression::prepare` cuts the payload at every stream's start and end offset and stores each segment as its own block behind a small block table, so a reader can decode one stream without the others. The [CPU LZ4 layout](/docs/reference/resource-store#cpu-lz4-layout) defines the table and the segments. A payload without streams is one segment.

The size, probe, and savings rules apply to each segment. A segment stays raw when it's smaller than 1 KiB or compression wouldn't save more than 12.5 percent. Before it compresses a segment of 128 KiB or more, it compresses four 16 KiB samples spread across the segment. When the samples save less than 6.25 percent, it stores the segment raw without compressing the rest of it, which is the usual outcome for BC7 mip levels. When no segment compresses, or the temporary compression output can't be prepared safely, the whole resource is stored as `raw`. Set `ProcessedAsset::with_compression(ResourceCompressionPolicy::Disabled)` when one resource must remain uncompressed. A backend can override the CPU compression policy when it needs another transport path.

The block table lives in the payload instead of the stream descriptions, so a complete read decodes every block without metadata. That keeps `ResourceReader::into_backing_storage` and `beld` payload reads independent of `streams`. A raw block is one whose stored size equals its decoded size: a kept LZ4 block is always smaller, so the table needs no separate flag. The tests in `resource/compression.rs` and `resource/reader/mod.rs` guard that a stream read returns exactly the requested streams' bytes and that a payload with a raw block next to an LZ4 block still decodes completely.

The resource hash always identifies decoded bytes, so changing the storage encoding doesn't change resource identity. Byte Engine computes it with rapidhash V3, a non-cryptographic hash whose output stays the same across crate versions and platforms. Each resource stores one `encoding`: `raw`, `cpu-lz4`, or `metal-io-lz4`. CPU and GPU encodings are mutually exclusive by construction. Inspect `encoding`, `size`, and `stored_size` when you need to distinguish the client-facing payload from its physical extent.

Only complete payload store calls apply CPU compression. A `ResourceTransaction` created with `begin_resource` stays uncompressed because its bytes can arrive through partial writes.

## ReDB storage backend

`ReDBStorageBackend` is Byte Engine's persistent resource-storage
implementation. It stores metadata in `resources.db` and supports two payload
layouts:

- `files` stores each resource payload in a separate extensionless file named from its resource ID, decoded hash, and encoding. This mode is the default. Read the resource's persisted `encoding` to interpret the file contents.
- `packed` stores every payload in a reusable range of `resources.pack` and records each resource offset in `resources.db`.

One mode applies to the whole ReDB resource store. The implementation records
that mode when it creates the store and discovers it when the store is reopened.
It rejects a conflicting mode instead of mixing payload layouts.

`ResourceStorageSettings` can also select native Metal I/O LZ4 transport for
compatible textures in file mode. The per-resource CPU policy and this ReDB
store setting select the final payload encoding. They aren't additional
resource state.

Packed replacements use copy-on-write publication so an interrupted bake can't replace valid metadata with partial bytes. After publication, the backend reuses the old range when no mapped reader still owns it. Deletion also returns its range. The allocator merges adjacent free ranges, chooses the smallest range that fits, and grows `resources.pack` only when no free range is large enough. When you reopen the store, it reconstructs free ranges from the live offsets in `resources.db`, which also recovers space left by an interrupted bake.

The backend publishes each resource with a commit that doesn't wait for the disk, and writes its payload without syncing it. `WriteStorageBackend::persist` makes everything stored so far durable at once: it syncs every payload file published since the last durable commit, then commits durably. Deleting a resource commits durably too, so it syncs those payloads first. A crash before a flush rolls the store back to its last durable commit, which loses only resources that the next bake rebuilds. The asset manager calls `persist` on an asset worker once the last root bake that callers wait on finishes, and that root returns once the flush is done. A bake of many assets therefore waits for the disk once, at the end.

A change must keep these rules true:

- Sync a payload before any durable commit that could make a record naming it durable, so a durable record never names a payload that a crash would lose.
- Sync payloads through Compio, which uses a plain `fsync` on Apple platforms. The standard library's `File::sync_data` flushes the whole drive cache there for each file, and the durable commit after the syncs already flushes it once for all of them.
- Flush only when no root bake is in flight. Syncs and durable commits issued in the middle of a bake queue behind each other on the disk, and every texture that waits on them keeps its GPU claim; see [GPU claims](/docs/develop/resource-management/assets#gpu-claims).

Use one ReDB backend instance for a resource directory while it can be updated.
Drop read-only ReDB backends and their mapped resource backings before reopening
the directory for writing.

Repeated rebuilds with changing payload sizes can split free space into many small ranges. The backend warns you when a pack of at least 64 MiB has at least 32 free ranges, at least 25 percent of the file is free, and no single range holds half of that free space. Delete the resource directory and [bake the application resources again](/docs/use/resources/bake) when you see this warning.

The ReDB implementation converts resource URLs into stable resource IDs for
storage lookup. It maintains class and property indexes so BELD and editor tools
can query resources without scanning and deserializing every entry.

## Streams

Some resources contain multiple logical byte ranges in one payload.
Meshes are the common example: positions, normals, UVs, triangle indices, meshlet data, and other streams can live in one packed buffer.

A mesh stores each detail level in its own `level[N].` streams, so the renderer can read one level without decoding the others. The baker orders each primitive's vertices by the coarsest level that uses them, coarsest first. A level then needs only a prefix of the vertices: the ones in its own vertex streams and in every coarser level's. No vertex is stored twice. `Primitive::lods` lists each level's meshlet count, vertex count, and error. Level 0 also stores full detail as a plain triangle list, for renderers that draw without meshlets. The [resource store reference](/docs/reference/resource-store#resource-classes) defines the streams.

`StreamDescription` names those byte ranges. Provide stream read targets when you
need selected streams instead of the complete payload.

## Loading bytes

The default load path requests backing storage from the reader. A backend can
provide any reader-owned backing that satisfies that contract. For example, the
ReDB file layout can provide a mapped file. Use an explicit buffer, boxed buffer,
or stream target when you need ownership or preallocated memory.

Use the default target when the consumer can borrow the backing storage directly.
Use explicit targets when the consumer needs a specific allocation, lifetime, or stream layout.

A CPU-compressed resource is always decoded before a client receives it. Load it into an exact buffer sized to `Reference::size`, reader-owned backing storage, or stream targets. A stream target decodes only the blocks its stream covers, so loading one mesh level or one mip level doesn't decompress the rest of the payload. Partial byte ranges are rejected, because a range can start inside an LZ4 block.
