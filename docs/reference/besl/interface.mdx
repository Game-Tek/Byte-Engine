Use the shader interface to connect a BESL program to stage inputs and outputs,
GPU resources, shared memory, and the native pipeline contract.

## Raster entry points

Declare values that cross a raster stage boundary with an anonymous
`interface` type. A vertex shader returns its interface. A fragment shader
receives the matching interface as a parameter:

```rust
in_position: input<vec2f, 0>;

main: fn (input: StageInput) -> interface { position: vec4f, uv: vec2f, instance_index: u32 } {
	let position: vec4f = vec4f(in_position.x, in_position.y, 0.0, 1.0);
	let uv: vec2f = in_position * 0.5 + vec2f(0.5, 0.5);

	return { position, uv, instance_index: input.instance_index };
}
```

```rust
main: fn (
	pipeline_input: interface { instance_index: u32, uv: vec2f },
) -> output { color: vec4f } {
	let color: vec4f = vec4f(pipeline_input.uv.x, pipeline_input.uv.y, 0.0, 1.0);
	return { color };
}
```

Use the same interface field names and types in adjacent stages. Their source
order doesn't need to match. BESL sorts the field names to assign stable native
locations, so the two examples agree even though they list `uv` and
`instance_index` differently. Integer fields use flat interpolation. A vertex
`position: vec4f` field is the native clip-space position, doesn't consume a
varying location, and isn't a fragment input.

An `output` record describes final fragment attachments. Declaration order sets
the color attachment locations, starting at `0`.

Keep explicit top-level `input<TYPE, LOCATION>` declarations for vertex-buffer
attributes. Task payloads and mutable mesh output arrays also keep their
dedicated declarations:

```rust
out_instance_index: output<u32, 0, 126>;
```

Locations range from `0` through `255`. Don't repeat a location within one
explicit input or output list.

## Stage input values

Add a `StageInput` parameter when a vertex shader needs its invocation indices.
Read `input.vertex_index` or `input.instance_index`; both values are `u32` and
don't consume vertex-attribute locations:

```rust
main: fn (input: StageInput) -> interface { instance_index: u32 } {
	let vertex: u32 = input.vertex_index;
	return { instance_index: input.instance_index };
}
```

BESL maps both indices to the matching system values on each backend:

| `StageInput` field | Vulkan GLSL | HLSL | MSL |
| --- | --- | --- | --- |
| `vertex_index` | `gl_VertexIndex` | `SV_VertexID` | `[[vertex_id]]` |
| `instance_index` | `gl_InstanceIndex` | `SV_InstanceID` | `[[instance_id]]` |

These values are available only in the vertex stage. In VM tests, bind them
through `builtin_vertex_index_slot()` and `builtin_instance_index_slot()`.

## Task payload and workgroup storage

Task and mesh stages can share payload arrays. Task and compute stages can also
declare storage shared by every invocation in one workgroup:

```rust
visible_meshlets: task_payload<u32, 32>;
visible_count: workgroup<atomicu32>;
scratch: workgroup<f32, 64>;
```

Omit the count for one shared value. Add a positive count for shared arrays.
Use `workgroup_barrier()` before reading values written by other invocations.

## Push constants

Use push constants for small uniform values outside normal descriptor bindings:

```rust
push_constant: push_constant {
	material_index: u32,
}
```

## Descriptors

A descriptor declares a named binding between the shader and one GPU resource.
Declare its required properties inside the descriptor object:

```rust
name: descriptor<{
	type: ResourceType,
	binding: BINDING,
	access: ACCESS,
}>;
```

`type`, `binding`, and `access` are required. You can write the properties in
any order, and you can add a trailing comma. Use `memory` for a buffer memory
class and `count` for a fixed array of independent resources:

```rust
name: descriptor<{ type: ResourceType, binding: BINDING, access: ACCESS, count: COUNT }>;
name: descriptor<{ type: BufferStruct, binding: BINDING, access: ACCESS, memory: MEMORY_CLASS }>;
name: descriptor<{
	type: BufferStruct,
	binding: BINDING,
	access: ACCESS,
	memory: MEMORY_CLASS,
	count: COUNT,
}>;
name: descriptor<{ type: ElementType[], binding: BINDING, access: ACCESS }>;
```

This example declares buffer, texture, texture-array, and storage-image bindings:

```rust
Frame: struct {
	view_projection: mat4f,
}

Vertex: struct {
	position: vec3f,
}

frame: descriptor<{ type: Frame, binding: 0, access: read, memory: constant }>;
vertices: descriptor<{ type: Vertex[], binding: 1, access: read }>;
albedo: descriptor<{ type: Texture2D, binding: 2, access: read }>;
shadow_maps: descriptor<{ type: Texture2DArray, binding: 3, access: read }>;
gbuffers: descriptor<{ type: Texture2D, binding: 4, access: read, count: 4 }>;
output_image: descriptor<{ type: StorageImage<rgba16f>, binding: 7, access: write }>;
```

The descriptor resource type selects the reflected binding kind. BESL supports
these resource types:

| Resource type | Binding | Use |
| --- | --- | --- |
| A previously declared struct, such as `Frame` | Storage buffer | Bind structured data. Declare the struct before the descriptor. |
| An element type followed by `[]`, such as `Instance[]` | Runtime-sized storage buffer | Bind a contiguous sequence and index it directly. |
| `Texture2D` | Combined 2D texture and sampler | Sample one two-dimensional texture. |
| `Texture2DArray` | Combined 2D-array texture and sampler | Sample layers from one two-dimensional texture array. |
| `Texture3D` | Combined 3D texture and sampler | Sample a three-dimensional texture. |
| `TextureCube` | Combined cube texture and sampler | Sample one cube texture. |
| `TextureCubeArray` | Combined cube-array texture and sampler | Sample cube textures from an array. |
| `StorageImage` | Storage image | Load or store an image whose format remains backend-defined. |
| `StorageImage<FORMAT>` | Typed storage image | Load or store an image with an explicit backend image format, such as `r8`, `r32f`, `r32ui`, or `rgba16f`. |

Set `access` to `read`, `write`, or `read_write`. The access must include every
operation the shader performs on the resource.

For a buffer, set `memory` to `constant` for small, read-only values shared
by a dispatch or draw. Use `device` for large buffers, data that varies between
shader threads, and every writable buffer. If you omit the memory class, a buffer
uses `device`. Image and texture descriptors cannot declare a memory class.

Set `count` to a positive integer to declare an array of independent resources.

Write `ElementType[]` to bind one storage buffer whose element count comes from
the bound resource. Index it directly in a function, without a wrapper struct:

```rust
Instance: struct {
	position: vec3f,
	sprite_id: u32,
}

instances: descriptor<{ type: Instance[], binding: 1, access: read }>;

main: fn (pipeline_input: interface { instance_index: u32 }) -> void {
	let instance: Instance = instances[pipeline_input.instance_index];
	instance;
}
```

`ElementType[]` describes the contents of one buffer. It doesn't declare an
array of descriptors. Reflection reports one storage-buffer binding and the
element stride.

`Texture2DArray` also describes one resource: a layered two-dimensional
texture. Indexing it selects a layer from that resource before sampling:

```rust
sprites: descriptor<{ type: Texture2DArray, binding: 0, access: read }>;

main: fn (pipeline_input: interface { sprite_id: u32, uv: vec2f }) -> output { color: vec4f } {
	let color: vec4f = sample(sprites[pipeline_input.sprite_id], pipeline_input.uv);
	return { color };
}
```

Use `descriptor<{ type: Texture2D, binding: BINDING, access: read, count: COUNT }>` when you need `COUNT`
independent 2D texture descriptors instead.

Reflection retains the authored name and flat slot for each descriptor reachable
from `main`.

Storage-buffer counters use `atomicu32` or `atomici32` members with the
[atomic intrinsics](/docs/reference/besl/intrinsics#buffer-and-workgroup-atomics).
Integer storage images can be read as scalars with `image_load_u32`:

```rust
Counters: struct {
	values: atomicu32[1024],
}

counters: descriptor<{ type: Counters, binding: 5, access: read_write, memory: device }>;
index_image: descriptor<{ type: StorageImage<r32ui>, binding: 6, access: read }>;
```

## Standalone stage metadata

Standalone `.besl` assets require an adjacent `.besl.bead` file. Set `stage` to
`Vertex`, `Fragment`, `Compute`, `Task`, or `Mesh`.

Compute, task, and mesh stages can set `workgroup` with up to three positive
dimensions. Omitted dimensions default to `1`, and omitting `workgroup` uses
`[1, 1, 1]`.

```json
{ "stage": "Compute", "workgroup": [8, 8, 1] }
```

You can also name the dimensions. This JSON5 form is equivalent to `[8, 8, 1]`:

```json5
{ stage: "Compute", workgroup: { width: 8, height: 8 } }
```

Task stages require a positive `maximum_mesh_threadgroups` value:

```json
{ "stage": "Task", "workgroup": [32, 1, 1], "maximum_mesh_threadgroups": 32 }
```

Mesh stages require positive `maximum_vertices` and `maximum_primitives` values:

```json
{ "stage": "Mesh", "workgroup": [128, 1, 1], "maximum_vertices": 64, "maximum_primitives": 126 }
```

`Vertex` and `Fragment` stages don't accept `workgroup` or mesh limits.

## Stage and backend support

The normal generators support these stage and output-language combinations:

| Stage | GLSL | HLSL | MSL |
| --- | --- | --- | --- |
| Vertex | Supported | Supported | Supported |
| Fragment | Supported | Supported | Supported |
| Compute | Supported | Supported | Supported |
| Task | Not supported | Supported as an amplification shader | Supported as an object stage |
| Mesh | Supported through `GL_EXT_mesh_shader` | Supported | Supported |

The generated language support doesn't guarantee that a device exposes the
required shader stage or extension. Half-precision and subgroup operations also
require their target capabilities. BESL validates subgroup intrinsics for
compute stages only; see [compute-stage intrinsics](/docs/reference/besl/intrinsics#compute-stage).

the values declared by the interface.
