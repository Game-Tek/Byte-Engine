Byte Engine records physical input as device-trigger values in one input
collector. Input sinks resolve those values into actions such as `Move`,
`Lookaround`, `RightHand`, `View`, or `Exit`, and your application listens for
action events instead of checking raw keys and buttons. This page defines the
pieces of that model. To declare actions, read their events, and give each
consumer its own sink, follow [Respond to input](/docs/use/input).

## Device classes

A device class describes the input layout for a category of hardware.
The standard setup registers classes such as `Pointer`, `Mouse`, `Keyboard`, and `Gamepad`.

Each class has triggers:

- `Pointer.Position`, `Pointer.Movement`, `Pointer.LeftButton`, `Pointer.Scroll`
- `Mouse.Movement`, `Mouse.LeftButton`, `Mouse.Scroll`
- `Keyboard.W`, `Keyboard.Space`, `Keyboard.Period`, `Keyboard.Backspace`, `Keyboard.Character`
- `Gamepad.LeftStick`, `Gamepad.RightStick`, `Gamepad.X`, `Gamepad.RightTrigger`

Each device class declares its named inputs and the value type that each input
produces.

`Keyboard.LeftMeta` and `Keyboard.RightMeta` are the keys beside the space bar
that the system keeps for its own shortcuts: Command on macOS, the Windows key
on Windows, and Super on Linux. The system may take some combinations with
them, such as Command and the space bar on macOS, before the application sees
them.

`Keyboard.LeftShortcut` and `Keyboard.RightShortcut` are the keys that start
the platform's shortcuts: Command on macOS, and Control on Linux and Windows.
They aren't keys of their own. Each press, repeat, and release of that physical
key also reports as the matching shortcut input, right after it, so the press
reaches both `Keyboard.LeftControl` and `Keyboard.LeftShortcut` on Linux. Bind
shortcuts to them, so users on each platform press the key they use in other
applications. Show them by the platform's name, Cmd on macOS and Ctrl
elsewhere.

A keyboard key names a physical position, not the character printed on it: the
key right of Caps Lock is `Keyboard.A` on every layout, including those whose
letters aren't Latin, and with any modifier held. The text a key types follows
the layout and reaches `Keyboard.Character`.

## Devices

A device is a concrete instance of a class.
One keyboard and two gamepads are three devices, even though the gamepads share one device class.

The default graphics setup creates one pointer, one mouse, one keyboard, and one gamepad device after registering the standard classes.
Custom integrations can register their own classes and create devices directly through `InputCollector`.

## Seats

A seat identifies the player or user context associated with input.
The current default window integration uses `SeatHandle::stub()` until platform seats are wired through end to end.

Seats let the same type of physical input belong to different users.
Input state is stored by seat, device, and trigger, so local multiplayer, split-screen, remote control, or editor/game focus can be represented without changing the action model.

## Triggers

A trigger is a named value on a device class.
It can be boolean, float, unicode, vector, quaternion, color, or another supported input value type.

Window events are translated into trigger records.
For example, a key press becomes a boolean value for `Keyboard.W`, mouse motion becomes a `Vector2` value for `Mouse.Movement`, and typed text becomes a unicode value for `Keyboard.Character`. Only text a key types reaches `Keyboard.Character`: control characters, such as those Enter and Backspace type, and the private-use characters a platform reports for keys that type no text, such as the arrows and function keys on macOS, don't. On macOS and Linux, a key pressed while Control or `Keyboard.LeftMeta` or `Keyboard.RightMeta` is held types nothing, so shortcuts don't type. A dead key types nothing on its own and joins the next key into one character, such as `´` then `e` into `é`. One physical event can become records on more than one device: a mouse click becomes both `Pointer.LeftButton` and `Mouse.LeftButton`.

The collector queues records until the sinks pull them. When the tick ends, it
keeps the latest value for each seat, device, and trigger.

## Pointer and mouse

The `Pointer` and `Mouse` classes report the same mouse two ways. `Pointer`
reports the system cursor, as the platform moves it with pointer acceleration;
bind it for interfaces and anything the cursor points at. `Mouse` reports the
physical mouse before pointer acceleration; bind it for camera control and
aiming.

| Trigger | Value |
| --- | --- |
| `Pointer.Position` | Where the cursor is: the window's left and bottom edges at `-1`, its center at `0`, and its right and top edges at `1`. Positions outside the window extend past these values. |
| `Pointer.Movement` | How far the cursor moved since the previous record, after pointer acceleration. |
| `Mouse.Movement` | How far the mouse moved since the previous record, before pointer acceleration. |
| `LeftButton`, `RightButton`, `MiddleButton` | Whether the button is held. Both classes report every press and release. |
| `Scroll` | How far the wheel turned since the previous record. |

Both movements are `Vector2` values: `x` grows to the right and `y` grows
upward. Each record is one movement, and a tick can hold many. The size of a
movement doesn't depend on the window's size.

| Platform | `Pointer` source and units | `Mouse` source and units |
| --- | --- | --- |
| macOS | AppKit events; movement in points | Game Controller mouse input; movement in mouse counts. While no Game Controller mouse is connected, AppKit events, as `Pointer` reports them. Scroll always comes from AppKit. |
| Windows | Window messages; movement in pixels | Raw input; movement in mouse counts; scroll in wheel notches |
| Linux (Wayland) | Pointer events; movement in relative-pointer units; scroll in wheel notches, or surface units for a touchpad | Pointer events; movement in unaccelerated relative-pointer units; scroll as `Pointer` reports it |

## Cursor capture

A window with cursor capture holds the cursor while it's captured, so the
mouse can move without end, and `Mouse.Movement` keeps reporting motion. A
window gets cursor capture when it's created, or later through a
[feature change](/docs/reference/rendering#windows).

| Rule | Value |
| --- | --- |
| Engages | While the window has focus and no mouse button is held. On Wayland, the pointer must also be over the window. |
| While captured | The cursor is hidden and held at the window's center. `Pointer.Position` isn't recorded. `Pointer.Movement` keeps reporting motion on macOS and Wayland, and isn't recorded on Windows. |
| Releases | When the window loses focus, is minimized, or closes, or when a feature change removes its cursor capture. The cursor shows again at the window's center. |
| One at a time | At most one window holds the cursor. |
| Background windows | A window that runs unattended never captures the cursor. |

## Actions

An action represents input that your application understands. It has:

- a name, which a [bindings document](/docs/reference/input-bindings) replaces its bindings under
- an output type
- default trigger bindings, which a bindings document can replace
- optional value mappings
- a tick policy

For movement, keyboard keys can map to direction vectors, and the resolved action value can be a single `Vector3`.
For lookaround, mouse movement turns the view by how far the mouse moved, and a gamepad stick turns it at a rate.

Actions are created on the application's world. A `Name` attached in the same
creation chain lets inspection tools find the action by name.

## Value mapping

Bindings can map a trigger value into the action's output type.

Byte Engine doesn't support a general cast between every input value type. The
following table lists the conversions that action bindings support:

| Trigger value | Supported action values | Conversion |
| --- | --- | --- |
| Boolean | Boolean, Float, Vector2, Vector3 | A Boolean value passes through unchanged. For a Float action, the binding supplies the scalar value used while the trigger is active. For a Vector2 or Vector3 action, Byte Engine adds the mapped direction from each active Boolean binding, then normalizes the result. |
| Unicode | Unicode | The character passes through unchanged. |
| Float | Boolean, Float | `0.0` becomes `false`, and any other value becomes `true`. A Float value passes through unchanged. |
| Integer | None | Action bindings don't convert integer trigger values. |
| Vector2 | Vector2, Vector3 | A Vector2 value passes through unchanged. A Vector3 action can use `Function::Sphere` to map the two components to a 3D direction and apply the binding's mapped Vector3 transformation. |
| Vector3 | Vector2, Vector3 | Converting to Vector2 keeps `x` and `y` and drops `z`. A Vector3 value passes through unchanged. |
| Quaternion | None | Action bindings don't convert quaternion trigger values. |
| RGBA | None | Action bindings don't convert color trigger values. |

These rules apply when a sink resolves device triggers through action
bindings. An `ActionEvent` published directly, for example by the inspector,
must carry a value whose type already matches the action type.

For movement, boolean key triggers can map to direction vectors.
When multiple movement keys are active, the input resolver combines the active mappings and normalizes the result.
This is why diagonal keyboard movement can be represented as one stable movement vector instead of separate key checks.

For lookaround, `Function::Sphere` can map a 2D input into a 3D direction.
Your application receives a direction-like action value without needing to know
whether it came from mouse position or a stick.

## Dead zones

A dead zone keeps a resting stick or trigger from moving anything, and lets a
worn one still reach its full value. It applies to a binding's Float and
Vector2 source values, before they convert to the action's type, so an analog
trigger bound to a Boolean action also stays `false` inside it. It's the
scaled radial dead zone: a stick keeps its direction, and a Float keeps its
sign.

| Term | Definition |
| --- | --- |
| Magnitude m | A Float's absolute value, or a Vector2's length. |
| Inner | The magnitude at and below which the value is zero. From 0, inclusive, to 1. |
| Outer | The magnitude at and above which the value has magnitude 1. Above the inner bound, up to 1. |
| Result | Zero when m is at most the inner bound. Otherwise the value times min((m − inner) / (outer − inner), 1) / m. |

| Rule | Value |
| --- | --- |
| Binding | A binding's own dead zone applies when it sets one. Inner 0 and outer 1 leave its values unchanged. |
| Device class | A binding without its own dead zone takes its source's device class dead zone, which is none unless the application sets one. The `input.gamepad.dead-zone.inner` and `input.gamepad.dead-zone.outer` [runtime settings](/docs/reference/parameters#runtime-settings) set the gamepad's. |
| Other values | Boolean, Vector3, and every other value pass through unchanged. |

## Response curves

A response curve bends how a stick or trigger answers between rest and full,
such as for finer aim near the center. It applies to the same values as a
[dead zone](#dead-zones), after it: a stick keeps its direction, and a Float
keeps its sign.

| Term | Definition |
| --- | --- |
| Exponent e | A number above 0. Above 1 is finer near rest, below 1 is quicker off rest, and 1 is a straight line. |
| Result | The value times m<sup>e</sup> / m, where m is its magnitude after the dead zone. Zero stays zero. |

| Rule | Value |
| --- | --- |
| Binding | A binding's own exponent applies when it sets one. |
| Device class | A binding without its own exponent takes its source's device class exponent, which is 1 unless the application sets one. The `input.gamepad.response-curve` [runtime setting](/docs/reference/parameters#runtime-settings) sets the gamepad's. |

## Axis inversion

A binding can invert its value's axes, such as a look stick's vertical axis for
a player who expects pushing up to look down. It applies to the same values as
a dead zone, after the response curve. Inversion belongs to a binding alone:
there's no device class inversion, since inverting every stick would invert
movement too.

| Axis | Inverted |
| --- | --- |
| x | A Float's value, or a Vector2's `x`, changes sign. |
| y | A Vector2's `y` changes sign. A Float has no `y`. |

## Toggles

A toggle binding turns an action on with one press and off with the next, for
a player who can't hold a button down.

| Rule | Value |
| --- | --- |
| Button | The binding's `triggered_by` button, or without one its own source, which must then be a Boolean trigger. |
| Press | An action holding its default value takes the value the press gives, as a press binding samples it. An action holding any other value returns to its default value. |
| Release | Changes nothing. |
| Holding | The action holds the toggled value for its seat and device as a held key does, so its tick policy repeats it. |
| Cancel | Ending a seat's or a device's held input, such as when the window loses focus, returns a toggled action to its default value. |

## Input layers

An input layer takes its share of a tick's input before the world's actions
resolve, such as a tool drawn over the game that keeps the clicks it handles.

| Rule | Value |
| --- | --- |
| Order | Each tick, the application runs its layers in the order they were added, then resolves the world's actions. |
| Capture | Input a layer's sink captures doesn't reach later layers or the world's actions. A captured press keeps its control until it's released. |
| Held actions | A world action that's held when a layer starts capturing its input keeps its value until the world's sink cancels it. |
| Window | A resolved action reports the window its input came from: the window the pointer was in, or the focused window for a key. It reports none for input from no window, such as a gamepad, and for a held value repeated by its tick policy. |

## Tick policy

Actions can emit with different policies:

- `OnChange`: emit when input changes
- `OnChangeAndRepeat`: emit when input changes, and again on each key repeat while the key is held
- `WhileActive`: emit every frame while the resolved value is non-default
- `Always`: emit every frame after the action has a known value

A repeating policy emits at most once per tick for each device: the record that
changes the value is that tick's emission, and later ticks repeat the held value.
Movement usually uses `WhileActive` so holding a key or stick keeps producing movement events.
Discrete actions such as fire, view toggle, or exit usually use the default change-based behavior.
Actions that step through something while a key is held, such as deleting text
or moving through a list, use `OnChangeAndRepeat`.

## Key repeat

A key repeat is another press of a key that's still held, at the delay and rate
the operating system's keyboard settings set.

| Rule | Value |
| --- | --- |
| Source | macOS and Windows send the repeats. On Wayland, the application makes them from the delay and rate the compositor sends, and a rate of 0 turns them off. |
| Keys | Every key the platform repeats. Modifier keys don't repeat. On Wayland, only the most recently pressed key repeats, and it stops when that key is released, another key is pressed, or the window loses the keyboard. |
| Typed text | Each repeat of a key that types a character also records that character again. |
| Owner | A repeat belongs to the sink that captured the press, and is hidden from every other sink. It never starts a new interaction or captures a control. |
| Actions | An `OnChangeAndRepeat` action emits one event per repeat, with its held value and the phase `Repeated`. Actions with any other policy don't emit for repeats. |

## Device outputs

A device output is a named value an application sets on a device, such as a
controller's rumble or light. Outputs use the same `Class.Name` names as
triggers, but values flow to the device instead of from it.

| Output | Value | Range | Meaning |
| --- | --- | --- | --- |
| `Gamepad.LowFrequencyRumble` | Float | 0 to 1 | Strength of the heavy motor, usually in the left grip. 0 stops it. |
| `Gamepad.HighFrequencyRumble` | Float | 0 to 1 | Strength of the light motor, usually in the right grip. 0 stops it. |
| `Gamepad.Light` | RGBA | 0 to 1 for each channel | Color of the controller's light. Alpha is ignored. |
| `Gamepad.PlayerLights` | Int | Bit mask | Which player indicator lights are on. Bit 0 is the leftmost light. |

The controllers that accept each output:

| Controller | `LowFrequencyRumble` | `HighFrequencyRumble` | `Light` | `PlayerLights` |
| --- | --- | --- | --- | --- |
| DualShock 4, USB and Bluetooth | Yes | Yes | Yes | No |
| DualSense, USB and Bluetooth | Yes | Yes | Yes | Bits 0 to 4 |
| Xbox One and Series, USB | Yes | Yes | No | No |
| Xbox 360, USB | Yes | Yes | No | No |
| Generic joystick | No | No | No | No |

| Rule | Value |
| --- | --- |
| Holding | A device keeps an output's value until it's set again. Rumble doesn't stop by itself. |
| Several values in one tick | The last value set for a device and output wins. The device receives at most one update per tick. |
| Outputs never set | The controller keeps showing what it showed before, such as its own light color, until the application first sets that output. Setting one output never changes another. |
| Unknown or unsupported output | The value is ignored, and the engine logs one warning for each device and output name. |
| Wrong value type | The value is ignored, and the engine logs one warning for each device and output name. |
| Write access | A controller the engine can only read takes no outputs, and the engine logs one warning for it. This happens on Linux when the device node grants only read access, and on Windows when the controller's driver offers no output reports. |
| Disconnection | Values set on a device that disconnected are discarded. A controller that connects again starts with no outputs set. |
