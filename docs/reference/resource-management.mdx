Resource management is the boundary between content authoring and runtime use.
Byte Engine processes source files into typed data that its rendering, audio,
animation, and other runtime systems can consume without understanding the
source format.

## Core terms

- **Asset**: A source file for your application, such as an image, model, audio
  clip, material declaration, or shader source file.
- **Resource**: Runtime-ready data that Byte Engine produces from an asset. A
  resource includes the metadata and payload needed by an engine system.
- **URL**: A reference to an asset or resource. It can be a path relative to the
  application's `assets` directory or an internet URL. A fragment can select
  one item produced from a container asset.

An asset can produce one resource, several resources, or a resource with
dependencies on other resources. For example, a model can produce meshes,
materials, images, a skeleton, and animation clips.

## Lifecycle

Resource management follows the same boundary whether an application processes
an asset on demand or prepares it before packaging:

1. A tool or application requests a typed resource ID.
2. Byte Engine finds an existing resource or asks an asset handler to process
   the source asset.
3. The handler converts source-format data into engine-format metadata and a
   binary payload.
4. Resource storage publishes the processed result.
5. The caller receives a typed reference with its dependencies resolved.
6. The consuming system reads or streams the payload when it needs the data.

This boundary keeps source-format parsing out of runtime systems. A renderer can
use image dimensions or mesh streams without reopening a PNG or glTF file, and
an audio system can consume processed samples without knowing how they were
authored.

## Assets and processing

Assets remain in formats suited to artists, designers, and content tools.
Common examples include PNG textures, glTF or FBX models, WAV or OGG audio,
`.bema` material declarations, and BESL shader sources.

An asset handler owns the conversion for one family of source files. Processing
can decode or normalize content, derive additional data, compile shaders, and
produce dependencies. Container formats can expose generated resources through
fragments such as a named animation or skeleton.

The processed result is explicit engine data rather than a cached copy of the
source file. This makes the runtime contract independent of authoring format and
lets tools inspect resource metadata without loading the complete payload.

## Resources and references

A stored resource has two conceptual parts:

- **Metadata** identifies and describes the resource. It includes its class,
  content identity, typed model, dependencies, and information needed to read
  the payload.
- **Payload** contains the bytes consumed by the renderer, audio system, or
  another runtime system.

A typed resource reference connects that metadata to a payload reader. Systems
can inspect metadata and resolve dependencies before they read, upload, stream,
decode, or play the payload. Resources with several logical byte ranges can
describe streams so a consumer can address the data it needs.

Resource storage owns persistence and publication. It can choose a physical
layout or encoding without changing the resource's decoded identity or the
typed contract seen by consumers.

## Freshness

A stored resource is **current** when every input its bake observed still has
the fingerprint the bake recorded. Otherwise it's **stale**, and the next
request for it bakes it again. No other rule decides whether a resource is
baked again.

### Bakes and provenance

| Term | Definition |
| --- | --- |
| Bake | One run of an asset handler for one requested ID. It stores the resource with that ID, and can store others, such as the materials and the skeleton of a model. |
| Provenance | What the store records for a resource ID: the inputs its latest finished bake observed, the other resources that bake stored, and the IDs whose bakes store the resource. |
| Producer | An ID whose bake stores a resource with another ID. |

| Resource | Made current by |
| --- | --- |
| A resource whose ID was baked by request | Checking the inputs of its own bake. |
| A resource only a producer stores | Making the producer current. |
| A resource the store has no provenance for | Baking its ID. |

A bake that fails or is interrupted leaves its ID stale, whatever it stored
before it stopped. When a bake finishes, each resource its previous bake stored
and it didn't store again is removed, unless another bake stores it too.

### Inputs

An input is a key and a fingerprint. The key's prefix names its kind.

| Key | Recorded when a bake | Fingerprint | Changes when |
| --- | --- | --- | --- |
| `source:<asset ID>` | Reads a source file, a sidecar, or a directory default, or checks whether one exists. | The file's size and modification time and, for a file the bake read, its content hash; or a record that the file is absent. | The content changes, or the file appears or disappears. A file the bake read that has a new modification time and the same content is unchanged. |
| `resource:<resource ID>` | Uses another bake's stored resource. | The hash of that resource's metadata and decoded payload, or a record that it's absent or failed to bake. | The resource bakes to a different result, appears, or disappears. A resource that bakes again to the same result leaves the resources baked from it current. |
| `query:<class>,<property>=<value>` | Lists the stored resources a [query](/docs/reference/resource-store#queries) matches. | The hash of every match's ID and resource fingerprint. | A match appears, disappears, or bakes to a different result. |
| `listing:<pattern>` | Lists the source files whose ID matches a pattern. | The hash of the matching IDs. | A matching file appears or disappears. |
| `setting:<name>` | Reads a setting. | The value declared under that name, or zero when none is. | The declared value changes, or the name is no longer declared. |

Checking a `resource` or `query` input first makes the resources it names
current, which can bake them.

### Settings

Everything that shapes a bake and isn't a file or a resource is a setting.

| Setting | Read by | Covers |
| --- | --- | --- |
| `handler:<type>` | Every bake of that handler. | The handler's options, such as lightmap UVs for models or the merge threshold for levels. |
| `program-generator` | Every bake that generates a material program. | The generator's code, the [render features](/docs/reference/parameters) it was built with, and whether the build is a debug build. |
| `program-transform` | Every bake of a standalone shader. | The same, for the transform standalone shaders go through. |
| `shader-code` | Every bake that links a shader. | The BESL code that links and lowers shaders. |
| `shader-compiler` | Every bake that compiles a shader. | The platform shader toolchain, its version, and the flags it runs with. |
| `store` | Every bake that stores an image. | The store's texture compression. |

A change to `config.json`, an environment variable, or a command-line argument
makes a resource stale only through a setting the resource's bake read.

A change to the code that defines the store's layout, the engine's
resource-management source, isn't a setting. It resets the whole store through
the [version marker](/docs/reference/resource-store#version-marker).

### Requests

| Request | Result |
| --- | --- |
| A current resource | Nothing is baked. |
| A stale resource | The resources its inputs name are made current, then it bakes. |
| A forced resource | It bakes, and so does every resource its bake uses, each once for the run, whatever their provenance says. No other resource bakes. |
| A resource of an [excluded](/docs/reference/assets#excluded-assets) asset | The request fails. A query doesn't match the resource. |

## Development and release

Debug applications can process missing or stale assets on demand. This shortens
the edit-run loop, but the first request can perform asset-processing work.

Release applications use resources prepared before packaging. They don't need
source assets or processors at runtime, which makes the packaged content
deterministic and keeps authoring dependencies out of the application.

Both workflows produce the same resource model. The difference is when the
asset is processed, not what runtime systems consume.

### Bake stream

A debug application that bakes on demand reports its bakes as a
[debug data stream](/docs/reference/debug-data-streams) named `Assets`, whose
records have the stream `bakes`. A bake is one run of an asset's processor; a
request that finds the resource current bakes nothing and changes no record.
A record is written when a bake starts and when it ends, and carries the state
after that change.

| Field of `data` | Type | Meaning |
| --- | --- | --- |
| `baking` | Array | The bakes running, oldest first. Each has the resource `id`, `requested_by`, the IDs waiting on it outermost first (empty for a bake requested directly), and `elapsed_ms`, the milliseconds since it started. |
| `baked` | Integer | The bakes that stored their resource since the application started. |
| `failed` | Integer | The bakes that ended without storing their resource since the application started. |
| `finished` | Array | The latest 16 bakes to end, newest first. Each has the resource `id`, `requested_by` as in `baking`, `ok`, which is `true` when it stored its resource, and `duration_ms`. |

The key is the `id` of every bake in `baking`, with `baked` and `failed`; a
record where only times changed has the same key.
