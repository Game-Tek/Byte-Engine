Build a release binary, then package it with the resources your application
needs at runtime. Select your operating system for its packaging steps. Your
choice matches the operating system selected in the environment setup guide.

## Build and bundle for macOS

Use [cargo-bundle](https://github.com/burtonageo/cargo-bundle) to package a Byte
Engine application as a macOS `.app`. Bake resources first because
`cargo-bundle` copies files but doesn't process assets.

### 1. Install cargo-bundle

```bash
cargo install cargo-bundle
```

### 2. Bake your application resources

[Install BELD](/docs/develop/resource-management/install-beld), then run
it from the application directory:

```bash
beld --source "$PWD/assets" --destination "$PWD/resources" \
  bake
```

The zero-ID form includes every recognized application asset and the engine
shaders exposed through `assets/byte-engine`. Verify the resulting inventory:

```bash
beld --destination "$PWD/resources" list
```

A release build doesn't compile a missing shader on demand.

Keep `resources/` outside Cargo's `target/` directory. It is an application
input to packaging. Cargo owns `target/` and might remove it when you run
`cargo clean`.

### 3. Declare your bundle contents

Add bundle metadata to the application's `Cargo.toml`:

```toml
[package.metadata.bundle]
name = "My Application"
identifier = "com.example.my-application"
resources = ["resources"]
```

Use a reverse-DNS identifier that you own before distributing the application.
The `resources` entry makes cargo-bundle copy the complete baked directory into
the application bundle.

### 4. Select the bundled resource directory

Let `GraphicsApplication` select the default resource directory during normal
development and release runs:

- In a debug build, it uses `resources/` under `CARGO_MANIFEST_DIR` when Cargo
  provides that directory. Otherwise, it falls back to `resources/` beside the
  executable.
- In a release build, it uses `resources/` beside the executable.
- An explicit `resources.path` value replaces the default. A relative value is
  relative to the process's current working directory.

The `assets-path` default follows the same manifest-first policy in debug
builds. Release builds don't install asset processors, so package the baked
`resources/` directory instead of the source `assets/` directory.

A macOS application bundle is the exception. Its executable lives in
`Contents/MacOS`, but cargo-bundle copies the resource directory to
`Contents/Resources/resources`. Add the override only when the executable is
inside a macOS application bundle:

```rust
use std::path::PathBuf;

use byte_engine::application::{Application, Parameter};

fn bundled_resources_path() -> Option<PathBuf> {
    let executable = std::env::current_exe().ok()?;
    let contents = executable.parent()?.parent()?;

    (contents.file_name()?.to_str()? == "Contents")
        .then(|| contents.join("Resources").join("resources"))
}

let parameters = bundled_resources_path()
    .map(|path| {
        Parameter::new_string(
            "resources.path".to_owned(),
            path.to_string_lossy().into_owned(),
        )
    })
    .into_iter()
    .collect::<Vec<_>>();

let app = GraphicsApplication::new("My Application", &parameters);
```

Outside an application bundle, `parameters` is empty and `GraphicsApplication`
applies the current debug or release directory policy. You can still pass an
absolute `--resources.path` value to select a fixed directory, or a relative
`--resources.path=custom/resources` value to select one from the current working
directory.

### 5. Build the application bundle

```bash
cargo bundle --release --format osx
```

The completed app is written to:

```text
target/release/bundle/osx/My Application.app
```

Its relevant layout is:

```text
My Application.app/
  Contents/
    MacOS/my-application
    Resources/resources/
      resources.db
      ... baked payload files ...
```

Copy the `.app` to `/Applications` or drag it there in Finder to install it
locally. Code signing and notarization are required before distributing it to
other Macs. A DMG is optional distribution packaging layered on top of the
`.app`; it isn't required to run or install the application.

## Build for Linux

Create an optimized application binary from your project directory:

```bash
cargo build --release
```

Cargo writes the binary to `target/release/`.

## Build and bundle for Windows

Bundle the release executable, baked `resources/` directory, Agility SDK, DXC,
and DirectStorage runtimes together. Byte Engine loads these DirectX components
at runtime, so a successful Cargo build doesn't prove that the final application
directory contains the required DLLs.

### 1. Bake your application resources

[Install BELD](/docs/develop/resource-management/install-beld), then bake the
resources for the Windows target from your application directory:

```powershell
beld --source "$PWD\assets" --destination "$PWD\resources" bake
beld --destination "$PWD\resources" list
```

Keep `resources/` outside Cargo's `target/` directory. Cargo owns `target/` and
might remove it when you run `cargo clean`.

### 2. Build the release executable

```powershell
cargo build --release
```

Cargo writes the executable to `target\release\`.

### 3. Get the supported DirectX runtimes

Install Byte Engine's pinned retail runtime set into a local staging directory
with the NuGet CLI:

```powershell
nuget install Microsoft.Direct3D.D3D12 `
  -Version 1.619.5 `
  -OutputDirectory .packages `
  -ExcludeVersion
nuget install Microsoft.Direct3D.DXC `
  -Version 1.9.2607.13 `
  -OutputDirectory .packages `
  -ExcludeVersion
nuget install Microsoft.Direct3D.DirectStorage `
  -Version 1.3.0 `
  -OutputDirectory .packages `
  -ExcludeVersion
```

The [Agility SDK 1.619.5 package](https://www.nuget.org/packages/Microsoft.Direct3D.D3D12/1.619.5)
provides the retail runtime for Shader Model 6.9 and Enhanced Barriers. The
[DXC 1.9.2607.13 package](https://www.nuget.org/packages/Microsoft.Direct3D.DXC/1.9.2607.13)
provides the matching retail shader compiler. Byte Engine also targets the
stable [DirectStorage 1.3.0 package](https://www.nuget.org/packages/Microsoft.Direct3D.DirectStorage/1.3.0).
Don't substitute a preview Agility SDK, preview DXC, or DirectStorage runtime
without updating the GHI contract and rerunning its native DX12 tests.

These runtimes are redistributable under Microsoft's terms, not Byte Engine's
MIT license. Review and comply with the license files in every package before
you distribute it. The Agility SDK provides `LICENSE.txt`; DXC provides
`LICENSE-MS.txt`, `LICENSE-LLVM.txt`, and `LICENCE-MIT.txt`. In the Agility SDK,
`LICENSE-CODE.txt` covers SDK headers and metadata; it isn't the license for the
runtime DLLs.

### 4. Select the matching runtime architecture

Select each package directory that matches the executable's Rust target:

| Rust target | Agility SDK | DXC | DirectStorage |
| --- | --- | --- | --- |
| `x86_64-pc-windows-msvc` | `build\native\bin\x64` | `build\native\bin\x64` | `native\bin\x64` |
| `aarch64-pc-windows-msvc` | `build\native\bin\arm64` | `build\native\bin\arm64` | `native\bin\ARM64` |
| `i686-pc-windows-msvc` | `build\native\bin\win32` | `build\native\bin\x86` | `native\bin\x86` |

Always use one architecture for every runtime and the executable. The `.lib`
files, headers, and WinMD metadata aren't needed at runtime.

### 5. Stage the application directory

This example stages an x64 application named `my-application`:

```powershell
$applicationName = "my-application"
$bundleDirectory = Join-Path $PWD "dist\$applicationName"
$agilityDirectory = Join-Path $PWD `
  ".packages\Microsoft.Direct3D.D3D12\build\native\bin\x64"
$dxcDirectory = Join-Path $PWD `
  ".packages\Microsoft.Direct3D.DXC\build\native\bin\x64"
$directStorageDirectory = Join-Path $PWD `
  ".packages\Microsoft.Direct3D.DirectStorage\native\bin\x64"
$agilityBundleDirectory = Join-Path $bundleDirectory "D3D12"

New-Item -ItemType Directory -Force -Path $bundleDirectory | Out-Null
New-Item -ItemType Directory -Force -Path $agilityBundleDirectory | Out-Null
Copy-Item -LiteralPath "target\release\$applicationName.exe" `
  -Destination $bundleDirectory -Force
Copy-Item -LiteralPath "resources" `
  -Destination $bundleDirectory -Recurse -Force
Copy-Item -LiteralPath "$agilityDirectory\D3D12Core.dll" `
  -Destination $agilityBundleDirectory -Force
# Include the matching debug layer only in development and test bundles that enable validation.
Copy-Item -LiteralPath "$agilityDirectory\d3d12SDKLayers.dll" `
  -Destination $agilityBundleDirectory -Force
Copy-Item -LiteralPath "$dxcDirectory\dxcompiler.dll" `
  -Destination $bundleDirectory -Force
Copy-Item -LiteralPath "$dxcDirectory\dxil.dll" `
  -Destination $bundleDirectory -Force
Copy-Item -LiteralPath "$directStorageDirectory\dstorage.dll" `
  -Destination $bundleDirectory -Force
Copy-Item -LiteralPath "$directStorageDirectory\dstoragecore.dll" `
  -Destination $bundleDirectory -Force
```

The resulting files must keep this layout, whether you distribute a ZIP,
installer, or MSIX package:

```text
my-application/
  my-application.exe
  dxcompiler.dll
  dxil.dll
  dstorage.dll
  dstoragecore.dll
  D3D12/
    D3D12Core.dll
    d3d12SDKLayers.dll  # Development and test validation only
  resources/
    resources.db
    ... baked payload files ...
```

Keep DXC and DirectStorage beside the executable, and keep `D3D12Core.dll` in
the `D3D12` child directory. The engine requests that exact directory through
the retail independent-device API. Keep the matching `d3d12SDKLayers.dll` there
while testing with validation, but remove it from production installers as
Microsoft recommends. Don't place runtime DLLs inside `resources/`, install
them into a Windows system directory, or rely on a developer machine's `PATH`.

### 6. Verify the completed bundle

Check the staged files, then run the application from that directory:

```powershell
$requiredBundleFiles = @(
  "$bundleDirectory\$applicationName.exe",
  "$bundleDirectory\dxcompiler.dll",
  "$bundleDirectory\dxil.dll",
  "$bundleDirectory\dstorage.dll",
  "$bundleDirectory\dstoragecore.dll",
  "$bundleDirectory\D3D12\D3D12Core.dll",
  "$bundleDirectory\resources\resources.db"
)

$missingBundleFiles = $requiredBundleFiles |
  Where-Object { -not (Test-Path -LiteralPath $_) }

if ($missingBundleFiles.Count -ne 0) {
  throw "The Windows bundle is missing: $($missingBundleFiles -join ', ')"
}

& "$bundleDirectory\$applicationName.exe"
```

Test the bundle on a clean Windows machine or VM that doesn't have these SDKs
installed. Startup verifies the Agility SDK, Shader Model 6.9, native 16-bit and
64-bit shader operations, wave operations, and Enhanced Barriers. Also exercise
a file-to-buffer or file-to-image load because startup might not create a
DirectStorage queue.

<Callout type="info" title="Run the native DX12 tests">
	Cargo doesn't copy app-local runtimes beside hashed test executables. Point
	the engine at the Agility SDK directory, add DXC and DirectStorage to `PATH`
	for the test process, then restore the previous values:

```powershell
$agilityDirectory = Resolve-Path `
  ".packages\Microsoft.Direct3D.D3D12\build\native\bin\x64"
$dxcDirectory = Resolve-Path `
  ".packages\Microsoft.Direct3D.DXC\build\native\bin\x64"
$directStorageDirectory = Resolve-Path `
  ".packages\Microsoft.Direct3D.DirectStorage\native\bin\x64"
$savedProcessPath = $env:PATH
$savedAgilityPath = $env:BYTE_ENGINE_D3D12_SDK_PATH

try {
	$env:BYTE_ENGINE_D3D12_SDK_PATH = "$agilityDirectory\"
	$env:PATH = "$dxcDirectory;$directStorageDirectory;$savedProcessPath"
	cargo nextest run -p byte-engine-ghi dx12
} finally {
	$env:PATH = $savedProcessPath
	$env:BYTE_ENGINE_D3D12_SDK_PATH = $savedAgilityPath
}
```
