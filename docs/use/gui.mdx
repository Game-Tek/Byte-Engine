Use the early UI module to build retained, asynchronous interfaces inside the
Byte Engine render loop.

An asynchronous component function receives a layout `Context`. It creates
elements in stable keyed slots, waits for events, and can mount child components
that return values. The runtime keeps state between evaluations, so your
application doesn't rebuild each interaction from the beginning.

```rust
engine.mount(async |ctx| {
    let mut panel = ctx
        .element("panel")
        .container(|c| card(c).width(240.into()).flow(flow::column))
        .await;
    panel.element("title").text("Settings", |t| t.font_size(20.0)).await;
    panel.element("clock").component(clock).await;
});
```

Pass components as async closures or async functions that take
`&mut EvaluationContext`, such as `async fn clock(ctx: &mut EvaluationContext)`.

## Choose the main API

- `layout::engine::Engine` evaluates retained UI and produces render data.
- `Context` and `ContainerContext` are the component-facing construction and event APIs.
- `Container`, `Text`, `Image`, `Curve`, and `Path` are the current built-in primitives. Declare a text field with `text_field`: it's a `Text` that receives text edits while focused.
- `UiRenderPass` turns evaluated UI render data into GPU draw work.
- `ConcreteStyle`, `ConcreteLayer`, and `Transform` hold styling and animation-oriented transforms; set opacity with the `opacity` property.

The layout layer stays small by design.
Containers own sizing, positioning, flow, clipping, style, and visual data.
Flow functions such as row, column, grid, and centered variants place children.
Elements you declare directly in a mount are laid out from the window's top-left
corner: give each one an absolute position, or it sits at the corner. To keep one
against another edge or centered, anchor it as described in [Pin an element to an
edge or the center](#pin-an-element-to-an-edge-or-the-center). They don't
flow after each other, so each mount, such as a heads-up display and a pause menu, places
its own elements. When two overlap, the one declared later paints on top.
Transforms are best treated as animation and presentation state, while position and sizing describe stable layout.
A transform applies to the whole subtree: a scaled container scales its
descendants' rectangles, hit bounds, clipping, curve points, stroke widths, and
font sizes together, so one transform on a content layer zooms a canvas.

## Draw text with your own fonts

Without fonts of its own, the UI draws text with a system font. To ship your
own, put `.ttf` or `.otf` files in your assets directory, load each once at
startup, and give the same list to the engine and to the render pass, so text
is measured and drawn alike. Name each font by its asset ID; the first one is
the default:

```rust
let runtime = build_single_threaded_async_runtime();
let load = |id| {
    runtime
        .block_on(byte_engine::ui::load_font(app.resource_manager(), id))
        .unwrap_or_else(|error| panic!("{error}"))
};
let fonts = [
    ("Inter-Regular.ttf", load("Inter-Regular.ttf")),
    ("Inter-SemiBold.ttf", load("Inter-SemiBold.ttf")),
];
setup_ui_render_pass(&mut app, None, "ui", &ui_renders, &fonts);
let mut engine = Engine::with_context(model).with_fonts(&fonts);
```

Text uses the default font unless it names another. Use a heavier font for a
title, for example:

```rust
panel.element("title").text("Settings", |t| t.font("Inter-SemiBold.ttf").font_size(20.0)).await;
```

Each font bakes into a [`Font` resource](/docs/reference/assets#fonts) like any
other asset, so a release build reads it from the resource store.

## Draw one interface over another

Give each interface its own engine, its own render factory, and its own UI pass
when they come from different code, such as a game's heads-up display and a
tool that installs itself over the game. Each pass draws over everything
registered before it, so register the one that goes on top last:

```rust
let hud_renders = Factory::new();
setup_ui_render_pass(&mut app, None, "hud", &hud_renders, &[]);
let editor_renders = Factory::new();
setup_ui_render_pass(&mut app, None, "editor", &editor_renders, &[]);
```

Give every pass a different name. The name is how you hide one at runtime: set
`render.pass.editor` to `bypassed` to hide the editor and keep the heads-up
display. A second pass with a name already in use stops the application at
startup.

## Open an interface in a window of its own

To show an interface in its own operating system window, such as a tool beside
the game, create the window without a camera and register a UI pass for that
window alone, in the same tick:

```rust
let tool = app.window_factory().create(Window::new("Tool", Extent::rectangle(800, 600)));
let tool_renders = Factory::new();
setup_ui_render_pass(app, Some(tool), "tool", &tool_renders, &[]);
```

The window shows only the passes registered for it, drawn over black. Give the
interface its own engine, sized to the window, and publish its renders to
`tool_renders`. Passes registered with `None` draw only in windows with a
camera, so the game's own interface stays out of the tool's window. See
[windows](/docs/reference/rendering#windows) for the rules.

## Pin an element to an edge or the center

To keep an element in a corner or centered however its parent resizes, anchor
it instead of computing its position from the parent's size. Pick an `Anchor`
for each axis: `Start` measures from the left or top edge, `Center` from the
center, and `End` from the right or bottom edge, with the distance moving the
element into the parent.

```rust
use byte_engine::ui::{Anchor, Position};

// 48 units from the window's bottom-right corner, at any window size.
let mut status = root
	.element("status")
	.container(|c| {
		c.position(Position::anchored(Anchor::End(48.0), Anchor::End(48.0)))
			.width(272.into())
			.height(92.into())
	})
	.await;

// Centered on the window.
root.element("crosshair")
	.container(|c| {
		c.position(Position::anchored(Anchor::Center(0.0), Anchor::Center(0.0)))
			.width(12.into())
			.height(12.into())
	})
	.await;
```

An element declared directly in a mount anchors to the window, so pass the
window's layout size to `Engine::evaluate` and the anchored elements follow
every resize; see [Keep an interface the same size on every display](#keep-an-interface-the-same-size-on-every-display).
Inside a container, the anchor measures from that container's box.

## Keep an interface the same size on every display

Lay your interface out at the window's layout size, not its size in pixels.
The application divides the window's pixels by the display's scale and by the
`ui.scale` setting, so a 260-unit panel is as wide on a Retina display as on
any other, and a larger window shows more around your interface instead of
shrinking it.

1. Remember which window your interface draws in from its resize event:

   ```rust
   while let Some(event) = window_events.read() {
       if let Event::Window { window: id, event: Events::Resize { .. } } = event {
           window = Some(id);
       }
   }
   ```

2. Each frame, evaluate at the size the application gives for that window. It
   changes when the window resizes, moves to another display, or `ui.scale`
   changes:

   ```rust
   if let Some(size) = window.and_then(|id| app.layout_size(id)) {
       engine.evaluate(size, app.frame_allocator());
   }
   ```

To draw something at its real pixel size, such as a render image your
interface shows, multiply its layout size by `app.ui_scale(id)`. The scale
rules are in [Scale](/docs/reference/gui#scale).

## Draw vector images

To draw an icon or another picture made of shapes sharp at any size, put its
`.svg` file in your assets and load it with `load_vector`. The bake keeps the
shapes, colors, gradients, and glass blurs the UI can draw, and fails with an
error that says what to change when a file uses something it can't; the
[SVG reference](/docs/reference/svg) lists what it keeps. Draw the image with
`draw_vector`:

```rust
use byte_engine::ui::{draw_vector, load_vector};

let runtime = build_single_threaded_async_runtime();
let play = runtime
    .block_on(load_vector(app.resource_manager(), "icons/play.svg"))
    .unwrap_or_else(|error| panic!("{error}"));

// Inside a component: a 24 unit wide icon, as tall as its view box's shape.
let mut icon = draw_vector(&mut button, "icon", &play, 24.0, []).await;
```

A centering flow lines the image up by where it looks centered, not by its
box, so a play triangle sits toward its flat side. The bake measures that point
once; see [Visual center](/docs/reference/gui#visual-center).

To build an image in code, give `Vector::new` its view box and its layers. A
layer without a paint of its own takes the colors you pass to `draw_vector`,
and `tint` on the returned view changes them later, such as when a button is
under the pointer:

```rust
use byte_engine::ui::{CurvePath, FillRule, Vector, VectorLayer, draw_vector};

let mut square = CurvePath::new(16.into(), 16.into());
let corners = [(2.0, 2.0), (14.0, 2.0), (14.0, 14.0), (2.0, 14.0)];
for (index, &corner) in corners.iter().enumerate() {
    square.push_line(corner, corners[(index + 1) % corners.len()]);
}
let square = Vector::new([16.0, 16.0], vec![VectorLayer::plain(square.segments().to_vec(), FillRule::NonZero)]);

let mut icon = draw_vector(&mut button, "icon", &square, 16.0, [ConcreteLayer::default().color(gray.into())]).await;
icon.tint(white).await;
```

## Light a surface with a gradient

To shade a panel or a button from one color to another, give a layer a
`LinearGradient` as its color. Place its two points with `relative`, as
fractions of the element's box, so the gradient keeps spanning the element
when it resizes, such as a panel that fits its content:

```rust
use byte_engine::ui::{ConcreteLayer, LinearGradient};

// Lighter at the top edge, darker at the bottom edge, at any height.
let lit = LinearGradient::relative([0.0, 0.0], [0.0, 1.0], top, bottom);
panel.update_container(|c| c.style([ConcreteLayer::default().color(lit.into())])).await;
```

Use `new` instead to place the points in the element's own units, such as a
gradient that ends 12 units below the top edge whatever the element's height.

## Round some corners and border some sides

To round only some corners, such as a tab rounded on top, give the container
`corner_radii` with a radius for each corner: top left, top right, bottom right,
then bottom left. To draw a line on only some sides, such as a rule under a
header, give a stroke layer `stroke_sides` with a width for each side: top,
right, bottom, then left.

```rust
use byte_engine::ui::ConcreteLayer;

// Rounded on top, with a rule along the bottom edge.
let rule = ConcreteLayer::default().color(line.into()).stroke_sides([0.0, 0.0, 1.0, 0.0]);
tab.update_container(|c| c.corner_radii([8.0, 8.0, 0.0, 0.0]).style([fill, rule])).await;
```

`corner_radius` and `stroke` set all four at once. Radii that overlap on a side
shrink together until they fit, and a clipping container keeps its children
inside its border's inner edge, whatever the sides' widths.

## Fade a layer's edges

To soften a panel so it fades into the scene instead of ending at a hard edge,
give its layer a feather. The layer fades from transparent at the element's edge
to its full color that many layout units inside it, on each edge you set.

```rust
use byte_engine::ui::ConcreteLayer;
use byte_engine::utils::RGBA;

// A dark band that fades out over its left 114 units.
panel.update_container(|c| {
	c.style([ConcreteLayer::default()
		.color(RGBA::new(0.0, 0.0, 0.0, 0.55).into())
		.feather_edges(0.0, 0.0, 0.0, 114.0)])
})
.await;
```

A feather fades a container's fill, stroke, and backdrop blur layers. When the
container clips, its first feathered layer also fades its children, so content
scrolled toward a faded edge fades with the background.

## Handle events and focus

UI events are futures that your component can await.
A component can wait for pointer-style events, keys, text edits, timers, or render ticks.
Containers ignore the pointer until you turn on `hit_testable(true)`, so turn it
on for each container that takes clicks, hovers, drags, or drops, such as a
button or a drop target. Everything else, such as a panel, a label's frame, or
a heads-up display, lets the pointer through to what's under it.
Text input is app-owned: a text field emits edit deltas such as inserted and deleted characters, and application state decides how to apply them. Write the result back with `update_text`.

Keys and typed text go to the focused element on their own. A component requests
focus for the element that should take them, such as a text field it just
declared, and releases it when it's done. Each absolute-depth layer, such as a
modal, keeps its own focused element, and the highest one takes the keys, so
opening a modal doesn't take focus from the screen under it.

A press elsewhere in the same layer takes focus away, while a press on the
element, inside it, or on the hit-testable container that holds it doesn't. To end typing
when that happens, await `focus_change(true)` beside the field's text edits:

```rust
input.request_focus().await;
loop {
	select! {
		edit = input.on_text_edit() => { /* apply the edit */ },
		_ = input.on_key(Key::Enter) => break,
		_ = input.focus_change(true) => break,
	}
}
```

## Read and change engine state

A component never holds the engine. Every change it makes is a future: declaring
an element, `update_container`, `remove`, `reparent`, focus requests, and
starting a component. Await it, and it writes straight into the engine while
your component runs, in the order you awaited them. The next layout sees the
change, and so do components that run after yours in the same evaluation.

Declarations and edits take a setup function that sets properties in place,
such as `|c| c.width(240.into()).clip(false)`. A new container paints nothing
until you give it a style, so a container that only arranges its children
needs no setup for its look. The setters write into the
element where the engine stores it, so nothing is built, copied, or sent on the
way. Setup runs only when the declaration creates the element. An element that
already exists keeps its properties until you edit it. A plain function over
`Properties` holds a reusable look for both declarations and edits:

```rust
fn card(card: Properties<'_, Container>) -> Properties<'_, Container> {
    card.corner_radius(8.0).style([fill, border])
}

let mut panel = ctx.element("panel").container(|c| card(c).width(240.into())).await;
panel.update_container(|c| card(c).opacity(0.5)).await;
```

To keep steady screens free of allocations, pass text as a `&str`, a number, or
`format_args!("{name} {score}")` instead of a formatted `String`, and style
layers as an array, such as `.style([fill, border])`. The engine reuses the
storage of removed elements, render entries, and ended components, so a screen
that opens again allocates only one box for each component or mount it starts.

To move an element over time, see [Animate an element](#animate-an-element).

Reads are futures that complete at once. Await them in the component:

```rust
let bounds = card.geometry().await.map(|geometry| geometry.logical);
let pointer = ctx.pointer().await;
let held = ctx.drag().await;
let score = ctx.with(|app: &App| app.score.get()).await;
```

`Context::with` lends the application context you passed to
`Engine::with_context`. The host reaches the same value between evaluations
through `Engine::ctx` and `Engine::ctx_mut`.

A geometry read returns two boxes. Use `logical` for interaction, such as
turning the pointer into a local position, because the pointer hits that box.
Use `display` to follow what's seen.

## Follow application state

To show a value that changes outside your component, such as the selection or a
worker's progress, follow it as a reactive value and update your elements each
time it changes. The first wait resolves at once with the current value, so the
same code shows the starting state and every later change.

Follow a value your application keeps in its context with `Context::proactive`.
Pass a function that reads it:

```rust
let mut selected = ctx.proactive(move |app: &App| app.selected == Some(id));
loop {
    select! {
        _ = row.on(Events::Actuated) => ctx.with(move |app: &mut App| app.selected = Some(id)).await,
        selected = selected.next() => {
            row.update_container(|c| c.style(row_style(*selected))).await;
        }
    }
}
```

The read runs only after the application context was written, and a read equal
to the last one isn't a change. It never asks for a frame, so a screen whose
components wait only on reactive values and events stays idle. Write the
context before you call `Engine::evaluate`, and read it with `Engine::ctx` when
you don't change it: every `Engine::ctx_mut` counts as a write. Keep the value
small, such as a flag, a count, or a position, since each read builds it again.

To let an idle screen cost nothing, evaluate only when the engine asks. Call
`Engine::next_tick` each frame, and skip `Engine::evaluate` until the tick it
returns has come, unless the window's size changed:

```rust
let due = engine.next_tick().is_some_and(|tick| tick <= Instant::now());
if due || size != laid_out {
    engine.evaluate(size, &frame_allocator);
    laid_out = size;
}
```

Input you feed the engine and edits your components make in response to it ask
for the ticks they need, so nothing is missed. For the same reason, write the
context only when a value changes: compare through `Engine::ctx` first.

Follow a value that another thread produces, or one too large to compare, with
a `Watch`. Write it with `Watch::set` or `Watch::update`, and pass a subscriber
to `Context::reactive`:

```rust
let mut progress = ctx.reactive(app_progress.subscribe());
loop {
    let percent = *progress.next().await;
    label.update_text(|t| t.content(format_args!("{percent}%"))).await;
}
```

A value that depends on time doesn't change by itself. To act once the user
held still for a second, wait on a timer beside the value, and start again when
the value changes first:

```rust
select! {
    _ = gesture.next() => continue,
    _ = ctx.wait(Duration::from_secs(1)) => show_hints(ctx).await,
}
```

## Animate an element

An animation is a value your component owns: where it's headed, where it
stands, and how fast it's moving. A run applies it to one container, frame by
frame, through callbacks you write. You decide which properties each value
drives. For motion your loop heads somewhere new as things change, such as a
drawer that follows whether it's open, hand the animation to the engine
instead; see [Follow a changing target](#follow-a-changing-target).

1. Create the animation with its starting value and a motion, such as a curve
   from `ease_out` or a `Spring`.
2. Set its target.
3. Run it on a container. In `on_every_frame`, write the current value to the
   properties that show it, then await the run.

```rust
let mut shown = Animation::new(0.0, ease_out(0.35));

shown.set_target(1.0);
toolbar
    .animate(&mut shown)
    .on_every_frame(|c, v| c.opacity(v.current).transform(Transform::identity().translate_y((v.current - 1.0) * 60.0)))
    .await;
```

The run resolves once the animation settles. Call `on_start` for what should
change once, as the run begins, and `on_end` for what should change once it's
over.

### Follow a changing target

Give the animation to the engine with `animation`, and keep the handle it
returns. The engine moves the animation on every frame until it settles, and
calls your callback to draw each frame. Your loop only sets targets, so it
needs no branch for the motion.

1. Get the ids of the containers the value drives with `id`.
2. Call `animation` with the animation and a callback that edits those
   containers through `update_container`, then await it for the handle.
3. Set the handle's target wherever your loop learns where it should go.

```rust
let id = drawer.id();
let shown = ctx
    .animation(Animation::new(0.0, ease_out(0.35)), move |frame, v| {
        frame.update_container(id, |c| c.transform(Transform::identity().translate_x((v.current - 1.0) * 300.0)))
    })
    .await;

let mut open = ctx.proactive(|app: &App| app.drawer_open);
loop {
    let open = *open.next().await;
    // Turned around partway, it heads back from where it stands.
    shown.set_target(if open { 1.0 } else { 0.0 });
}
```

To change the motion and the target together, call `update` with a closure
that changes the animation. Dropping the handle stops the animation.

To wait for the motion, await one of the handle's waits:

- `settled()` resolves once the animation stands at its target, at once when it
  already does. Await it to finish a motion before what follows, such as
  removing a panel after it leaves.
- `moved()` resolves after the next frame that draws the animation, with where
  it stands, and stays pending while the animation is at rest. Wait on it in a
  `select!` to follow the motion with something the callback can't edit, such
  as your application's state.

```rust
select! {
    _ = open.next() => {},
    shown = shown.moved() => ctx.with(move |app: &mut App| app.drawer_shown = shown).await,
}
```

### Interrupt an animation

Drop a run to stop it, such as by losing a `select!`. The container keeps the
values the run wrote last, and the animation keeps where it stands and how fast
it moves. Set a new target and run it again, and the motion turns around from
there: a spring keeps its speed, and a curve starts over from where it stands.

```rust
let mut shown = Animation::new(0.0, ease_out(0.35));
loop {
    shown.set_target(if open { 1.0 } else { 0.0 });
    select! {
        _ = toolbar.animate(&mut shown).on_every_frame(|c, v| c.opacity(v.current)) => {
            open = toggled(ctx, open).await;
        },
        // Toggled again before the toolbar arrived: the next run starts where this one stopped.
        changed = toggled(ctx, open) => open = changed,
    }
}
```

An `on_end` runs on an interruption too, with `Ending::Interrupted`, so it can
put the container in a state it should never stay in mid-motion. It runs before
any other change, so a run that starts in the same frame starts from what it
left.

```rust
dial.animate(&mut pose)
    .on_every_frame(|c, v| c.opacity(v.current))
    .on_end(|c, _, ending| match ending {
        Ending::Settled => c.position(PARKED),
        Ending::Interrupted => c,
    })
    .await;
```

### Animate a container's size without reflowing

Give the container its final size at once and animate only how big it looks.
The width and height are the logical size: they place the container, give its
children their space, and take pointer hits. The display width and height are
the box it's painted at and clips its children to. A run serves both: the
target for the logical size, and the current value for the display size.

```rust
let mut height = Animation::new(start, emphasized_out(0.25));
height.set_target(end);
panel
    .animate(&mut height)
    .on_start(|c, v| c.height(Sizing::pixels(v.target)))
    .on_every_frame(|c, v| c.display_height(Sizing::pixels(v.current)))
    .on_end(|c, _, _| c.display_height(Sizing::full()))
    .await;
```

The display box grows from the container's top-left corner. Children never move
while it animates, and a display edit doesn't rerun layout. Only containers
have a display size.

### Animate more than one value

An animation's value can be a number, a fixed array of numbers, a `Size`, an
`Offset`, a color, or a pair of these. Each number moves on its own, so a spring
keeps a speed for each. To drive several elements from one value, give the
animation to the engine with `animation`, and edit each element by its id in
the callback.

```rust
let (knob_id, fill_id) = (knob.id(), fill.id());
let position = ctx
    .animation(Animation::new(0.0, ease_out(0.2)), move |frame, v| {
        frame.update_container(knob_id, |c| c.absolute_position(v.current, 0.0));
        frame.update_container(fill_id, |c| c.width(v.current.into()));
    })
    .await;
```

## Follow a player's accessibility settings

Some players get sick from movement on screen, and some need larger text. Your
interface follows both the player's operating system settings and the
`accessibility.motion` and `accessibility.text-scale` settings, without changes
to your components:

- Under reduced motion, every animation reaches its target without moving, and
  motion blur turns off. Callbacks still run and waits still resolve.
- Under a text scale above 1, every text lays out and draws larger, and the
  containers that fit it grow with it.

Each frame, before you evaluate, pass both to your engine:

```rust
engine.set_motion(app.motion());
engine.set_text_scale(app.text_scale());
```

Motion blur follows the setting without any code. Leave room for larger text:
give labels containers that fit their content or fill the space left, instead
of fixed sizes. The rules are in [Reduced motion](/docs/reference/gui#reduced-motion)
and [Text scale](/docs/reference/gui#text-scale).

## Give a child the space its siblings leave

To let a list take the height between a header and a footer, set its height to
`Sizing::fill()`. A fill child takes what the flow's other children and gaps
leave along the flow's main axis, across for a row and down for a column, so it
follows the window as it resizes without a height to work out. Several fill
children share that space equally. Across the main axis, fill is the same as
full.

```rust
let mut panel = ctx
    .element("panel")
    .container(|c| c.flow(flow::column_with_gap(6)))
    .await;
panel.element("header").container(|c| c.height(32.into())).await;
panel.element("list").container(|c| c.height(Sizing::fill())).await;
panel.element("footer").container(|c| c.height(24.into())).await;
```

A flow that doesn't move its cursor, such as `flow::center`, has no main axis,
so its fill children are full on both axes.

## Wrap a long text

To break a message into lines that fit its container, turn on `wrap`. The text
takes the width its parent offers and breaks at spaces, so its height grows a
line at a time. Put it in a container with a fit height to let the container
grow with it:

```rust
let mut card = ctx
    .element("card")
    .container(|c| c.width(300.into()).height(Sizing::fit()).flow(flow::column))
    .await;
card.element("message")
    .text(&message, |t| t.font_size(12.0).wrap(true))
    .await;
```

A word wider than the line keeps a line of its own and runs past the edge;
words are never broken. A text field never wraps.

## Size a container to its content and animate its resize

To make a menu, toast, or panel hug what's inside it, set its width or height to
`Sizing::fit()`. The container takes the extent of its flow children, so it
grows when you add a row or lengthen a label, with no size to keep in sync.

```rust
let mut menu = ctx
    .element("menu")
    .container(|c| c.size(Sizing::fit()).flow(flow::column_with_gap(4)))
    .await;
```

A fit size changes the moment its content does. To glide to the new size
instead, follow the logical size with an animation and run it on the display
size:

1. Wait for the first layout's size with `logical_size_change`, and start the
   animation there.
2. Set the target to each new size `logical_size_change` reports, and run the
   animation until it settles or the size changes again.

```rust
fn display(c: Properties<'_, Container>, size: Size) -> Properties<'_, Container> {
    c.display_width(Sizing::pixels(size.x())).display_height(Sizing::pixels(size.y()))
}

let first = menu.logical_size_change(Size::new(0, 0)).await;
let mut size = Animation::new(first, Spring::default());
loop {
    // The run borrows the animation, so read the size it heads to first.
    let target = size.target();
    select! {
        _ = menu.animate(&mut size).on_every_frame(|c, v| display(c, v.current)) => {
            // Settled: wait for the content without asking for frames.
            size.set_target(menu.logical_size_change(target).await);
        },
        changed = menu.logical_size_change(target) => size.set_target(changed),
    }
}
```

A new target keeps the spring's value and speed, so content that changes again
mid-animation bends the motion instead of restarting it. Children lay out at
the final size at once, and the display box clips them while it catches up.
Pointer hits use the logical size, so a new row takes clicks right away.

The menu's siblings follow its logical size, so they move at once. To make them
glide too, wrap the fitting content in a container whose logical size you
animate: write the current value to the outer container's `width` and `height`
instead of its display size. Animating a logical size reruns layout each frame,
so keep it for content that's small.

### Test an animation

Advance the engine's clock by hand with `Engine::advance_clock`, then evaluate.
From then on, each frame's time is what you advanced, so a test can stop in the
middle of a run or a handle's motion and check what it wrote.

## Show one component per item of a list

To keep a row per item of a list in your application state, declare the rows
with `EvaluationContext::each`. Give it a closure that borrows the list, and a
component to run for each item. Items must implement `Hash`, since each item is
keyed by its own hash. The engine reads the list again whenever your state
changes: it starts a component for each new item, removes the component and its
elements for each item that left, and keeps the rest in list order:

```rust
list.each(|app: &App| &app.visible, async |row, handle: Handle| {
    entity_row(row, handle).await
})
.await;
```

A component that stays isn't given its item again, so when an item's data
changes under the same key, read it from your state by key, as you would with
`proactive`. Equal items count as one.

When items don't implement `Hash`, or their identity is one field and not the
whole value, key them with `EvaluationContext::each_by` and a closure that
returns the key:

```rust
list.each_by(|app: &App| &app.toasts, |toast| toast.id, async |slot, toast: Toast| {
    toast_card(slot, toast.id).await
})
.await;
```

Both return once the collection is set up, and the collection lives as long as
the element it was declared on. Declare one collection per element.

## Understand component lifetime

A component started with `component` runs until its future returns or until the
removal of the scope that started it, whichever comes first. A scope is the one a
`mount` created: when the mounted future completes or is dropped, its elements
are removed and every component started inside it ends, including components
those components started. Components started outside any mount live until they
return or the engine is dropped.

`EvaluationContext::remove` removes one element together with everything
declared under it: its descendants and the components started there. The
context it was called on stays valid only to declare the same key again, which
gets the same id. A mounted component awaited from outside the removed element
keeps running until its own future ends. Its elements are gone, so its updates
change nothing.

## Build content at runtime

`Context::element` takes an `ElementKey`. An element's id is computed from its
parent's path and its key, so the same key under the same parent always
resolves the same retained element. A static name identifies a fixed part of a
component. A name made from data, such as one node of a graph, is keyed by its
content. Pass it as `format_args!`, which is hashed while it's formatted
without allocating. An owned `String` with the same content gives the same key:

```rust
let mut node = canvas.element(format_args!("node-{id}")).container(|c| node_frame(c, position)).await;
let mut wire = canvas.element(format_args!("wire-{from}-{to}")).curve(|c| wire_between(c, a, b)).await;
```

Siblings under one parent need distinct keys. For a list, pair a name with the
item's index:

```rust
for (index, row) in rows.iter().enumerate() {
    list.element(("row", index)).container(|c| row_frame(c, row)).await;
}
```

Declaring the same key twice under the same parent in one frame is an error:
the engine logs it, ignores the second declaration, and fails a debug assertion.

Keep the element contexts as the handles to that content. Re-route a wire while
its ends move with `EvaluationContext::update_curve`, editing the path in place
so its segment buffer is reused. Changing only the segments repaints the curve
without replaying layout. Remove a node or a wire with
`EvaluationContext::remove`:

```rust
wire.update_curve(|c| c.clear_segments().cubic(from, from + tangent, to - tangent, to)).await;
node.remove().await;
```

## Send the pointer to the interface

The engine reads clicks and drags from one stream of pointer input. Create a
position action with
`ActionBindingDescription::new("Pointer.Position").dragged_by("Pointer.LeftButton")`
in your UI's input sink, and forward its phases in normalized window
coordinates. Forward a plain `Pointer.Position` action too, so hover follows the
pointer while no button is down. In this example, `accept_drop` maps a released
source to your data and validates the application target before changing
application state:

```rust
match phase {
    ActionPhase::Started => {
        if !engine.pointer_pressed(window_position) {
            // The interface didn't take the press; give it to the game.
        }
    }
    ActionPhase::Updated => {
        engine.pointer_moved(window_position);
    }
    ActionPhase::Ended => {
        if let Some(drop) = engine.pointer_released(window_position) {
            accept_drop(drop);
        }
    }
    ActionPhase::Cancelled => {
        engine.cancel();
    }
    ActionPhase::Repeated => {}
}
```

`Engine::pointer_pressed` holds the surface under the pointer until the release
and returns whether it found one, so a press on empty space can go to the game
instead. The release decides what the press was: a release on the pressed
surface, before the pointer traveled the drag threshold, is a click, which the
surface hears as `Events::Actuated`. A press that traveled the threshold is a
drag, and never clicks, even when it comes back.

Capture the gesture in your UI's sink before gameplay processes the same
input, and continue forwarding motion and release outside the source.
`Engine::hit` answers what's under a point when a sink needs that for its own
capture decisions, such as refusing a drop over UI.

## Click an element from a test

Find an element by the keys you declared it with, from the root down through
every component, with `Engine::find`. It returns the element's geometry from the
last evaluated frame, so a test can press and release at its center:

```rust
engine.evaluate(size, &allocator);
let save = engine.find(["toolbar", "save"]).expect("the save button is laid out").logical;
let center = UiPoint::new(
    (save.x() + save.width() * 0.5) / size.x() as f32 * 2.0 - 1.0,
    1.0 - (save.y() + save.height() * 0.5) / size.y() as f32 * 2.0,
);
engine.pointer_pressed(center);
engine.pointer_released(center);
engine.evaluate(size, &allocator);
```

The button's component hears `Events::Actuated` in the second evaluation.

## Drag a UI item onto an application target

Forward the pointer as [Send the pointer to the interface](#send-the-pointer-to-the-interface)
shows. A press that travels past the drag threshold drags the surface it
pressed, and `Engine::pointer_released` returns the drop.

The grabbed surface receives the gesture as events, so it can react on its own.
It gets `Events::Grabbed` on press. Once the pointer travels past the drag
threshold, it gets `Events::Dragged` at the start of each `Engine::evaluate` in
which the pointer moved, with `UiEvent::delta` set to the offset from the press
point in layout units. When the grab ends by release or cancellation it gets
`Events::DragEnded`, with `UiEvent::source` set to the surface the drag was
dropped on, if any. Await all three in one loop, because an event with no
component waiting for it's discarded, and a press and release can arrive in
the same frame:

```rust
let mut origin = None;
loop {
    let event = select! {
        event = card.on(Events::Grabbed) => event,
        event = card.on(Events::Dragged) => event,
        event = card.on(Events::DragEnded) => event,
    };
    match event.kind {
        Events::Grabbed => {
            origin = card.geometry().await.map(|geometry| geometry.logical);
            card.update_container(|c| c.depth(Depth::absolute(1))).await;
        }
        Events::Dragged => {
            if let (Some(origin), Some(delta)) = (origin, event.delta) {
                card.update_container(|c| c.transform(placed_at(origin.x() + delta.x, origin.y() + delta.y))).await;
            }
        }
        _ => {
            origin = None;
            card.update_container(|c| c.depth(Depth::relative(1)).transform(Transform::identity())).await;
        }
    }
}
```

`Depth::absolute` lifts the card out of its parent's flow and places it from
the viewport, so a translation by the drag offset from its grabbed geometry
follows the pointer. When scaling a preview, use
`Transform::origin(UiPoint::zero())` to keep its top-left corner anchored.

The surface under the release point, and then each of its ancestors, gets
`Events::Dropped` with `UiEvent::source` set to the released source. The source
itself is skipped when finding that surface. `Engine::pointer_released` resolves the
target from the last evaluated frame's hit geometry and queues the source's
`DragEnded` after it, so a target claims the source before the source settles.
Components hear both from the next `Engine::evaluate`, even when a cancel or a
resize comes first. A target takes a
dropped element into its own layout with `EvaluationContext::adopt`, which
makes it the target's last flow child while keeping its id and properties:

```rust
loop {
    let event = stack.on(Events::Dropped).await;
    if let Some(card) = event.source {
        stack.adopt(card).await;
    }
}
```

While a source is held, the surface under the pointer other than the source is
available as `DragCapture::over`, so the source can preview where a release
would land.

`Engine::pointer_released` still returns the `DragDrop` for applications that apply
drops outside the UI, so either side can act on it. An element can also move
itself under another parent with `EvaluationContext::reparent`.

`Engine::cancel` ends the interaction in progress: it restores the held source
and discards queued clicks, scrolls, key presses, and text edits. Call it when
the window loses focus or the user cancels. A changed viewport size cancels
from `Engine::evaluate`, because layout distances and the source's place move
with it. The UI supplies the gesture and geometry. Your application decides
which targets accept the item and how to apply it.

## React to the pointer passing over a surface

Each `Engine::evaluate` compares the surface under the pointer with the previous
frame's. When it changes, the old surface gets `Events::PointerExited` and the
new one `Events::PointerEntered`, each followed by the ancestors that stopped or
started containing the pointer. An ancestor containing both surfaces hears
nothing, so a panel keeps its hover state while the pointer moves between its
children. A held drag source is skipped, so a drop target under a dragged item
still receives `PointerEntered`. `Engine::hovered` answers the same question at
the application level, for a cursor shape for example.

Curves take part once given a hit width: `hit_width(width)` in a curve's setup
lets the pointer find the curve within `width` layout units of its stroke, along its
whole length even where it runs beyond its declared size. A wire can then be
hovered, clicked, and dropped on like a container. The width follows the
inherited transform scale.

A container with an absolute position may sit partly outside its parent,
including at negative coordinates, so a canvas can be panned past its edge
without snapping its content. Flow-placed children are still kept inside the
viewport.

## Work within the current limits

<Callout type="info" title="Primitive UI layer">
	The module isn't a complete widget toolkit yet. Treat it as a retained
	primitive layer with an asynchronous interaction model.
</Callout>

Build higher-level widgets through small composed components before you add
runtime machinery.

The UI renderer has fixed per-frame limits on clip masks, images, primitives,
and glyphs. The [UI reference](/docs/reference/gui) lists them, and defines how
depth orders elements and what text rendering guarantees.

## Publish only changed renders

Applications should publish a render only when `Render::revision` changes. The
render source deduplicates repeated revisions anyway, so a republished unchanged
render never makes a sink rebuild.

Anything that must change pixels has to go through the tree: mutate elements
through the evaluation context rather than by keeping visual state outside the
engine. Placement, style, opacity, clipping, and transforms all live on retained
elements, so the revision covers them. Changing the viewport size is the one
input outside the tree, and both evaluation and rendering key on it.
