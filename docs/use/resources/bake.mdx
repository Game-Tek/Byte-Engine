Use BELD to turn your source assets into the complete resource store that a
release application loads.

Keep source assets separate from baked runtime resources:

```text
my-app/
  assets/       # authored source files and linked engine assets
    byte_engine -> ../path/to/byte-engine/assets
  resources/    # BELD output used by release builds
  src/
```

Keep engine-owned shaders in the engine crate. Expose them in your application's
asset namespace with a directory symlink:

```bash
ln -s ../../Byte-Engine/crates/byte-engine/assets assets/byte_engine
```

The logical symlink path is retained in resource IDs, so `assets/byte_engine/rendering/sky.besl` becomes `byte_engine/rendering/sky.besl`. BELD follows linked files and directories and detects directory cycles. Broken or inaccessible links fail the bake instead of silently producing an incomplete release resource set.

The engine crate package includes its `assets/` directory. For a registry dependency, vendor the resolved crate source and point the same application symlink at that vendored `assets/` directory. This keeps the link target stable instead of depending on Cargo's registry cache layout:

```bash
cargo vendor --locked vendor
ln -s ../vendor/byte-engine/assets assets/byte_engine
```

Commit both the vendor directory and symlink, or recreate them in the same
bootstrap step in every developer and CI checkout. Your
[application's BELD](/docs/use/resources/add-beld) builds from the same
`Cargo.lock` as the application, so its handlers and resource formats match the
engine you link.

On Windows, the checkout must preserve directory symlinks. [Enable Developer Mode](https://learn.microsoft.com/en-us/windows/advanced-settings/developer-mode)
or otherwise grant link creation permission, and make sure Git doesn't
materialize the link as a plain text file. The current automated symlink
coverage runs on Unix hosts.

Run BELD from your application directory. Pass absolute source and destination
directories. Asset IDs remain relative to `assets/`.

```bash
cd my-app

beld --source "$PWD/assets" --destination "$PWD/resources" \
  bake
```

With no IDs, BELD recursively discovers all supported source assets, including linked engine shaders, standalone `.environment.bead` assets, images, meshes, materials, and audio. Unknown files and BEAD sidecars are skipped, and `.environment.bead` files count as standalone assets rather than sidecars. A standalone `.besl` file is discovered only when its adjacent `.besl.bead` exists. This keeps material-internal BESL sources out of the standalone shader pass. Explicitly requesting a `.besl` file without its sidecar fails the bake.

BELD gives concurrent bake work a soft memory budget equal to half of the system memory available when the command starts. Override the budget in MiB when a CI runner or shared workstation needs more headroom:

```bash
beld --source "$PWD/assets" --destination "$PWD/resources" bake \
  --memory-budget-mib 4096
```

BELD pauses new independent work when the budget is full, while active bakes and their dependencies continue until they release memory. One large asset can temporarily exceed the budget. See [Control bake memory](/docs/use/resources/beld#control-bake-memory) for sizing guidance and the deadlock-safety reason for using a soft limit.

Use explicit IDs when a container fragment is required. Quote an ID containing a fragment so the shell preserves it:

```bash
beld --source "$PWD/assets" --destination "$PWD/resources" bake \
  'character.glb#skeleton' \
  'character.fbx#animations/Walk'
```

The command writes the resource database and its payload files to `resources/`. These files, rather than the source `assets/` directory, are what a release application reads. Their layout is specified in the [resource store reference](/docs/reference/resource-store).

Use packed storage when you want all binary payloads in one `resources.pack` file:

```bash
beld --source "$PWD/assets" --destination "$PWD/resources" \
  --storage-mode packed bake
```

The default `files` mode writes one extensionless payload file per resource. Its basename contains the resource ID, decoded hash, and encoding. BELD records the selected mode and each resource's payload encoding in `resources.db`, and the application discovers them when opening the store. Clear the destination before changing its mode.

In packed mode, rebuilding or deleting a resource returns its old range to a coalescing free-space allocator after active mapped readers release it. BELD reuses the smallest suitable range and grows `resources.pack` only when none fits. If BELD warns that the pack is fragmented, delete the destination resource directory and run the bake again to produce a compact pack.

Shader payloads are target-native: BELD writes SPIR-V on Linux, DXIL on Windows, and Metal libraries on macOS. The authored shader sources remain BESL; the Metal and Vulkan bakes lower the task payloads that the visibility task and mesh stages share. Run the matching BELD build on the platform targeted by the packaged application; a resource directory baked for another platform isn't portable.

## Leave render features out of the bake

Use your project's `config.json` to leave optional render features out of
both the baked shaders and the running application. You can leave out
ground-truth ambient occlusion (GTAO), screen-space global illumination
(SSGI), and contact shadows. Put the file in the
application directory, next to `assets/` and `resources/`:

```json
{
  "render": {
    "gtao": { "enabled": false },
    "ssgi": { "enabled": false },
    "contact-shadows": { "enabled": false }
  }
}
```

BELD reads `config.json` from the current directory, over the parameters your
application passes in code, so run it from the application directory or pass
`--config`:

```bash
beld --source "$PWD/assets" --destination "$PWD/resources" bake \
  --config "$PWD/config.json"
```

When you set a feature's `enabled` value to `false`, BELD bakes shaders without
its code and skips its pipelines:

| Feature | Code left out | Pipelines skipped |
| --- | --- | --- |
| `render.gtao.enabled` | GTAO occlusion in material shaders | `gtao`, `gtao-blur-x`, `gtao-upscale` |
| `render.ssgi.enabled` | SSGI lighting and its diffuse light output in material shaders | `ssgi-trace`, `ssgi-temporal` |
| `render.contact-shadows.enabled` | The contact-shadow filter in `sun-visibility.besl` | `contact-shadows` |

The application reads the same file at startup and doesn't create the left-out
passes. Turning a left-out feature on at runtime, or selecting a left-out
`render.gi.technique`, logs a warning instead.

Ray-traced surfel global illumination works the other way around: BELD leaves
it out unless `config.json` sets `render.surfel-gi.enabled` to `true`. With it
in, BELD also bakes a closest-hit shader for every material, which surfel rays
run where they hit the material, and the `surfel-*` pipelines and shaders. See
[Light with ray-traced global illumination](/docs/use/lighting#light-with-ray-traced-global-illumination).

A missing file keeps the features your application's parameters set. The
application also loads every other value in `config.json` as a startup
parameter, so `{"render": {"debug": true}}` sets `render.debug`. Environment
variables override the file for both the application and BELD, and
command-line arguments override it for the application.

After you change a feature in `config.json` or in your application's
parameters, run `beld bake` again. The features are part of what each shader's
bake records, so the bake processes the shaders built with the old setting and
skips everything else.

## Choose how materials are evaluated

Set `render.material-evaluation` in `config.json` to choose how the visibility
pipeline shades materials. The default, `pipelines`, gives every material
program its own pipeline. `uber` bakes one shader for each of the opaque and
transparent phases, holding every material in the bake:

```json
{
  "render": {
    "material-evaluation": "uber"
  }
}
```

The two shaders have no asset of their own: BELD bakes them last, from every
material in the resource store, and skips them when no material changed. After
you change the mode, run `beld bake` again.
A material baked in one mode doesn't carry what the other mode needs. See
[materials](/docs/reference/rendering#materials) for what each mode does.

## Bake only what your application uses

Use `resources.roots` in your project's `config.json` to bake only the assets
your application loads by ID, and everything they use. List them as glob
patterns:

```json
{
  "resources": {
    "roots": ["scenes/*", "audio/music/*", "ui/fonts/*.ttf"]
  }
}
```

When you run `beld bake` without IDs, BELD bakes the discovered assets that
match a root. A texture or material bakes only because a root uses it, so
the bake doesn't add a resource that nothing uses.

Resources from earlier bakes stay, such as a texture a material stopped
using. To delete everything no root uses in the same run, add `--prune` and
use a development build of BELD:

```bash
beld bake --prune
```

If any asset fails to bake, `--prune` deletes nothing. To review what it would
delete first, follow
[Find resources nothing uses](/docs/use/resources/beld#find-resources-nothing-uses).

If an asset matches both a root and a pattern in `assets.exclude`, BELD
stops before it bakes anything and names the asset. Remove it from one of the
two lists. The [Roots reference](/docs/api/beld#roots) specifies how roots
select assets.

## Keep assets out of the bake

Use `assets.exclude` in your project's `config.json` to keep work-in-progress
or source-only files out of every bake. List them as glob patterns, where `*`
matches any run of characters, including `/`:

```json
{
  "assets": {
    "exclude": ["textures/wip/*", "*.blend1", "audio/raw/*"]
  }
}
```

BELD skips matching files when it bakes the whole source directory, and a
development build of your application refuses to bake them on demand. If an
asset you keep still uses an excluded one, its bake fails and the error names
the excluded asset, so you find what still depends on it. Excluding an asset
doesn't delete a resource you baked before; remove it with `beld delete`. The
[Excluded assets reference](/docs/reference/assets#excluded-assets) specifies
how patterns match.

## Check the baked output

Inspect the output before you package the application:

```bash
beld --destination "$PWD/resources" list
beld --destination "$PWD/resources" inspect scene.glb
```

Run `beld bake` again after changing a source asset. BELD rebakes only the assets with a changed [input](/docs/reference/resource-management#inputs): a source file, a resource they're baked from, or a setting such as a feature in `config.json`. Baking requested IDs updates their generated output but doesn't remove unrelated old resources. Use `beld clear` only when you intentionally want to discard the entire resource directory.

## Fix a resource store that doesn't open

When BELD or your application can't open the resources directory, it stops and
reports the directory, the most likely cause, and the fix. It never switches to
a temporary store, so a bake can't report success without writing its output.

Find the cause in the message, then apply its fix:

| The message says the store | Do this |
| --- | --- |
| Is already open | Close the application or the other BELD command that uses the directory, then run your command again. Only one program at a time can open a resources directory. |
| Is corrupt or unreadable | Delete the resources directory and bake again. BELD and your application leave a corrupt store exactly as they found it, so you can copy it first if you want to keep it. |
| Didn't open because a file couldn't be created, read, or written | Make sure you can write to the directory and that the disk has free space, then run your command again. |
| Can't be opened | Follow the fix in the message: bake with the `--storage-mode` it names, or bake again with the BELD build that matches your engine. |

To rebuild a corrupt store, delete it and bake again:

```bash
rm -rf "$PWD/resources"
beld --source "$PWD/assets" --destination "$PWD/resources" bake
```

## Use resources in development and release

Debug applications can install an `AssetManager` and bake missing assets on demand. Release applications have no asset-processing fallback: they read the complete `resources/` directory prepared by BELD and fail when a requested shader is absent. Keeping baking as an explicit pre-package step makes releases reproducible and avoids shipping source assets solely for runtime processing.
