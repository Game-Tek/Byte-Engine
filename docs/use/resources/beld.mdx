Use BELD to bake, inspect, query, browse, and delete Byte Engine resources.

[Add BELD to your application](/docs/use/resources/add-beld) before you
run the commands on this page. They write the command as `beld`; run your
application's with `cargo run --release --bin beld --` followed by the same
arguments. Every flag, default, exit code, and output format is in the
[BELD command line reference](/docs/api/beld).

It reads source assets from an assets directory and writes processed resources to a resources directory.
By default those paths are `assets` and `resources`, but both are configurable.

```bash
beld --source assets --destination resources bake
```

## Run the commands

`beld bake` processes asset IDs into resources. If you omit the IDs, BELD finds
every supported source file below the source directory. It follows symlinks,
preserves their logical paths as resource IDs, rejects broken links, and avoids
directory cycles. BELD ignores `.bead` sidecars and unknown files. A standalone
`.besl` source needs an adjacent `.besl.bead` file for discovery. BELD processes
the discovered IDs in deterministic path order and runs independent asset work
concurrently.

BELD skips an asset when its stored resource is current with every source file
it was baked from, so running `beld bake` again only processes what changed.
Use `--force` to rebake the selected assets anyway, together with the textures,
materials, and other resources they depend on. Force a bake after you update
BELD's asset processors or change `--texture-compression`, because BELD only
tracks source file versions:

```bash
beld --source assets --destination resources bake --force
```

To bake only selected assets, provide their IDs explicitly:

```bash
beld --source assets --destination resources bake mesh.glb character.fbx material.bema
```

By default, BELD stores each binary payload in a separate file. Use packed storage when you want one payload file for packaging or distribution:

```bash
beld --source assets --destination resources --storage-mode packed bake
```

BELD records the selected mode in the resource database. Later bake, inspect, query, and delete commands discover that mode automatically. If the destination already exists, `--storage-mode` must match it. Clear the destination before selecting another mode.

Quote glTF or FBX subresource IDs so the shell doesn't treat their fragment as a comment:

```bash
beld --source assets --destination resources bake \
  'character.glb#skeleton' \
  'character.fbx#animations/Walk'
```

`beld list` prints stored resource IDs.

`beld inspect` prints metadata for a resource ID or UID.
Use `--format json` when editor tooling or scripts need structured output.
In development builds, the output also includes the resource's bake `trace`.
You can inspect a failed asset by ID even when it produced no resource. In that
case, the output contains `resource: null` and the trace that explains the
failure.

`beld query` prints the resources that match a filter, grouped and sorted.
See [Query resources](#query-resources).

`beld delete` removes resources by ID.

`beld clear` and `beld wipe` remove the resources directory and recreate it.

BELD continues baking after an individual asset fails, but the command exits with status `1` if any selected asset failed. A successful command logs the total elapsed bake time and success/failure counts.

## Check what a bake produces

Use a dry run to see the resources an asset bakes into without writing them to
your resources directory. BELD bakes the asset and everything it depends on in
memory, prints the result, and leaves the destination untouched:

```bash
beld --source assets bake --dry-run --format json character.glb
```

Add `--payload typed` to include each stream's data as JSON values, such as
vertex positions, texels, audio frames, and LUT entries. Use `--payload base64`
when you need the exact bytes. Both need `--format json`:

```bash
beld --source assets bake --dry-run --format json --payload typed character.glb \
  | jq '.resources[] | select(.class == "Mesh") | .streams[] | select(.name == "Vertex.Position") | .data[:3]'
```

Animation clips already print their keyframes under `resource.tracks`, so you
don't need `--payload` to read them. Name the clip's ID to bake it:

```bash
beld --source assets bake --dry-run --format json 'character.fbx#animations/Walk'
```

## See the shader program a material compiles

Add `--intercept '*.besl'` to a dry run to print the BESL program each shader
compiles from, as your application's renderer generated it. Use it to check
what a material's graph turned into, or to read the program behind a shader
compile error:

```bash
beld --source assets bake --dry-run --intercept '*.besl' materials/wood.bema
```

Each program prints under a `// <shader ID>.besl` line, such as
`// materials/wood.bema#shader.besl`. A glTF or FBX file's generated materials
compile to shared shaders named `character.glb#shaders/<key>`. To print only
one file's programs, match its ID, such as `--intercept 'character.glb#*'`.
Add `--format json` to read them with another tool.

To see the platform shader each program lowered to, intercept `*.msl` on
macOS, `*.hlsl` on Windows, or `*.glsl` on Linux. Use it to check what the
platform compiler receives, such as when a shader compiles but runs slower or
renders differently than its BESL suggests:

```bash
beld --source assets bake --dry-run --intercept '*.msl' materials/wood.bema
```

Pass both patterns, `--intercept '*.besl' --intercept '*.msl'`, to read each
program beside the shader it became.

BELD bakes with your project's `config.json`, so the programs match the
renderer features your application uses.

To read the data of a resource you already baked, add the same `--payload`
option to `beld inspect`. Logs go to standard error, so you can redirect the
output to a file or pipe it to another tool. The
[payloads reference](/docs/api/beld#payloads) lists every stream format.

## Control bake memory

BELD limits how much memory concurrent bake work can reserve. By default, the soft memory budget is half of the system memory available when `beld bake` starts, and never less than a quarter of the installed memory. For example, BELD uses a 6 GiB budget when 12 GiB is available at startup, and a 4 GiB budget on a 16 GiB machine under memory pressure.

Set an explicit budget in MiB when you need predictable behavior in CI, on a shared workstation, or on a dedicated bake machine:

```bash
beld --source assets --destination resources bake \
  --memory-budget-mib 4096
```

When the budget is full, BELD pauses new independent bake work. Active bakes and their dependencies continue so they can finish and release memory. BELD logs when it pauses and resumes.

The budget is soft rather than a strict process-memory cap. One large asset or active work can temporarily exceed it. This avoids a deadlock where every worker holds memory while waiting for another worker to release memory. Use a lower value to leave more memory for other applications, or a higher value when the bake machine has dedicated capacity.

## Query resources

Use `beld query` to answer questions about your resource store from a script or
an AI agent. It takes the filter, fields, group, and sort of
[`beld browse`](#find-what-fills-the-store), prints the result, and doesn't
change the store:

```bash
beld query class=Material
beld query class=Image name=textures/hero_albedo.png
beld query --group source --limit 5
beld query --format json --limit 20 -- class=Image 'stored>1MiB' -is:compressed
beld query --format json is:stale
beld query --group source --limit 0 is:unreachable
beld inspect material.bema --format json
```

- Quote terms that contain `>`, `<`, `*`, or `?`, so your shell doesn't read
  them.
- Put `--` before the terms when one starts with `-`, and put the options
  before `--`.
- `--limit` caps the resources listed in each group. Counts and sizes still
  cover every match, so `--group class --limit 0` prints only the size of each
  class.
- In development builds, the JSON output includes each resource's bake `trace`.

Every resource model gets a `name` property by default. The
[Query reference](/docs/api/beld#query) lists every option and the shape of the
JSON output.

## Find what fills the store

Use `beld browse` to find the resources that take the most space, the ones a
bake left out of date, and what each resource pulls in. It opens a full-screen
view of the whole store in your terminal and doesn't change the store:

```bash
beld --source assets --destination resources browse
```

The table lists every resource, largest stored payload first. Press `/` and
type a filter to narrow it, `g` to group it, and `s` to change the sort. Press
`Enter` to keep the filter. These filters answer common questions:

| To find | Do this |
| --- | --- |
| The source files that produce the most data | Press `g` and pick `source`. |
| Large textures stored uncompressed | Filter `class=Image stored>1MiB -is:compressed`. |
| Identical payloads stored more than once | Filter `is:duplicate`, then press `g` and pick `hash`. |
| Resources the next bake processes again | Filter `is:stale`. |
| Resources no part of your application uses, in development builds | Filter `is:unreachable`, then press `g` and pick `source`. See [Find resources nothing uses](#find-resources-nothing-uses). |
| Resources that use an ID the store doesn't have, in development builds | Filter `is:dangling`. |
| Bakes that failed or warned, in development builds | Filter `is:failed` or `has:warnings`. |
| Images in one format | Filter `class=Image model.format=BC7`. |

Select a resource and press `Enter` to read its details: its streams, the
source files it came from, and its bake trace. In development builds, the
details also list the resources it uses and the resources that use it. Press
`Enter` on one of those to jump to it, and `Backspace` to go back.

Press `u` to see the usage of the whole store: the size of each class,
duplicate payloads, payload files that no resource uses anymore, and how
fragmented a packed store is. To reclaim the space of unused payload files or
of a fragmented pack, clear the store and bake it again.

After you bake in another terminal, press `R` to read the store again. Your
filter, group, and sort stay. Press `q` to quit.

`beld browse` needs an interactive terminal. In scripts, use
[`beld query`](#query-resources), which takes the same filter, group, and sort.
The [Browse reference](/docs/api/beld#browse) lists every key, and
[Filter, group, and sort](/docs/api/beld#filter-group-and-sort) lists every
field and filter term.

## Find resources nothing uses

Use roots to find the resources that no part of your application needs, so you
can remove their source assets. A root is a resource your application loads by
ID, such as a scene or a sound it plays by name. Everything else is needed only
when a root uses it, directly or through other resources.

Use a development build of BELD to bake and to search. Only development builds
record which resources use which, so a release build rejects `is:unreachable`
and `is:dangling`.

1. List the roots in your project's `config.json` as glob patterns. `*`
   matches any run of characters, including `/`:

   ```json
   {
     "resources": {
       "roots": ["scenes/*", "audio/music/*", "ui/fonts/*.ttf"]
     }
   }
   ```

1. Open `beld browse` from a development build, press `/`, and filter
   `is:root` to check that the patterns match the resources you expect.
1. Filter `is:unreachable` to see every resource that no root uses. Press `g`
   and pick `source` to see which source files they come from.
1. Filter `is:dangling` to find resources that use an ID the store doesn't
   have, such as a texture whose file you renamed.
1. Print the list to cull, for a review or a script:

   ```bash
   beld query --group source --limit 0 is:unreachable
   beld query --format json is:unreachable
   ```

   The first command prints one line per source file with the number and size
   of its unreachable resources, which is the list of files to review. The
   second prints every unreachable resource as JSON, for a script that checks
   or removes them. Both read the store and the configuration, and neither
   changes anything.

1. Remove their resources with `beld delete`, or run `beld bake --prune` to
   bake and delete every unreachable resource in one step. A bake with roots
   doesn't produce them again, because it bakes only the roots and what they
   use.
   Delete their source files too, or add them to `assets.exclude`, if you
   don't need them anymore.

BELD reads `config.json` from the working directory, over the parameters your
application passes in code. Pass `--config <path>` to read another file. The
[Roots reference](/docs/api/beld#roots) specifies how patterns match.

## Choose when to use BELD

Use BELD when you need deterministic resource output:

- Prepare assets before a release build.
- Inspect the resources that an asset produced.
- Check shader reflection metadata.
- Find what fills your resource store.
- Rebuild resources after you change a processor.
- Delete stale resources while you debug asset import.

During development, applications can also lazily bake assets at request time.
BELD is still useful because it gives you a direct, scriptable view of the same resource storage.
