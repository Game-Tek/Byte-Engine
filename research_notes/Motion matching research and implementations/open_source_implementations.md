# Open-source and source-available motion matching implementations (state as of October 2026)

Method note: licenses, last activity, and file layouts below were read from each repository through the GitHub API on 2026-10-24 (LICENSE file contents, `pushed_at`, commit logs, and recursive file trees), not from secondary write-ups. "Last push" is the GitHub `pushed_at` time; "last commit" is the newest commit on the default branch. Star counts are as of the same day. The Unreal Engine source was read from the private `EpicGames/UnrealEngine` repository through the user's linked Epic account (`release` branch, newest tag `5.8.4-release`); only names and default values are recorded here, no Epic code.

## What open-source and source-available motion matching implementations exist, and how is each built?

### Takeaway
About fifteen implementations are worth studying. Five are permissively licensed, complete, and still maintained in 2025 to 2026: Daniel Holden's C++ demo (MIT), O3DE's MotionMatching gem (Apache-2.0 or MIT), JLPM22's Unity package (MIT), GuilhermeGSousa's Godot 4 GDExtension (MIT), and EraEngine's HNSW-based module (Apache-2.0). Unreal's Pose Search plugin (5.8) is the most complete design, but its source is available only under the Epic EULA. MxM and Motion Symphony became "free and public" in June 2025 with no license file. Kinematica has been on hold since 2021. The only Rust implementation is a Bevy prototype that is not published on crates.io.

### Cited Findings

#### 1. Daniel Holden, `orangeduck/Motion-Matching` (C++, raylib)
- Repo: https://github.com/orangeduck/Motion-Matching. Language C++. License: MIT (LICENSE file). Last commit 2025-02-06 (merged PR #35, a C linkage fix); the previous one is 2024-10-02 (rotation-order fix in `train_decompressor.py`). 930 stars. Maintenance: stable reference code with occasional fixes, no feature work — [repo](https://github.com/orangeduck/Motion-Matching)
- Purpose: the source for the demos in the article "Code vs Data Driven Displacement", plus basic Motion Matching and Learned Motion Matching (LMM) implementations modeled on the Ubisoft LMM paper. It is not identical to the paper: it leaves out some of the database storage optimizations, and it uses no tags to tell walking from running — [README](https://github.com/orangeduck/Motion-Matching)
- Layout: the whole runtime is a few headers plus `controller.cpp` (2,487 lines). The search is in `database.h` (733 lines). Separate small headers cover arrays, quaternions, vectors, springs (`spring.h`), the neural network (`nnet.h`), and LMM (`lmm.h`) — [repo tree](https://github.com/orangeduck/Motion-Matching)
- Feature schema (`database_build_matching_features`): left and right foot positions (3+3), left and right foot velocities (3+3), hip velocity (3), trajectory positions (6 = three 2D future points), and trajectory directions (6). That is 27 dimensions. Each feature block is normalized by its mean and standard deviation, and the scale is divided by the user weight, so the weights act inside the normalization — [database.h](https://github.com/orangeduck/Motion-Matching/blob/main/database.h)
- Default weights: foot position 0.75, foot velocity 1.0, hip velocity 1.0, trajectory positions 1.0, trajectory directions 1.5. Search interval `search_time = 0.1` s, with a forced search when input changes. Inertialization blend halflife 0.1 s. Simulation velocity halflife 0.27 s — [controller.cpp](https://github.com/orangeduck/Motion-Matching/blob/main/controller.cpp)
- Search structure: brute force accelerated by two levels of axis-aligned bounding boxes over consecutive frames (`BOUND_SM_SIZE = 16`, `BOUND_LR_SIZE = 64`). A whole block is skipped when the query's distance to its box already exceeds the best cost. The search runs per clip range, skips the end of each range (`ignore_range_end`), skips frames around the current one (`ignore_surrounding`), and adds a `transition_cost` to any jump — [database.h](https://github.com/orangeduck/Motion-Matching/blob/main/database.h)
- Trajectory prediction: a critically damped spring simulation of desired velocity and rotation (`trajectory_desired_velocities_predict`, `trajectory_positions_predict`, `trajectory_rotations_predict`), driven by the gamepad, with a desired-gait spring. Collision with obstacles is handled by clamping trajectory points — [controller.cpp](https://github.com/orangeduck/Motion-Matching/blob/main/controller.cpp)
- Transitions and post-processing: inertialization with offset decay (`inertialize_pose_transition`, `inertialize_pose_update`, `inertialize_root_adjust`). Damped adjustment of the character toward the simulation (`damp_adjustment_exact`) with a maximum adjustment ratio, and clamping. Two-bone foot IK (`ik_two_bone`) and look-at IK (`ik_look_at`). Debug drawing of trajectories and features in raylib, with raygui toggles — [controller.cpp](https://github.com/orangeduck/Motion-Matching/blob/main/controller.cpp)
- Learned MM pipeline: `resources/train_decompressor.py` reads `database.bin` and `features.bin` and produces `decompressor.bin` and `latent.bin`. Then `train_stepper.py` and `train_projector.py` produce the stepper and projector networks. Training uses PyTorch and writes Tensorboard logs. Weight or feature changes require regenerating `features.bin` and retraining — [README](https://github.com/orangeduck/Motion-Matching)
- Dataset: the database is built from Ubisoft La Forge LaFAN1. The README notes that LaFAN1 is CC BY-NC-ND 4.0, unlike the MIT code — [README](https://github.com/orangeduck/Motion-Matching)
- Web demo: the demo compiles to WebAssembly with emscripten (`make PLATFORM=PLATFORM_WEB`) and is served by the included `wasm-server.py` — [README](https://github.com/orangeduck/Motion-Matching)

#### 2. Holden-derived minimal implementations (C++ and Python)
- `orangeduck/GenoViewPython-MotionMatching`: a bare-bones Python motion matching implementation using numpy, scipy, and raylib Python bindings. MIT license. Last push 2025-09-06. It needs three BVH files from `lafan1-resolved`. Its one script holds the whole pipeline: `ComputeDatabaseFeatures`, `ComputeRuntimeFeatures`, spring trajectory functions (`TrajectorySpringPosition` and `TrajectorySpringRotation`), decay springs, and `InertializeTransitionPosition` — [repo](https://github.com/orangeduck/GenoViewPython-MotionMatching)
- `orangeduck/lafan1-resolved`: LaFAN1 retargeted onto one common skeleton. The README says the data keeps the original dataset's terms and is not licensed for commercial use. The skinned Geno mesh is free only for non-commercial research. Last push 2025-09-16 — [repo](https://github.com/orangeduck/lafan1-resolved)
- `tomcatmew/simple_motion_matching`: C++ with legacy OpenGL, GLFW, Dear ImGui, and delfem2. MIT license. Last push 2026-10-18. It uses a 27-dimensional feature (future trajectory positions and facing at +20, +40, and +60 frames, foot positions and velocities, hip velocity), which is Holden's schema. It reports brute-force search in about 1 ms over 75k frames. Other features: inertialization, gamepad control through a critically damped spring trajectory, and a 3D path editor. The README says the current version was improved with Claude Code — [repo](https://github.com/tomcatmew/simple_motion_matching)

#### 3. Unreal Engine Pose Search plugin, 5.8 (source-available)
- Location: `Engine/Plugins/Animation/PoseSearch` in `EpicGames/UnrealEngine`. The repository is private and readable only after linking a GitHub account to an Epic account. The root `LICENSE.md` puts all use under the Unreal Engine EULA (https://www.unrealengine.com/eula). Newest release tag: `5.8.4-release`. Last push 2026-10-24. The plugin describes itself as a framework for indexing and searching pose features, used in techniques such as motion matching. It has a Runtime module and an UncookedOnly editor module, depends on `AnimationWarping`, and is disabled by default — [PoseSearch plugin (requires Epic-linked access)](https://github.com/EpicGames/UnrealEngine/tree/release/Engine/Plugins/Animation/PoseSearch)
- Feature schema: a `UPoseSearchSchema` holds a list of feature channels. The total cost is the sum of the channel costs. Channel types in 5.8: Pose, Position, Velocity, Heading, Trajectory, Phase, Curve, Distance, TimeToEvent, SamplingTime, PermutationTime, Group, Padding, and FilterCrashingLegs. Schema defaults: `SampleRate = 30`, and `DataPreprocessor = Normalize`, with experimental `NormalizeOnlyByDeviation` and `NormalizeWithCommonSchema` options. The schema also supports a `MirrorDataTable`, permutations (`NumberOfPermutations` and `PermutationsSampleRate`, used for interactions), and normalization sets that share normalization across databases — [PoseSearchSchema.h and channel headers](https://github.com/EpicGames/UnrealEngine/tree/release/Engine/Plugins/Animation/PoseSearch/Source/Runtime/Public/PoseSearch)
- Search structure: `EPoseSearchMode` offers BruteForce, PCAKDTree (the default), VPTree (experimental), and EventOnly (experimental). PCAKDTree projects poses onto `NumberOfPrincipalComponents` dimensions (default 4, range 1 to 64) and queries `KDTreeQueryNumNeighbors` candidates (default 200, maximum 600) before full-cost evaluation. When the neighbor count is 1, the full feature values are stripped and the search relies only on the PCA values. Optional duplicate pruning uses `PCAValuesPruningSimilarityThreshold`. Database cost biases: `ContinuingPoseCostBias = -0.01`, `LoopingCostBias = -0.005`, `BaseCostBias = 0`. Mirroring options: original only, mirrored only, or both. The plugin ships its own `KDTree.h` and `VPTree.h` — [PoseSearchDatabase.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Plugins/Animation/PoseSearch/Source/Runtime/Public/PoseSearch/PoseSearchDatabase.h)
- Runtime node: `AnimNode_MotionMatching` has `BlendTime = 0.2` s. It blends either through inertial blending, which needs an Inertialization node downstream, or through an internal blend stack when `MaxActiveBlends > 0`, and it supports blend profiles. Other settings: `PoseJumpThresholdTime` (no jumps to nearby poses in the same segment), `PoseReselectHistory = 0.3` s (no re-selecting recent poses), `SearchThrottleTime` (default 0, meaning a search every update), a `PlayRate` interval that absorbs speed mismatch between the movement model and the animation, interrupt modes for the continuing pose, and event-targeted searches (`EventToSearch`). Databases can be swapped at runtime (`SetDatabasesToSearch`) — [AnimNode_MotionMatching.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Plugins/Animation/PoseSearch/Source/Runtime/Public/PoseSearch/AnimNode_MotionMatching.h)
- Trajectory: a Pose History collector node samples past bones and can generate a trajectory. `IPoseSearchTrajectoryPredictorInterface` (experimental) lets an object fill the future samples of an `FTransformTrajectory`. `PoseSearchTrajectoryLibrary` holds helpers. The 5.8 documentation says the Character Trajectory component supplies samples to the Trajectory channel — [PoseSearchTrajectoryPredictor.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Plugins/Animation/PoseSearch/Source/Runtime/Public/PoseSearch/PoseSearchTrajectoryPredictor.h); [Motion Matching in Unreal Engine (5.8 docs)](https://dev.epicgames.com/documentation/unreal-engine/motion-matching-in-unreal-engine)
- Multi-character: `PoseSearchInteractionAsset`, `PoseSearchInteractionIsland`, and `PoseSearchInteractionSubsystem` support interactions searched jointly across characters through roles and `MultiAnimAsset` — [Runtime/Public/PoseSearch](https://github.com/EpicGames/UnrealEngine/tree/release/Engine/Plugins/Animation/PoseSearch/Source/Runtime/Public/PoseSearch)
- Editor and debugging: a Pose Search Database editor with a preview scene, asset tree, and viewport. A Pose Search Debugger with database views, cost-breakdown columns, and a Rewind Debugger track creator (`PoseSearchDebuggerTrackCreator`), fed by `PoseSearchTraceLogger` through Unreal Insights trace — [Editor/Private](https://github.com/EpicGames/UnrealEngine/tree/release/Engine/Plugins/Animation/PoseSearch/Source/Editor/Private)
- Official docs (5.8): databases accept Animation Sequences, Composites, and Blendspaces; Montages are not supported in Animation Blueprints. The page gives no numeric benchmarks, only guidance: more channels and samples raise runtime cost, a higher sample rate raises memory use, and PCAKDTree is the optimized mode — [Motion Matching in Unreal Engine](https://dev.epicgames.com/documentation/unreal-engine/motion-matching-in-unreal-engine)

#### 7. JLPM22 / José Luis Pontón, `MotionMatching` (Unity, C#)
- Repo: https://github.com/JLPM22/MotionMatching. MIT license. Last commit 2026-04-24 (a null-check fix, #15). Version 0.3.2 dated 2026-02-24, with fixes for PoseSet deserialization memory and a NativeArray tag bug. No GitHub releases. 602 stars. Requires Unity 6+ and installs as a UPM git package. It began as the author's master's thesis (UPC, 2022) — [repo](https://github.com/JLPM22/MotionMatching)
- Data: sample mocap ships as BVH files renamed to `.txt` under `Samples/Animations`, defined through MMData assets. Processed pose and feature databases are written to `StreamingAssets/MMDatabases` — [README](https://github.com/JLPM22/MotionMatching)
- Architecture, from its files: a BVH importer, `PoseExtractor` and `PoseSet`, generic `Feature1D` to `Feature4D` extractors, `FeatureSet`, tags with Burst tag operations, and the search classes `LinearMotionMatchingSearch`, `LinearMotionMatchingSearchBurst`, `BVHMotionMatchingSearch`, and `DynamicMotionMatchingSearch`. Also `Inertialization`, `TwoJointIK`, spring-based character controllers (spline, path, crowd, collisions), and editor windows `MMSearchDebugEditorWindow` and `AnimationViewerEditorWindow`, plus `FeatureDebug` gizmos — [repo tree](https://github.com/JLPM22/MotionMatching)
- Custom search API: subclass the abstract `MotionMatchingSearch` ScriptableObject and implement `Initialize`, `ShouldSearch`, `FindBestFrame` (often a Burst job), and the optional `OnSearchCompleted`, `OnUpdateEnvironmentFeatureWeight`, and `DrawGizmos`. Environment features are stored unnormalized, and each search decides how they affect the score. The docs give no benchmark numbers — [Custom Search docs](https://joseluisponton.com/motionmatching-docs/advanced/custom_search/)
- Roadmap: done are a BVH editor with real-time tag queries, Animator integration (for example Unity animation on the upper body and MM on the lower body), and packaging. Planned are more pose features, more mocap, visual debugging and database visualization, deep-learning memory reduction, a Unity 6 DOTS version, IK, an event system, and networked MM — [Roadmap](https://joseluisponton.com/motionmatching-docs/roadmap/)
- Derived research code: `UPC-ViRVIG/Environment-aware-Motion-Matching` (SIGGRAPH Asia 2025, MIT, Unity 6.2, last push 2026-04-24, data on Zenodo). It adds environment features and obstacle-aware penalization to the search — [repo](https://github.com/UPC-ViRVIG/Environment-aware-Motion-Matching); [data](https://zenodo.org/records/17220516). `UPC-ViRVIG/MMVR` (SCA 2022, motion matching for VR avatars) is licensed CC BY-NC-SA 4.0 (LICENSE file), last push 2026-06-06 — [MMVR](https://github.com/UPC-ViRVIG/MMVR)

#### 8. O3DE MotionMatching gem (EMotionFX, C++)
- Location: https://github.com/o3de/o3de/tree/development/Gems/MotionMatching. `gem.json` declares the license "Apache-2.0 Or MIT", and the root LICENSE.txt makes Apache-2.0 the default with MIT as an option. Recent commits: 2026-08-11 (ground plane loading fix), 2026-07-26, 2026-07-13 (i18n), 2026-05-07 (gem initialization switched to `parallel_for`), 2026-03-09 (ScriptCanvas demo fixes). That is maintenance only. It first shipped as an experimental gem in O3DE 22.05 — [gem](https://github.com/o3de/o3de/tree/development/Gems/MotionMatching); [o3de LICENSE.txt](https://github.com/o3de/o3de/blob/development/LICENSE.txt); [blog post](https://docs.o3de.org/blog/posts/blog-motionmatching/)
- Feature schema: user-defined features (Position, Velocity, AngularVelocity, Trajectory), each extracted relative to a joint, usually the root, so the search is invariant to the character's location. Each feature has a cost factor and a residual type (squared or absolute). Each feature does three jobs: extract into the feature matrix, fill the query vector, and compute its cost. The suggested starting set is the root trajectory plus foot positions and velocities — [README](https://github.com/o3de/o3de/blob/development/Gems/MotionMatching/README.md)
- Defaults: the trajectory feature uses a 0.7 s past window with 4 samples and a 1.2 s future window with 6 samples. The default schema has 59 feature values. Memory example: 1 hour at 30 Hz is 108,000 frames, about 6.4 million values, about 24.3 MB — [README](https://github.com/o3de/o3de/blob/development/Gems/MotionMatching/README.md)
- Search: a broad phase uses a KD-tree, tuned by maximum depth and minimum frames per leaf, to return candidate frames. A narrow phase sums the per-feature costs over those candidates. The search runs a few times per second, 5 per second in the pseudo-code, and the gem skips the transition when the best frame is close to the current one. Feature matrix transformers include standard and min-max scalers (`FeatureMatrixStandardScaler`, `FeatureMatrixMinMaxScaler`) — [README](https://github.com/o3de/o3de/blob/development/Gems/MotionMatching/README.md); [Code/Source](https://github.com/o3de/o3de/tree/development/Gems/MotionMatching/Code/Source)
- Trajectory: a `TrajectoryHistory` records world-space root position and facing each tick. Prediction from a joystick builds an exponential curve that starts in the character's direction and bends toward the target. Discard-frame motion events cut unwanted sections out of the imported clips — [README](https://github.com/o3de/o3de/blob/development/Gems/MotionMatching/README.md)
- Integration and tools: exposed as an EMotionFX blend tree node (`BlendTreeMotionMatchNode`), so it mixes with other graph nodes. An `ImGuiMonitor` shows feature costs and performance. CSV serializers export the feature matrix, and Jupyter notebooks plot feature histograms and a 2D PCA scatter to diagnose database coverage. Demo levels and prefabs include an automatic path-following character and a gamepad-controlled one. The blog lists debug visualizations of velocities and trajectories, feature cost over time, and performance metrics, but gives no millisecond figures — [README](https://github.com/o3de/o3de/blob/development/Gems/MotionMatching/README.md); [blog](https://docs.o3de.org/blog/posts/blog-motionmatching/)
- Dataset: `Assets/Animations` has 22 FBX clips stored in Git LFS (for example Acceleration1, Circles1, Crouching1, FreeRoaming1/2, Jog1, JogPivotTurn1, Jumps1, Pushes1), captured along "dance card" paths after Kristjan Zadziuk's GDC 2016 talk. The gem's declared license covers the gem directory — [Assets/Animations](https://github.com/o3de/o3de/tree/development/Gems/MotionMatching/Assets/Animations); [blog](https://docs.o3de.org/blog/posts/blog-motionmatching/)

#### 10. Bevy and Rust
- `voxell-tech/bevy_motion_matching` (Nixon / Voxell). Rust. Licensed MIT OR Apache-2.0: both LICENSE-MIT and LICENSE-APACHE are present, and `Cargo.toml` says `license = "MIT OR Apache-2.0"`. Last commit 2025-12-24 (update to Bevy 0.17), last push 2025-12-28. 61 stars. MSRV 1.85. The README says the project is being split into library and example crates for crates.io and asks for help — [repo](https://github.com/voxell-tech/bevy_motion_matching)
- Not published: crates.io returns "crate `bevy_motion_matching` does not exist", and keyword searches for `motion-matching` and `motionmatching` return 0 crates — [crates.io search](https://crates.io/search?q=motion%20matching)
- Its architecture, from its sources and `Cargo.toml`: BVH loading through `bvh_anim` 0.4, wrapped in a `bevy_bvh_anim` workspace crate. Motion data is split into chunks with separate pose and trajectory data. Matching is two-stage: `trajectory_match` scans all chunks for the best trajectory, then `pose_match` picks among the nearest trajectories. Alternative backends are a `KdTreeMatchPlugin` (the `kdtree` 0.7 crate) and a `KMeansMatchPlugin` (the `clustering` 0.2.1 crate). ### Inferences
- The field has converged on one pipeline: per-frame feature vectors (foot positions and velocities, hip velocity, future and past root trajectory), per-block normalization with weights, a periodic search (every 0.1 to 0.2 s, or every update in Unreal) with a continuing-pose bias, and a transition by inertialization. The implementations differ mainly in the search accelerator: AABB blocks (Holden, Motion Symphony, JLPM22's BVH), a KD-tree (O3DE, Godot, Bevy), PCA plus a KD-tree or VP-tree (Unreal), k-means or clustering (MxM, Bevy), or HNSW (EraEngine).
- Unreal is the only implementation with production-scale tooling: Rewind Debugger integration, cost breakdown per channel, normalization sets, interactions, and event-targeted searches. Its settings and defaults (PCA 4 dimensions, 200 neighbors, cost biases of -0.01 and -0.005, 0.3 s reselect history) are a useful design checklist even though its code cannot be reused.
- Kinematica, MxM, and Motion Symphony are effectively frozen: no updates since 2020, 2025-03, and 2024-03 respectively.
- The only performance figures are tomcatmew's brute-force number (about 1 ms over 75k frames for 27 dimensions) and O3DE's memory figure (about 24.3 MB per hour at 30 Hz with 59 values). Byte-Engine would need its own benchmarks.

### Gaps
- No implementation publishes systematic search-time benchmarks. Unreal's docs give none, O3DE's blog gives none in milliseconds, and JLPM22's docs give none.
- I could not read the GASP 5.7 blog directly (HTTP 403), so the "about 400 new animations" figure comes only from a search summary of the Japanese edition. I did not check GASP's current Fab license text; the UE-only term comes from a 2024 CG Channel article.
- The license and origin of JLPM22's bundled sample BVH files, and the license of the Environment-aware Motion Matching Zenodo data, were not checked.
- I did not confirm whether a hosted copy of Holden's web demo is still online.
- I did not look for motion matching in other open engines beyond those named (for example Wicked Engine, Defold, or ezEngine). GitHub topic and language searches surfaced only EraEngine.
- MxM and Motion Symphony may still be listed (possibly free) on the Unity Asset Store and Fab with store EULA terms. I did not check the store listings.

## Which implementations are most useful as references for a Rust engine, and why?

### Takeaway
Use Holden's `Motion-Matching` as the algorithmic core to port: it is MIT, has no engine dependencies, is data-oriented, and has the right size of schema, AABB search, springs, and inertialization. Use O3DE's gem for the data architecture, database tooling, and permissively licensed sample mocap (Apache-2.0 or MIT). Use EraEngine and Bevy for ECS and approximate-nearest-neighbor ideas, GuilhermeGSousa's Godot plugin for animation-graph and editor integration, and Unreal Pose Search 5.8 only as a read-only design checklist.

### Cited Findings
- Holden's runtime is a few dependency-free headers (`array.h`, `quat.h`, `vec.h`, `spring.h`, `database.h`) plus one controller file. The search is a flat float matrix with per-block AABB bounds and early rejection by best cost, and everything is MIT — [repo](https://github.com/orangeduck/Motion-Matching); [database.h](https://github.com/orangeduck/Motion-Matching/blob/main/database.h)
- Holden's pipeline also has a matching Python reference (`GenoViewPython-MotionMatching`, MIT) that a Rust port can be checked against numerically — [repo](https://github.com/orangeduck/GenoViewPython-MotionMatching)
- O3DE separates a skeleton-bound shared `MotionMatchingData` (frame database, feature schema, feature matrix) from a per-character `MotionMatchingInstance` (trajectory history, query vector, last best frame, playback time). Features own extraction, query filling, and cost. Search is a broad phase plus a narrow phase. The gem is Apache-2.0 or MIT and still maintained in 2026 — [README](https://github.com/o3de/o3de/blob/development/Gems/MotionMatching/README.md); [commits](https://github.com/o3de/o3de/commits/development/Gems/MotionMatching)
- The O3DE gem's sample animations sit inside a gem whose `gem.json` declares "Apache-2.0 Or MIT", and the Godot plugin already reuses them as demo data — [gem.json](https://github.com/o3de/o3de/blob/development/Gems/MotionMatching/gem.json); [Godot README](https://github.com/GuilhermeGSousa/godot-motion-matching)
- `bevy_motion_matching` is the only Rust code. It shows ECS-system decomposition (load, trajectory match, pose match, as Bevy systems), pluggable search backends as plugins (KD-tree and k-means), BVH ingestion, and egui-based tuning and measurement. It depends on general crates (`kdtree`, `clustering`, `peak_alloc`) and is a prototype that is not on crates.io — [repo](https://github.com/voxell-tech/bevy_motion_matching); [Cargo.toml](https://github.com/voxell-tech/bevy_motion_matching/blob/main/Cargo.toml)
- EraEngine puts the accelerator behind a `motion_matching_knn_structure` interface with an HNSW implementation, splits features into pose, trajectory, and phase, has unit tests for the motion database, and is Apache-2.0 — [module tree](https://github.com/EldarMuradau/EraEngine/tree/master/modules/simple_motion_matching)
- JLPM22 shows a swappable search interface (`ShouldSearch`, `FindBestFrame`, environment-feature weights), Burst SoA linear search, tag queries, and environment-aware features. It is MIT and the most actively maintained Unity option (2026) — [Custom Search docs](https://joseluisponton.com/motionmatching-docs/advanced/custom_search/); [repo](https://github.com/JLPM22/MotionMatching)
- GuilhermeGSousa's plugin shows how to embed MM as one node in an existing animation graph (AnimationTree), with synchronizers that reconcile the character controller and root motion (clamp, mix, root motion) and editor visualization tabs — [repo tree](https://github.com/GuilhermeGSousa/godot-motion-matching)
- Unreal Pose Search 5.8 shows the full production feature set: channel-based schema, PCA-KD-tree, VP-tree, and event-only search modes, cost biases, mirroring, normalization sets, multi-character interactions, a trajectory predictor interface, and a Rewind Debugger integration — [PoseSearch Runtime/Public](https://github.com/EpicGames/UnrealEngine/tree/release/Engine/Plugins/Animation/PoseSearch/Source/Runtime/Public/PoseSearch); [Editor/Private](https://github.com/EpicGames/UnrealEngine/tree/release/Engine/Plugins/Animation/PoseSearch/Source/Editor/Private)

### Inferences
- For Byte-Engine, whose `AGENTS.md` asks for pure functions, separated layers, and no transient allocations, the closest match is Holden's flat matrix with AABB blocks and O3DE's split between shared data and per-instance state. Both map onto Rust slices and structs without trait objects or per-query allocation.
- A layered Rust design follows naturally: (1) a pure feature-extraction function from pose samples to a row; (2) normalization as a separate pure pass; (3) an accelerator trait with brute-force-AABB, KD-tree, or HNSW implementations (as in EraEngine and Bevy); (4) a per-character instance with history, query, and an inertialization state; (5) graph integration and root-motion reconciliation (as in the Godot synchronizers); (6) debugging (cost breakdown, histograms, and PCA, as in O3DE and Unreal).
- Byte-Engine's recent navigation work (continuous steering, gait picked by distance, per the git log) would supply the desired velocity and facing that Holden-style spring trajectory prediction expects. The trajectory predictor should take that velocity as input rather than raw gamepad state, which mirrors Unreal's `IPoseSearchTrajectoryPredictorInterface`.
- The O3DE mocap appears to be the only permissively licensed motion matching locomotion set among those surveyed. It suits default test data and examples, whereas LaFAN1 and lafan1-resolved can serve only non-commercial benchmarking.

### Gaps
- No public Rust crate offers a production-quality KD-tree, VP-tree, or HNSW tuned for about 27 to 60 dimensions with motion matching access patterns. I did not benchmark `kdtree`, `kiddo`, or HNSW crates for this workload.
- None of the permissive implementations includes Unreal-style multi-character interaction search or event-targeted search. These would have to be designed from the Unreal concepts alone.
- I did not check how complete the O3DE mocap set is (clip durations, total minutes, skeleton definition) beyond file names. The FBX files are LFS objects and were not downloaded.

### Inferences
- "Free" in the MxM and Motion Symphony READMEs is a statement of price and availability, not a grant of rights to copy or modify. Unless the author adds a license, Byte-Engine should treat both as read-for-ideas only, the same as Unreal.
- Studying ideas (algorithms, parameter choices, architecture) from EULA-only or unlicensed code is generally safer than copying text. Even so, a clean-room approach is advisable: write the design from the permissive sources and papers, and use Unreal, MxM, and Motion Symphony only to cross-check feature lists. This is a general practice, not legal advice.
- Apache-2.0 sources (O3DE, EraEngine, Bevy MM under its Apache option) carry a NOTICE and patent clause. MIT sources need only the copyright notice. A Rust engine under MIT OR Apache-2.0 can take both.
- Holden's MIT code ships a `database.bin` generated from LaFAN1, so the code is portable but its bundled data is not. Byte-Engine tests and examples should use the O3DE clips or self-captured data, not LaFAN1 assets.

### Gaps
- I did not check whether `UmutFarukDilli/motionmatchingreplicated` and other MIT-labeled GASP derivatives redistribute Epic content. If they do, their MIT label would not cover those assets.
- I did not verify the exact LaFAN1 license text in Ubisoft's repository: GitHub reports `NOASSERTION`, and the terms come from Holden's and lafan1-resolved's READMEs.
